> **Partially superseded on 2026-08-14:** Initiative 06 [ADR-011](../../06-copilot-solution-ecosystem-outcome/decisions/adr-011-solo-owner-repository-governance.md) replaces Decision item 4 and its applied one-review branch-protection state. ## Context

`docs/05-security/self-service-store-provisioning.md` recommends Architecture 4.B′ (a GitHub-verified provisioning broker that asserts entitlement to Infisical rather than minting and dispensing store credentials) and, in §11 (`@agent-sec`, first pass, WP-399/WP-400) and §11.9 (independent second pass, WP-401), scores the design against STRIDE+DREAD, ending 0 Critical / 3 High / 9 Medium / 5 Low across 17 findings. §11.8 names eight decisions that only the owner can ratify, gathered from §6.4, §7 (E-9), and the review itself. The owner's instruction ("do 3") is to adopt the security review's recommendations as the rulings, verbatim where the review states one, rather than reopen each as a fresh decision. This ADR is that ratification. It follows the naming and format of [ADR-006](ADR-006-ecosystem-setup-preflighted-saga.md), [ADR-007](ADR-007-onboard-schema-v2-breaking-bump.md), and [ADR-008](ADR-008-repair-and-publish-deferred.md).

**This ADR ratifies policy parameters and a governance fix. It does not build the broker.** Standing up the 4.B′ broker (the GitHub App membership check, the OIDC-issuer signing service, `cc connect`, `cc store verify`, the per-scope Infisical identities, the offboarding sweep) is a **NEXT initiative unlocked by this ADR**, not started by it — see Consequences.

## Decision

The eight rulings, each adopting the security review's recommendation from `docs/05-security/self-service-store-provisioning.md` §11.8 (list order preserved):

1. **Broker hosting and custody (§11.8 item 1).** Ratified as recommended: the broker is a small HTTP service co-located beside Infisical on the organization's own Coolify host (§4.B's comparison table, "the only workable home for on-demand provisioning"), holding its own signing key and (per the second-pass correction, §11.9 item 1) the GitHub App's private key, both in the host's own secret manager. **Genuinely lacking a recommendation:** the review asks that a specific individual be named as custodian of the host's secret manager and of the CI/CD deploy credential (E-19) but does not itself name one. Ratified as: the owner holds both until a named delegate is assigned — flagged as an open action, not resolved by this ADR.
2. **Access-token TTL (§11.8 item 2).** Ratified at the review's recommended value: Infisical `accessTokenTTL` = 15 minutes. This is the number that bounds the offboarding exposure window (E-5), the stolen-token blast radius (E-20), and the broker-outage graceful-degrade window (E-6); §11.7 shows it is also the number that makes the design's "closes G-12 by construction" claim concrete (maximum window between a GitHub-team removal and every live credential expiring = 15 minutes).
3. **Signing-key rotation cadence (§11.8 item 3).** Ratified at the review's recommended values: the broker's JWT-signing key rotates every 90 days on schedule, with immediate emergency rotation on suspected compromise, and a JWKS rotation overlap window of at least `accessTokenTTL` + 24 hours (≥ 24 hours 15 minutes at the ratified TTL) so tokens signed with the outgoing key keep validating through their natural expiry during a scheduled rotation.
4. **`team_scopes` push governance, E-16 (§11.8 item 4).** Ratified as the cheaper of the review's two named options and applied today: `enforce_admins: true` on `Everyone-Needs-A-Copilot/claude-copilot-internal`'s `main` branch protection. This is the single flag that actually closes the gap — with `enforce_admins: false`, the existing `required_approving_review_count: 1` rule does not bind `pablitoalejo` or `james-lukensow` (both hold `admin:true`) at all, which is the precise defect E-16 names; flipping it now makes the existing one-reviewer rule apply to every push to `main`, including pushes by either admin account, with no new file and no second control to keep in sync. A `CODEOWNERS` rule was the review's other named option but is not additionally needed: `require_code_owner_reviews` would still be moot for both admin accounts without `enforce_admins: true`, so the flag is the load-bearing half of either option and is sufficient on its own. See the Applied section below for the before/after state, verified live via `gh api`.
5. **Admin-pair retirement window, E-9 (§11.8 item 5).** Ratified at the review's recommended value: 30 days of clean audit-log evidence (no authentication against the current org-wide `INFISICAL_CLIENT_ID`/`_SECRET`) before that pair's client secret is revoked and its identity deleted.
6. **Infisical platform-admin MFA, E-17 (§11.8 item 6).** Ratified as recommended: hardware-key MFA is required on every account with Infisical console/platform-admin access, named individuals only, reviewed on the same cadence as item 5's retirement window. **Execution requires the owner's own accounts** — see the owner-hands section below for exact instructions; this ADR ratifies the requirement, it does not itself enable the setting.
7. **DNS custody for the broker's hostname, E-18 (§11.8 item 7).** Ratified as recommended: registry lock, DNSSEC, and 2FA on the DNS/registrar account for the broker's discovery hostname, plus a direct question to Infisical about JWKS caching/pinning behavior (§10 item 8) before this ships. **Execution requires the owner's own registrar/DNS accounts** — see the owner-hands section below for exact instructions; this ADR ratifies the requirement, it does not itself configure the registrar.
8. **Admin-pair retirement trigger, the fork named in §11.8 item 8.** Ratified as the review's recommendation: evidence-gated, not calendar-gated. The org-wide admin pair retires on **first-B′-login plus 30 days of clean audit evidence** (E-9 step 3's dogfood-before-demolition sequencing, then item 5's window) — never on a fixed date independent of actual cutover.

| `required_pull_request_reviews.required_approving_review_count` | `1` | `1` (unchanged) |

Verified live before the change (`gh api repos/Everyone-Needs-A-Copilot/claude-copilot-internal/branches/main/protection`) and re-verified live after (`gh api -X POST .../protection/enforce_admins` then a second read of the same endpoint). ## Owner-hands items — execution requires the owner's own accounts

| Item | Ratified requirement | Exact instructions |
|---|---|---|
| **Infisical platform-admin MFA (E-17, ruling 6)** | Hardware-key MFA required on every Infisical console/platform-admin account, named individuals only | In the Infisical instance's own admin console, under the organization's security/authentication settings, enable/enforce MFA for the organization, then, for each account that holds platform-admin/console access, register a hardware-backed authenticator (a FIDO2/WebAuthn key such as a YubiKey, or a platform authenticator like Touch ID/Windows Hello backed by a hardware-protected key) rather than a TOTP-only second factor. Do this **before** the console is used to create the first per-scope identity (§6.1's backstage setup), since that console session is the root of trust E-17 protects. Review the account list on the same cadence as ruling 5's 30-day retirement window. |
| **DNS/registrar custody for the broker's hostname (E-18, ruling 7)** | Registry lock, DNSSEC, and 2FA on the DNS/registrar account for the broker's discovery hostname | At whichever registrar holds the zone for the broker's OIDC discovery hostname (the illustrative `secrets.ineedacopilot.com` shape in §8 is a worked example, not the real endpoint — use the actual hostname once chosen): (1) enable two-factor authentication on the registrar account itself, not just on downstream services; (2) enable Registry Lock (`clientTransferProhibited`/registry-level transfer lock) if the registrar or TLD offers it; (3) enable DNSSEC signing for the zone; (4) separately, contact Infisical directly (support channel or account team) and ask in writing whether a pinned/static JWKS is supported as an alternative to live discovery-URL trust — this closes §10 item 8 and directly bounds E-18's blast radius. |

## Consequences

- §11.8's ruling list in `docs/05-security/self-service-store-provisioning.md` is closed: every item now has a recorded ratification, an ADR to cite, and (for the two owner-hands items) a named next action rather than an open decision.
- The E-16 governance gap — the one item the review said to fix "regardless" of the rest of the ruling list — is closed today, not deferred to broker implementation. It required no code and no new file.
- **This ADR does not authorize building 4.B′.** The broker, `cc connect`, `cc store verify`, the per-scope Infisical identities, the GitHub App `Members: read` wiring, and the offboarding sweep remain entirely unbuilt (per the design doc's own "What is true today" line). A future task that begins that build must open as a new initiative and may cite this ADR for its ratified parameters (TTL, rotation cadence, governance posture) rather than re-litigating them.
- The two owner-hands items (Infisical MFA, DNS/registrar custody) are ratified as requirements but not yet executed; they block "day zero" (§6.1) of any future broker build, not this ADR.
- Item 1's custodian gap (who holds the Coolify host's secret manager and CI/CD deploy credential) is a named open action, not silently absorbed — a future task must assign it before the broker is deployed.

## Rejected alternatives

- **Leaving §11.8 open pending a full owner review session of all eight items individually.** Rejected per the owner's explicit instruction: adopt the security review's recommendations as the rulings now, rather than hold the governance fix (E-16) and the parameter ratifications hostage to a longer scheduling exercise.
- **Deferring the E-16 fix until the broker is actually built.** Rejected: the review states this fix should happen "regardless" of the rest of the design's fate, because the gap it closes (unreviewed push access to `team_scopes`) is live today, in the current `ecosystem.yml`, independent of whether 4.B′ is ever implemented.
- **Adding a `CODEOWNERS` file in addition to `enforce_admins: true`.** Rejected for now as unnecessary: with `enforce_admins: true` already binding both admin accounts to the existing one-reviewer rule, a `CODEOWNERS` entry would add a second file to keep in sync without closing any gap the flag does not already close. Revisit if the org later wants to name a *specific* required reviewer for the `team_scopes` path rather than any one of the existing collaborators.
- **A longer access-token TTL for steady-state ergonomics.** Rejected per the review's own tradeoff: 15 minutes is short enough to bound offboarding exposure and outage blast radius to something an admin sets rather than a sweep an admin must remember to run, and the design's ladder rung already caches within that TTL so steady-state reads are not dominated by re-mint round trips.
