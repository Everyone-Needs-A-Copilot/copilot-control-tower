What you actually need to run it

The short version: if you install it, you need nothing. A signed release just runs. Someone who publishes releases signs them once. And the org infrastructure — a telemetry collector, a shared secret store — is optional, and only for organizations that want those features. Access to an org or department is granted through a GitHub repo, not a device push. This page says exactly who needs what.

If you're installing it

The end user

A developer or an employee who runs the menu-bar app. You download a signed release and open it. No account, no certificate, no infrastructure, no configuration file.

→ You need nothing.

If you're distributing it

The publisher / IT admin

Whoever cuts the releases or deploys it across an organization. You sign each release once, and — only if you want the fleet features — stand up a little optional infrastructure.

→ A one-time signing setup, plus optional infra.

Signing · one-time, publisher-side

Nobody signs but the publisher

Code signing is how an operating system decides to trust a binary. An unsigned, always-on background agent triggers a security warning and fails an enterprise security review — which this product is built to pass. So releases are signed. But signing is done once, by whoever publishes the release; everyone who downloads that release runs it with no signing step at all. The only people who ever sign are those who fork and rebuild it themselves — the same as any open-source project.

Infrastructure · optional, organization-side

The endpoints, and who truly needs them

These are servers or URLs the app can talk to. None are hosted by us — an organization stands them up if it wants that feature. For an individual, all four are unnecessary. Each is a self-hosted, open component; there is no paid tier and no service to sign up for.

By situation

Start from where you are

Situation 01

An individual developer

You just want to run it on your own machine.

  • ✓Download a signed release and open it.
  • ✓Sign in when the app asks (your own accounts).
  • —No infrastructure. No certificate. No config.
Situation 02

A small team

You distribute it to a handful of people.

  • 1Get an Apple Developer ID; sign + notarize releases.
  • 2Optional: an update feed so the team auto-updates.
  • 3Optional: a shared secret store if you share integration credentials.
Situation 03

An enterprise fleet

IT deploys it across many machines.

  • 1Sign + notarize; add minisign 2-of-N for update integrity.
  • 2Stand up the org/department repos and grant GitHub team access — that's the entitlement.
  • 3Optional: telemetry collector for the fleet dashboard.

Honest status

What is, and isn't, wired up yet

The app is built and its seams for all of the above exist and are tested. But turning them on for real depends on things only an owner can supply: the signing certificates above, the CLI engine the app drives (published separately), and whichever endpoints an organization chooses to host. Until those land, the app runs against local mocks.

The one gap worth naming: proactive OS notifications aren't built yet on either platform — the app surfaces what needs attention in its own window instead. Everything else on this page is code-complete and waiting on the credentials and endpoints, not on more building.

Deeper detail for whoever deploys it lives in the repository under docs/06-deployment/ — the per-area owner-gated checklists and the platform bring-up runbooks.
