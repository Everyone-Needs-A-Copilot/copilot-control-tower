## 0. Trust boundaries (mapped before any code review, per methodology)

| Boundary | One side | Other side | Crossing mechanism |
|---|---|---|---|
| **B1 — Process/OS boundary** | Control Tower (userland, no admin, hardened runtime) | macOS kernel, other user processes | Entitlements, sandboxless-but-hardened-runtime Developer ID signing |
| **B2 — CLI invocation** | Control Tower (Rust core) | `copilot`/`cc` binaries (vendored, separate repo/CI) | Absolute-path `Command::new` spawn — never PATH, never bare `copilot` (avoids the `gh copilot` collision) |
| **B3 — `--json` parse boundary** | `copilot`/`cc` stdout (trusted-but-versioned) | Control Tower's JSON deserializer + UI renderer | The versioned `--json` contract (`cli-contract.md`) |
| **B4 — Self-update boundary** | The update feed (`UpdateFeedURL`) | The running app binary on disk | Tauri signed-manifest updater, minisign verification, watchdog-mediated swap |
| **B5 — launchd/watchdog boundary** | `launchd` (OS-level, `~/Library/LaunchAgents`, per-user) | The app process | Crash-only `KeepAlive={SuccessfulExit:false}` relaunch |
| **B6 — MDM managed-config domain** | `com.apple.ManagedClient.preferences` (forced) vs `~/Library/Preferences/dev.enac.controltower.plist` (user-writable) | Control Tower's config reader | `CFPreferencesAppValueIsForced` |
| **B7 — Telemetry sink** | Control Tower (org-scoped emitter) | The org's IT dashboard endpoint | HTTPS to the org-configured (or `AdminContact`-configured) endpoint |

Everything in §2 is organized by which of these seven boundaries it crosses.

## 1. Trust basis

**Two independent trust roots, deliberately not one:**

1. **Apple's Developer ID chain** — codesigns and notarizes the `.app`/`.dmg`; Gatekeeper/`spctl` verify it against Apple's root, not ours. Hardened runtime, userland-only entitlements (**no admin, no privileged helper** — invariant #4's "no `--force`" has a platform-level analogue: Control Tower cannot elevate even if it wanted to).
2. **The Tauri minisign key** — independent of the Apple chain, verifies the *content* of a self-update manifest before the watchdog promotes a staged bundle (`architecture.md` §7). This is compiled-in code — the public key ships in the binary, not in any config domain, exactly as invariant #4 requires ("trust roots are compiled-in code, not config").

**Why two roots, not one:** Apple's chain proves *this Team ID built it*; minisign proves *this update manifest is the one the release process actually cut*. A single popped credential (say, a leaked Developer ID cert) doesn't automatically grant the ability to ship an *update* — the minisign key is a second, separately-custodied gate the watchdog checks before promoting a staged bundle (§7 of the architecture doc, closing B-M4 — see §3.2 below).

**Why config can't weaken this (invariant #4):** `UpdateFeedURL`, `FoundationMirror`, `HTTPSProxy`, `AllowSelfUpdate`, and friends are read via `CFPreferencesAppValueIsForced` — a value present *only* in the user-writable domain is **ignored**, not merged, and the compiled-in default is used instead (`architecture.md` §8.3, closing B-C5). This is the direct architectural answer to the STRIDE question "can an attacker weaken the trust basis via config": **no**, because the only domain that can override a security-sensitive default is one the attacker (a local, non-admin user, or malware running as that user) cannot write to. The same principle is extended in `credentials-and-boundary.md` §1.4 to *which OAuth issuers are trusted at all* — no config domain, forced or not, can add a new trusted secret-acquisition endpoint; that requires a signed CLI release. This threat model extends it one more notch in §2.5/§4 below (a gap this pass found, not yet closed).

**Third-party trust extension:** the vendored `copilot`/`cc` binaries are built in a *different* repo (`claude-copilot`) under different CI. This is a cross-repo signing contract, not a shared trust root: `claude-copilot` CI publishes already-signed, notarized, pinned-SHA artifacts; Control Tower CI *verifies* (`codesign`, `spctl`), **never re-signs** (`architecture.md` §7, closing B-H1). Re-signing someone else's binary would mean Control Tower's own signing identity vouches for code it didn't produce and can't audit line-by-line — exactly the anti-pattern invariant #4 exists to prevent.

## 2. STRIDE analysis by trust boundary

### 2.1 B2 — the CLI-invocation path (translocation-safe absolute path vs. `gh copilot` collision / path hijack)

| STRIDE | Threat | Status |
|---|---|---|
| **S**poofing | A `gh copilot` alias/wrapper on `$PATH` answers in place of the real `copilot`/`cc` if Control Tower ever spawned by bare name | **Closed by construction** — invariant #4's tech rule ("never bare `copilot`") + B-L3's fix: the binary is resolved relative to the *running bundle's* `Bundle.main.bundleURL`, never PATH, never a hardcoded `/Applications/...` (which would break under Gatekeeper translocation). No PATH lookup exists to spoof. |
| **T**ampering | Substituting the vendored binary on disk between resolution and exec (TOCTOU), or modifying it in place | **Bounded, not fully closed.** The vendored binaries ship *inside* the signed `.app` bundle (or are independently notarized per C2's fix); modifying a file inside a sealed, codesigned bundle invalidates the seal and the next Gatekeeper/`spctl` check (including the app's own `cli-spawnable` doctor check, A-C2's fix) surfaces it as a distinct finding rather than a silent bypass. Residual: an attacker who already has arbitrary code execution as the same user can still *observe* and *race* the exec (classic TOCTOU), but gains nothing beyond what same-user code execution already grants — no privilege boundary is crossed. |
| **R**epudiation | N/A — local process spawn, not a network action; covered under B7 (telemetry) for what gets reported about it. | — |
| **I**nformation Disclosure | None specific to this boundary beyond what B3 covers (the CLI's own stdout). | — |
| **D**enial of Service | Gatekeeper/quarantine killing every spawn of an un-notarized vendored binary on a cold machine, rendering the app unable to do anything but show failures (A-C2, Critical) | **Closed** by the fix: independently notarize the vendored binaries (or exec from inside the signed bundle), `.pkg` postinstall strips quarantine, and a named `cli-spawnable` doctor check distinguishes this from a generic red rather than mis-reporting a benign state. |
| **E**levation of Privilege | An attacker-substituted binary at the resolved path runs with Control Tower's (userland, hardened-runtime, no-admin) privileges | Same residual as Tampering above — bounded to same-user, no privilege crossing, because Control Tower itself never runs elevated. |

### 2.2 B3 — the `--json` parsing boundary (malicious/malformed CLI output)

This is the boundary invariant #1 ("parse, never compute") exists to narrow: Control Tower's *only* job here is deserialize-and-render, never re-derive a security decision from the payload.

| STRIDE | Threat | Status |
|---|---|---|
| **S**poofing | A schema version the app doesn't recognize, or one it recognizes but that no longer means what it used to (B-H6) | **Closed** — bidirectional `min_schema`/`max_schema` gating (`architecture.md` §6): a CLI schema *older* than Control Tower's floor is as fatal as one newer; the dead-end "run doctor in a terminal" degrade (useless to a Bob with no terminal) is replaced with an in-app "versions don't match — click to update." |
| **T**ampering | A missing security-relevant field (`destructive`, `signed`, `severity`) silently defaulting to a permissive/safe-looking value (the exact silent-bypass shape B-H6 warns about) | **Closed** — "missing security-relevant fields fail closed... absent `destructive`/`signed`/`severity` ⇒ treated as destructive/unsigned/fail, never as safe" (`architecture.md` §6). |
| **R**epudiation | The app's own local action log is user-writable, so "append-only" is a convention, not an enforced guarantee (B-L2, Low) | **Partially open** — recommend either dropping the "tamper-evident" claim for the local log or hash-chaining entries with a periodic head-hash anchor to the org telemetry endpoint (B-L2's own fix), so local truncation is *detectable* server-side even though it isn't *preventable* client-side. Not yet implemented per the architecture doc's action-log description (`architecture.md` §9 mentions a "hash-chained action log anchored to the org endpoint" for the always-on surface — confirm this covers the general local log, not only the deprovision/security-trailer subset, before closing B-L2). |
| **I**nformation Disclosure | None beyond what's already in the payload by design (schema fields are deliberately content-free for safety signals per invariant #6/A-C5). | — |
| **D**enial of Service | A malformed/oversized JSON payload crashing the deserializer | Not explicitly addressed in either red-team doc or the architecture doc. **Residual — flag for WS-A**: the versioned schema needs a documented size/depth bound and a fail-closed (not panic) parse-error path, same posture as the missing-field case. |
| **E**levation of Privilege | **NEW — unsanitized rendering of CLI-supplied strings in the Tauri webview.** Fields like a skill/finding *name* or a `what-changed` description ultimately originate from git-repo content (org/dept/foundation tiers) and are rendered into the webview UI. Neither red-team doc examines the webview-rendering surface at all (their scope was process model, MDM, signing, notifications — not the UI layer). If a crafted name/description string is rendered unescaped, it is a content-injection (XSS-in-webview) vector; in a Tauri app, a webview compromise is more consequential than in a browser tab because the webview has an IPC bridge to Rust-side commands. | **Open — NEW finding, not in either red-team doc.** Mitigating factors: content reaching the webview is either (a) covered by the same signature that gates the whole payload (so injecting a hostile name requires forging or riding a legitimately signed commit — a much higher bar than a pure UI bug), or (b) local-only strings the CLI itself generates (lower attacker control). Recommend: render all CLI-supplied strings via the framework's default text-escaping path (never `dangerouslySetInnerHTML`-equivalent or raw HTML injection into the webview), and scope the Tauri IPC command allowlist tightly enough that even a successful script-injection in the webview cannot invoke a destructive Rust-side command (invariant #1 already helps here — the Rust side does no resolution/wipe logic itself, narrowing what an XSS could even ask it to do). |

### 2.3 B4 — self-update (invariant #4: no `--skip-verify`/`--force`; minisign key compromise)

| STRIDE | Threat | Status |
|---|---|---|
| **S**poofing | An attacker-controlled update feed masquerading as `UpdateFeedURL` | **Closed on the config side** — B-C5's fix (§2.5 below). Remains open on the *content* side only if the minisign key itself is compromised (next row). |
| **T**ampering | **Minisign private-key compromise → a signed-but-malicious update ships fleet-wide** (B-M4, rated Medium by red-team B: "Medium (High impact, lower likelihood given key custody)"). Aviator/Control Tower holds a live `gh` token and auto-materializes executable-adjacent content on a timer — if the minisign key *and* the codesign cert are both popped, every machine auto-installs attacker code with the user's token and the ability to rewrite `.claude/` agents. | **Mitigated, not eliminated** — two-of-N signing (or a transparency-log witness) so one popped key isn't fleet-wide RCE; codesign cert and minisign key held in **separate custody**; staged rollout with anomaly-halt (`architecture.md` §7, closing B-M4). **Signing custody itself is an open decision** (`architecture.md` §11 item 1) — who holds the second of two-of-N keys is not yet assigned. See §5 below. |
| **R**epudiation | A staged-rollout anomaly-halt depends on telemetry to detect post-update crash/behavior spikes — if telemetry is off (the pre-C5-fix default), the anomaly-halt has no signal | Closed by the same fix as A-C5 (safety-class telemetry on by default for managed machines) — but the anomaly-halt's dependency on telemetry should be stated explicitly wherever it's specified, so it isn't silently assumed to work on unmanaged/opted-out installs. |
| **I**nformation Disclosure | N/A for this boundary. | — |
| **D**enial of Service | A bad update that crashes before its own health-probe can run traps its own rollback logic (B-C3, Critical) | **Closed** — rollback owner moved to the tiny, never-self-updated watchdog, gated on an early liveness heartbeat written before webview init; no heartbeat within timeout ⇒ discard staged bundle, keep current, mark the version poisoned, notify (`architecture.md` §3). |
| **E**levation of Privilege | A successful minisign-key-compromise attack is, functionally, remote code execution across the fleet at the user's own privilege level (not root — Control Tower never runs elevated) but with a live OAuth/`gh` token in scope | Same as Tampering row — mitigated by two-of-N signing, not eliminated; this is the single highest-*damage* threat in this document (see DREAD, §3). |

### 2.4 B5 — the launchd crash-only watchdog (`KeepAlive` abuse)

| STRIDE | Threat | Status |
|---|---|---|
| **S**poofing | N/A | — |
| **T**ampering | `~/Library/LaunchAgents/dev.enac.controltower.plist` is **user-writable** (per-user, not root — invariant "per-user, not per-machine," `architecture.md` §8.3). An attacker who already has same-user code execution could edit the plist's `Program` path to point at a different binary, or flip `KeepAlive` to `true`, turning the legitimate watchdog into a persistence mechanism for arbitrary code (a well-known macOS malware technique: hijacking a legitimate LaunchAgent for persistence). | **Residual, not closed — and out of scope for the app to close.** This requires an attacker to *already* have same-user code execution; hijacking Control Tower's watchdog grants no privilege the attacker didn't already have (no elevation), only *persistence* dressed as a trusted process name. This is a generic property of any per-user LaunchAgent, not specific to Control Tower's design, and is not addressed by either red-team doc (their `KeepAlive` findings — B-C2 — are about the *legitimate* watchdog fighting the user or crash-looping, not about a malicious edit). Flagged in §5 as a residual assumption, not a design defect: Control Tower does not attempt endpoint-security-style plist-tamper detection, and doing so would be scope creep beyond "supervisor over the CLI." |
| **R**epudiation | N/A | — |
| **I**nformation Disclosure | N/A | — |
| **D**enial of Service | `KeepAlive=true` (the now-rejected core-doc design) would make launchd fight a clean `Cmd-Q`/quit and crash-loop a bad build at throttle speed (B-C2, Critical) | **Closed** — `KeepAlive={SuccessfulExit:false}` only, `RunAtLoad=false`, a `ThrottleInterval`, and a launch-failure circuit breaker (N non-zero exits in a window ⇒ stop relaunching, surface "reinstall") (`architecture.md` §3, invariant #2). |
| **E**levation of Privilege | Orphaned LaunchAgent/`SMAppService` registration surviving a drag-to-Trash deletion, relaunching a stale/rollback copy pointed at a nonexistent or wrong binary (B-H2, High) | **Closed** — a signed uninstaller runs `launchctl bootout` + `SMAppService.unregister()` + keychain cleanup; the watchdog self-`bootout`s if its own `Program` path goes missing (`architecture.md` §7). |

### 2.5 B6 — the managed/MDM config domain (spoofed config)

| STRIDE | Threat | Status |
|---|---|---|
| **S**poofing | A local, non-admin attacker (or malware running as the user) writes `defaults write dev.enac.controltower UpdateFeedURL https://evil/...` on an unmanaged machine, repointing the auto-updater, the ecosystem mirror, or the HTTPS proxy (full supply-chain MITM) — B-C5, Critical, the platform red-team's #3 must-fix. | **Closed for the enumerated security-sensitive keys** — `UpdateFeedURL`, `FoundationMirror`, `EcosystemSeedURL`, `HTTPSProxy`, `GitHubHost`, `AuthMode`, `AllowSelfUpdate`, `Deprovisioned` are read via `CFPreferencesAppValueIsForced`; a value present *only* in the user domain is ignored in favor of the compiled-in default and logged as a tamper event (`architecture.md` §8.3). This holds identically on managed and unmanaged machines, because it's a property of *which domain is honored*, not of whether MDM is present. |
| **T**ampering | Same mechanism as above, for the same key set. | Same closure. |
| **R**epudiation | A logged "tamper event" for a rejected user-domain write is only useful if something reads that log — ties to the telemetry-sink question in §2.6. | Depends on §2.6's fix landing; not independently closed. |
| **I**nformation Disclosure | `DisableWizard=true` with a missing required key: undefined behavior across partial-apply, malformed-value, and type-coercion edge cases (A-C1/B-H4, Critical/High) | **Closed** — schema-validate the managed profile before entering silent mode; distinguish *absent* (retry over a settling window), *present-but-invalid* (immediate "IT config error: `<key>`"), and *valid*; type-check bool/URL fields; never fall through to Bob-interactive under `DisableWizard` (`architecture.md` §4). |
| **D**enial of Service | N/A beyond the above. | — |
| **E**levation of Privilege | **NEW — `AdminContact` (the safety-escalation endpoint) is *not* in the enumerated forced-domain-only key list.** `architecture.md` §8.3 states the managed profile "pre-seeds... plus a **mandatory `AdminContact`**/escalation endpoint," but the very next paragraph's explicit enumeration of keys "honored ONLY from the managed (forced) domain" is `UpdateFeedURL, FoundationMirror, EcosystemSeedURL, HTTPSProxy, GitHubHost, AuthMode, AllowSelfUpdate, Deprovisioned` — `AdminContact` is absent from that list (as is `DisableWizard`, though that key's misuse ceiling is lower — it only suppresses prompts, it doesn't redirect a trust-sensitive channel). If `AdminContact` is read the same way as an *ordinary* (non-security-sensitive) config key — i.e., a user-domain value is merged/honored when no managed value is forced — then a local attacker (or the very malware A-C5's fix is meant to report *on*) can silently redirect every safety escalation (sig-fail, auth-revoked, policy-conflict, stalled-onboarding, persistence-disabled, notifications-off) to an attacker-controlled endpoint instead of real IT. This would **fully defeat A-C5's fix** ("safety escalation is a required managed-profile key, on by default for managed machines") without ever touching the escalation *logic* — only its destination. | **Open — NEW finding, not in either red-team doc.** Neither red-team examined `AdminContact` specifically as a spoofing target (B-C5 named the update/mirror/proxy/auth keys; A-C5 was about the on/off default, not the endpoint's integrity). Recommend: add `AdminContact` to the same `CFPreferencesAppValueIsForced`-gated key list as the other security-sensitive keys, with the same "user-domain-only value ⇒ ignored + logged as tamper" treatment — closing this is a small, mechanical extension of the existing B-C5 fix, not a new mechanism. |

### 2.6 B7 — the telemetry sink (data exfil / PII)

| STRIDE | Threat | Status |
|---|---|---|
| **S**poofing | A spoofed telemetry/IT-dashboard endpoint (see §2.5's `AdminContact` finding — the endpoint identity *is* the spoofing surface here). | Open, same finding as §2.5; closing the config-domain gap closes this too. |
| **T**ampering | Telemetry payload tampered in transit | Not addressed in either red-team doc; assume standard TLS to the org endpoint is the baseline — **not independently specified** in the architecture doc beyond "HTTPS." Flag as an assumption in §5, not a finding — no evidence of a defect, only absence of an explicit statement. |
| **R**epudiation | The safety-escalation channel's own audit trail — who resolved a sig-fail/auth-revoked event, and when — is IT's own dashboard, outside Control Tower's boundary once emitted. Within Control Tower's boundary, the hash-chained action log (`architecture.md` §9) anchors a head-hash to the org endpoint so local truncation is server-detectable, per B-L2's fix. | Addressed at the emission boundary; the receiving side is IT's system, out of scope. |
| **I**nformation Disclosure | (a) `machine_id` colliding across two users sharing one Mac, blending two people's health state and undercounting distinct machines; (b) an org-wide salt making the HMAC a stable, re-identifiable pseudonym an admin can correlate via MDM inventory; (c) a misclassified layer leaking a personal skill's *name* (e.g., a personal-tier skill literally named something sensitive) into org-scoped usage telemetry if it shadows an org item (B-H5, High) | **Closed** — `machine_id = hmac(hardware_uuid + posix_uid, per-install-random-salt)`, keyed per-user not per-device, salt random-per-install and never transmitted (non-reversible from MDM inventory); usage emits only items whose CLI-computed `winning_layer ∈ {org,dept,foundation}` **as computed by `resolve --explain`**, dropping any item whose `shadowed_by` names a personal path — never trusting a name string's apparent layer (`architecture.md` §9). |
| **D**enial of Service | Safety escalation gated behind off-by-default analytics telemetry meant every "Escalate to IT" rung reached no one on a default managed machine (A-C5, Critical — the platform's own #1 must-fix) | **Closed** — safety escalation (content-free: sig-fail, auth-revoked, policy-conflict, stalled-onboarding, persistence-disabled, notifications-off) is split from analytics and is **on by default** for managed machines via the mandatory `AdminContact` key; analytics (usage/adoption) stays genuinely opt-in (`architecture.md` §9). |
| **E**levation of Privilege | N/A for this boundary beyond §2.5's finding. | — |

## 4. Invariant-to-defense mapping

| Invariant | Threats it closes |
|---|---|
| **#1 — Parse, never compute** | Narrows the entire B3 boundary to render-only: even the NEW webview-injection finding (§2.2) is *bounded* by this invariant, because there is no resolution/sync/signature/wipe logic client-side for a successful script injection to invoke — the worst case is a rendering bug, not a security-decision bypass. Also structurally prevents the app from ever computing its own (possibly wrong) verdict on a `destructive`/`signed` field — that computation, and its fail-closed defaults (B-H6), live in the CLI/schema contract, not in app code that could independently drift. |
| **#2 — Single process** | Closes B-C1 (double-sync race from a daemon + in-app fallback loop both driving `copilot update`) and B-C2 (`KeepAlive=true` fighting the user / crash-looping) by construction — there is no second scheduler to race, and the CLI's own `flock` on `copilot.lock` means even a hypothetical stray second process can't double-write. Narrows the watchdog's job (§2.4) to crash-only relaunch, which is what keeps the residual LaunchAgent-tampering finding bounded to "persistence," never "a second live scheduler to exploit." |
| **#3 — Never-destroy** | Closes any threat path where an attacker triggers Control Tower's own repair/re-materialize machinery *as a weapon* against personal content — the invariant means even a fully successful trigger of the app's normal healing behavior cannot touch a dirty personal working tree. This is the app-level backstop for `credentials-and-boundary.md`'s leakage-wall guarantees (§2.3 of that doc) — re-materialization pressure never becomes a path to overwrite or destroy personal-tier content. |
| **#4 — Security posture inherited/enforced, never weakened** | Closes B-C5 (user-domain preference spoofing of the update feed/mirror/proxy/auth mode) and — once §2.5's finding is addressed — will close the `AdminContact`-spoofing gap this pass found. Also the invariant under which B-M4 (minisign key compromise) is *mitigated* (two-of-N signing keeps "no `--skip-verify`, no `--force`" meaningful even under partial key compromise) and under which B-H1 (cross-repo signing) is closed (verify-never-re-sign is itself a "never weaken the posture you inherited" application). |
| **#5 — Route by actor-competence × reversibility** | Closes A-C3 (a Bob notification as the *sole* control on an active security exposure) by auto-suspending a security-shadowed personal override rather than leaving it to Bob's attention; closes A-H11 (held-major approval handed to someone who can't judge it) and M15 (capability-policy noise training Bob to ignore real alerts, which would otherwise compound C3). Indirectly hardens against social-engineering-flavored threats: an attacker cannot rely on "ship something technically signed and count on Bob clicking through a warning," because security-classed events don't wait on Bob at all. |
| **#6 — One-way inheritance; secrets never travel in it** | This is `credentials-and-boundary.md`'s domain in full (Problems 3 and 4) — not re-derived here. The app-level relevance: Control Tower never holds a secret or a cross-tier credential itself (§3 of that doc's piece-ownership table), so even if an app-level compromise occurred (e.g., the §2.2 webview finding, worst case), there is no secret material or shared-tier write credential resident in the app process for it to reach. |

## 5. Residual risks / assumptions

1. **Signing custody (open decision, carried from `architecture.md` §11 item 1)** — two-of-N signing vs. a transparency-log witness for Control Tower releases is specified as the *mechanism*, but **who holds the second of two-of-N keys is not yet assigned.** This is the single largest open item bearing on the #2-ranked DREAD threat (minisign key compromise, §3). Until assigned, treat the mitigation as "designed, not yet operationally real" — a two-of-N scheme with an unassigned second custodian is, in practice, a one-of-one scheme with a placeholder.
2. **`AdminContact` forced-domain gap (§2.5, §3 rank #1)** — flagged as the top open finding in this document; recommend closing before the safety-escalation channel (A-C5's fix) is treated as fully hardened.
3. **Webview content-injection surface (§2.2, §3 rank #3)** — not yet examined by either red-team doc because the UI layer wasn't built at the time of those reviews; revisit once the actual rendering code exists (P1/P2 of the phased roadmap), since this threat model can only reason about it structurally, not empirically.
4. **Local action-log tamper-evidence (B-L2)** — "tamper-evident" is currently an overclaim for a user-writable file; either downgrade the claim or confirm the hash-chain-anchored-to-org-endpoint mechanism (`architecture.md` §9) covers the general local log, not only the security-trailer/deprovision subset.
5. **`--json` payload size/depth bounds** — not specified in either red-team doc or the architecture doc; a malformed/oversized payload's failure mode (fail-closed parse error vs. panic/DoS) should be added to the CLI-contract schema work (WS-A) rather than assumed.
6. **Watchdog LaunchAgent tampering (§2.4, §3 rank #5)** — explicitly out of this app's threat boundary. It requires a same-user code-execution precondition Control Tower doesn't introduce and doesn't worsen; documented here so it isn't later mistaken for a gap in this design specifically.
7. **Telemetry transport integrity** — assumed to be standard TLS to the org endpoint; not independently specified beyond "HTTPS" in the architecture doc. No evidence of a defect — flagged as an assumption, not a finding, per this review's own rule against flagging without confirming evidence.
8. **Kiosk/lab machine-credential depth** (`architecture.md` §11 item 3, B-H7) — still an open decision upstream of this document; any app-level threat analysis of the kiosk path should be revisited once that decision lands, per the same open item already tracked in `credentials-and-boundary.md` §1.5.

## 6. A note on scope and naming

The two red-team documents (`redteam-platform.md`, `redteam-use-cases.md`) predate the product's rename from "Aviator" to "Control Tower"; their finding IDs (A-C1…A-M17, B-C1…B-L3) are the stable citation keys used throughout this document and are unchanged by the rename — only the prose product name differs. This threat model does not re-litigate any finding those two documents already closed; it (a) restates the closure in STRIDE/DREAD terms for the enterprise-security-review audience this document is written for, and (b) adds exactly three items neither red-team examined: the `AdminContact` forced-domain gap (§2.5), the webview content-injection surface (§2.2), and the `--json` payload size/depth bound (§5.5) — all marked **NEW** at point of first mention.
