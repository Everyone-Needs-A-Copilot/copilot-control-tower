Onboarding

Here's what you're building, and the whole path

Your copilots live in a set of shared spaces on GitHub that build on one another. The open-source foundation sits at the bottom. Your organization adds its own on top. Each department adds what only it needs. Each person adds their own on top of that. Everyone inherits everything beneath them, so you share broad capabilities widely and keep specialized ones narrow.

  1. 1Describe your organization here.
  2. 2Claude Code sets it up in your terminal.
  3. 3Come back and run the Setup check.

This app never changes anything on GitHub itself. It gets you ready, hands the work to Claude Code, and checks the result.

Onboarding

Integrations

An integration here is a small command-line tool a developer builds, so a copilot can reach a system like Salesforce or your calendar. It isn't something you switch on.

How integrations work

It cascadesBuilt and published for the whole organization, it's inherited by every department. Published for one department, it belongs only there. Published nowhere, it exists for no one.
The key lives elsewhereAn integration names the key it needs. The key never comes near this app. It lives in the shared store, handed out only to the right team.

How integrations will arrive, a lifecycle preview

  1. An engineer on a department builds skills, agents, and integrations inside that department's spaces. Give an engineer write access to a department's team and they can build there.
  2. Each integration is added to a registry, a plain document that lives in the same space and lists what has been built.
  3. Merging that document to the main copy publishes the integration.
  4. From then on, the people entitled to that space see it, and the app your team uses can let them know when a new one arrives.

Your shared secret store

A shared secret store is one service that holds your organization's keys and hands them out by team. Shared integrations need it: an integration names the key it needs, and at runtime the store checks that the person is on the right GitHub team and only then hands over the key. That is why a key never lives in a repo or in this app.

Journey B. Integrations lifecycle

The admin's role in this journey is education only. Integrations are built and published by department engineers, in the departments' own repos; the app never declares, collects, or configures one. The engine, and the org setup file, know nothing about specific integrations; existence lives in per-repo registries, gated by entitlement. What governance no longer contains. Stated explicitly, because the removals are the design.

What was killed, and why

For review completeness: the surfaces the old build had that this redesign removes outright, not merely restyles.

The members panel

GitHub is the only user-management surface. Onboarding creates a team and a grant that makes joining possible; it never adds or removes a person. That act, and its undo, lives on GitHub.

The seed YAML form

The deterministic script writes ecosystem.yml from the plain-language brief. The seed is demystified in Orientation and shown concretely in Review, never hand-authored in a form.

Policy signers

Deferred entirely from v1. No panel, no user-facing concept. V1 relies on the GitHub protections the script configures automatically.

The in-app run button

The app fires no mutation and streams nothing. Review and hand off enumerates, writes the non-secret brief, and generates a copyable command; the old streamed rows relocate to Claude Code's terminal narration.

Deprovision, by button

Restructured into Someone left: instructional guidance naming GitHub teams to remove and store keys to rotate. The app renders what to do and where; it triggers nothing.

The integration declaration form

Killed because integrations are created and published at the repo level, by department engineers, never registered in the admin. The admin's Integrations screen teaches and previews; it declares nothing.
