> **Why this exists before any Windows code.** `CLAUDE.md`'s invariants (single process, crash-only watchdog, never-destroy, security posture inherited-never-weakened, actor-competence routing) are asserted as holding "identically on Windows." That claim is only true if every macOS-specific mechanism has a Windows mapping that preserves the *same guarantee*, not just the same surface behavior. This doc is where that mapping is checked, gap by gap, before P4 starts — not discovered mid-port.

> **BUILT-BUT-UNVERIFIED-ON-WINDOWS (M9, honesty stamp).** §3's open questions below are now design-**resolved** (ADR-M9-001..006, §4) and Windows code lands behind `#[cfg(windows)]` per those ADRs — but every line of it is authored, reviewed, and `cargo test`-proven **on a Mac with no Windows toolchain**. "Resolved" in this doc means *a decision was made and reasoned through*, never *a Windows behavior was observed*. Do not read a row's status below, or a green macOS CI run, as evidence Control Tower has ever actually run on Windows — it has not. The full buildable-now-vs-owner-gated split, and the honest list of what still needs a real Windows box, an EV cert, or a real MDM console before this is real, lives in [`../06-deployment/m9-owner-gated-split.md`](../06-deployment/m9-owner-gated-split.md) (the M9 analog of `../06-deployment/m5-owner-gated-batch.md` and the Admin-mode HYPOTHESIS stamp in `../06-deployment/README.md`).

## 1. The OS-integration boundary

| # | Mechanism | macOS implementation | Windows equivalent (re-skin target) | Parity status | Invariant risk |
|---|---|---|---|---|---|
| 1 | **Crash-only watchdog** | `launchd` per-user LaunchAgent, `KeepAlive={SuccessfulExit:false}`, `RunAtLoad=false`, `ThrottleInterval` + an app-level launch-failure circuit breaker (N non-zero exits in a window → stop relaunching, surface "reinstall"). Distinguishes a clean `Quit` (exit 0, no relaunch) from a crash (non-zero exit, relaunch) — `architecture.md` §3. | **Task Scheduler** logon/on-event trigger with "restart the task if it fails" (`<RestartOnFailure>`, retry count + interval), gated on the app's own exit code so a clean Quit (exit 0) is not a "failure" and is never restarted. | **Resolved (design) — owner-gated (empirical verification)**, ADR-M9-002, §4 | **Highest invariant risk in this document.** Invariant #2 says `launchd` is crash-only and **never** `KeepAlive=true` (auto-restart-always) because that resurrects the app after an intentional Quit and crash-loops a bad build. Task Scheduler's restart-on-failure is *nominally* the same shape (retry-with-limit on non-zero exit), but it is commonly misconfigured as "always restart" and, unlike `launchd`, has no native equivalent of `ThrottleInterval` backoff — the retry interval is fixed, not exponential. **The port must not use Task Scheduler's simpler "repeat task every N minutes" trigger** (that IS the auto-restart-always anti-pattern) — only the failure-triggered restart with an explicit retry cap, wired to the SAME `updater::circuit_breaker`/`updater::heartbeat` the macOS build already uses (ADR-M9-002). Design-resolved; whether Task Scheduler's trigger actually behaves crash-only under real hangs/failures is owner-gated. |
| 2 | **Login-launch persistence** | `SMAppService.mainApp.register()` (macOS 13+, admin-free, user-visible in System Settings); MDM pushes a managed login-item payload (`com.apple.servicemanagement`) so it's force-approved and non-toggleable — `architecture.md` §3, §8.3. | **Task Scheduler logon trigger** (per-user, no admin) via `tauri-plugin-autostart`'s Windows path, or a `Run` registry key (`HKCU\...\Run`) as the simpler fallback. GPO/Intune can push a **required** scheduled task so a local admin can't disable it (parity to "force-approved, non-toggleable"). | **Designed-for** | Low — this mechanism has no crash-only coupling; it only governs launch-at-login, not resurrection. Risk is UX parity only: Windows Task Scheduler's login task is less discoverable to a user than macOS's Login Items UI, which matters for the "Bob sees background-running is off" detection (`architecture.md` §3, fixes B-H3) — the Windows probe for "is my logon task still enabled" needs its own equivalent check (`schtasks /query`), not yet designed. |
| 3 | **Managed / forced config domain** | `.mobileconfig` via `com.apple.ManagedClient.preferences` writing the `dev.enac.controltower` domain; **security-sensitive keys are read via `CFPreferencesAppValueIsForced`** and a value present only in the user domain is ignored + logged as tamper — `architecture.md` §8.3, fixes B-C5. | **Group Policy (ADMX) or Intune configuration profile** writing `HKLM\Software\Policies\ENAC\ControlTower` (the `Policies` hive path is Windows' closest analog to "forced," since GPO-managed policy keys under `HKLM\...\Policies\` are refreshed by the policy engine and a standard user cannot write to `HKLM` at all). Same key *names* as the macOS managed domain (already a stated design goal in `design-distribution.md` §6). | **Resolved (design, sec-review pending) — owner-gated (enrollment-detection verification)**, ADR-M9-003, §4 | See §3/§4 — `HKLM\...\Policies` is administratively forced (standard users can't write `HKLM`), but it is **not** cryptographically or structurally distinct from a merely-elevated local admin the way `CFPreferencesAppValueIsForced` is distinct from a plain user-domain `defaults write`: on macOS, *only* an MDM-pushed profile satisfies "forced," full stop, regardless of local admin rights. On Windows, a local admin with an unmanaged machine *can* write to `HKLM\...\Policies` directly (e.g. via `reg add` or `gpedit.msc` on Pro/Enterprise editions) and there is no OS-level distinction between "IT's MDM wrote this" and "a local admin wrote this" the way there is on macOS. This matters directly for invariant #4 ("security posture is inherited and enforced, never weakened... honored only from the forced/managed MDM domain") — the macOS guarantee is stronger than anything Windows natively offers for an unmanaged/BYOD machine. **Decision (ADR-M9-003, sec-review pending):** honor `HKLM\...\Policies` as forced ONLY when the machine is domain-joined/MDM-enrolled (`dsregcmd`/MDM API); otherwise fall back to the compiled-in trust root only, exactly as `managed::forced`'s existing `#[cfg(not(target_os = "macos"))]` stub already does. |
| 4 | **Secret store** | OS Keychain (`Security.framework`, `SecItemAdd`/`kSecClassGenericPassword`), per-user, service ID `com.enac.copilot.<integration>` — `credentials-and-boundary.md` §1.4. SSH push-credential private keys live in the Keychain-backed `ssh-agent` — §6.1. | **Windows Credential Manager** (DPAPI-backed, per-user profile encryption key). The `keyring` crate (already the abstraction layer named in `design-distribution.md` §6) targets both backends with the same call shape. SSH private keys use the platform `ssh-agent` service + Credential Manager, exactly as `credentials-and-boundary.md` §6.1 already specifies for the Windows re-skin. | **Designed-for** | Low-medium. DPAPI ties the encryption key to the Windows user profile (parity to per-user Keychain), but DPAPI-protected secrets are recoverable by anything running as that same logged-in user (no separate unlock/ACL prompt the way macOS Keychain can require), so the "same OS secure-storage guarantee" claim in `credentials-and-boundary.md` §6.5 needs a Windows-side re-verification pass before ship, not before design. |
| 5 | **Code signing + gatekeeping** | Developer ID Application cert, hardened runtime, `notarytool submit --wait`, **staple** both `.app` and `.dmg` for offline Gatekeeper — `architecture.md` §7, `design-distribution.md` §1. Vendored `copilot`/`cc` binaries are a **cross-repo signing contract**: already-signed/notarized/universal artifacts at a pinned SHA, verified (`codesign`/`spctl`) never re-signed. | **Authenticode** code-signing (EV or OV cert), `signtool sign /tr <timestamp> /td sha256 /fd sha256`; **SmartScreen** reputation (built via download volume + EV cert reputation, or purchased EV reputation bypass) is the closest analog to Gatekeeper, but it is a **reputation system**, not a binary pass/fail gate the way a stapled notarization ticket is. | **Resolved (recommendation) — owner-gated (EV cert + real-fleet verification)**, ADR-M9-004, §4 | Medium-high. Notarization+staple gives a **deterministic, offline-verifiable** trust decision at first launch. SmartScreen has **no staple equivalent** — a brand-new signed binary can still show the "Windows protected your PC" interstitial until the cert/binary accumulates reputation, and that reputation is opaque and non-deterministic (Microsoft doesn't publish the threshold). The cross-repo vendored-CLI signing contract (verify-not-resign, pinned SHA, "block release if vendored CLI < compat floor") ports directly to Authenticode verification (`signtool verify`) — that half is Designed-for. **Decision (ADR-M9-004):** the updater's pre-promote check becomes Authenticode-signature-valid + version-monotonicity (no staple to check); for air-gapped fleets, an EV cert + MDM-pushed SmartScreen allow-list (`SmartScreenForTrustedAppsEnabled`) is recommended over relying on reputation accrual. This is a mitigation, not parity — **the offline-deterministic first-launch guarantee stays structurally weaker on Windows**; that gap is named, not closed. |
| 6 | **Tray / menu-bar presence** | `NSStatusItem` via Tauri's `tray-icon` feature; Dock icon hidden (`LSUIElement`/`ActivationPolicy::Accessory`) — `design-distribution.md` §2. | **System tray / notification area** — the *same* Tauri `tray-icon` API (cross-platform by construction; this is the one row where the framework already abstracts the OS difference). | **Designed-for** | Low. Windows' notification-area icon can be auto-hidden by the user into the overflow tray ("hidden icons" chevron) in a way `NSStatusItem` cannot be dismissed — a UX parity gap (a hidden tray icon means Bob can't see status at a glance) but not an invariant risk; no security/crash-only coupling. |
| 7 | **Translocation-safe path** | The CLI is invoked by an **absolute, translocation-safe path** (`Bundle.main.bundleURL`), never a bare `copilot`, to survive macOS App Translocation (Gatekeeper quarantining a downloaded, unstapled `.app` to a randomized read-only path) and to avoid the `gh copilot` name collision — `architecture.md` header invariants, `cli-contract.md`. | **Fully-qualified install-path resolution** — resolve the vendored CLI via the MSI-installed path (`%ProgramFiles%\...` or per-user `%LocalAppData%\Programs\...`) read from the registry uninstall key or a compiled-in relative-to-executable path, never `PATH` lookup (Windows has its own hazard: DLL/EXE search-order and `PATH`-planted shadow binaries, the rough analog to the `gh copilot` collision). | **Resolved (design checklist) — owner-gated (live hijack test)**, §3/§4 | Medium. macOS App Translocation is a *specific* Gatekeeper behavior with a known fix (staple, or resolve `Bundle.main.bundleURL` post-translocation). Windows has no direct translocation equivalent, but has its own path-hardening hazards (a malicious `copilot.exe` earlier in `%PATH%`, or DLL search-order hijacking if the app loads a same-named DLL from its working directory instead of its install directory). **Decision:** resolve the vendored CLI via the MSI-recorded install path (registry uninstall key or compiled-in relative-to-exe path), never `PATH`; restrict DLL search order (`SetDefaultDllDirectories`) if any dynamic loading is ever added (today: none exists — confirm at Windows-build time); verify Authenticode signature before invoking (ADR-M9-004). Live hijack-resistance (Process Monitor / a planted decoy binary) is owner-gated. |
| 8 | **Notifications** | `UNUserNotificationCenter`, runtime permission prompt; MDM can push a **notifications configuration profile** (`com.apple.notificationsettings`) to force-enable so the safety-escalation channel (`architecture.md` §9) is never silently defeated by a denied permission — fixes A-H10, B-M7. | **Windows toast notifications** (WinRT `ToastNotificationManager` / Action Center), surfaced via Tauri's notification plugin. GPO/Intune can push Focus Assist / notification policy, but Windows' "force an app's notifications on" lever is less centralized than the single `.mobileconfig` payload macOS uses. | **Resolved (conservative default) — owner-gated (Intune/GPO capability confirmation)**, §3/§4 | Medium — this feeds directly into invariant-adjacent behavior (§9's "safety escalation is on by default for managed machines" and the notify-denied fallback to the IT channel). **Decision:** do not assume Intune/GPO can force per-app notification permission on Windows 11 the way the single macOS `.mobileconfig` payload does; treat the fallback-to-IT-channel path as the **primary** path on Windows, not a fallback, until a real Intune/GPO test proves centralized force-enable exists. The empirical capability question itself remains owner-gated. |
| 9 | **Self-update** | Tauri's signed-manifest updater (`tauri-plugin-updater`), minisign key independent of the Apple chain; watchdog verifies the staged bundle is **stapled offline** before promoting — `architecture.md` §7. | **Same Tauri updater**, MSI-aware (swaps via `msiexec` reinstall rather than an atomic `.app` bundle swap). The minisign signature check is identical cross-platform (already independent of the OS signing chain by design). | **Designed-for** | Low-medium. The updater mechanism itself is genuinely platform-neutral (this was a stated reason for choosing Tauri's updater over Sparkle in `design-distribution.md` §4 — "in-stack, cross-platform... Windows re-skin gets it free"). The residual risk is the "staple-verify before promoting" step (#5 above) — there's no staple to verify on Windows, so the watchdog's pre-promotion check needs a different verification (Authenticode signature + version monotonicity), not yet specified. |
| 10 | **Packaging / delivery** | `.dmg` for direct download; signed `.pkg` (Developer ID Installer cert) for MDM push via Jamf/Kandji/Intune-for-Mac. | **MSI** (WiX, Tauri's `wix` bundler) for Intune/SCCM push + a **winget** manifest for direct/discoverable install. Per-user MSI install (no admin) to preserve the admin-free constraint. | **Designed-for** | Low. Tauri's bundler already supports WiX/MSI output; the open item is packaging as **per-user** (matching the admin-free posture `architecture.md` §7 states as a hard constraint — "no admin, no privileged helper") since MSI defaults to per-machine (`ALLUSERS=1`) unless explicitly configured per-user. |
| 11 | **Signed uninstaller / deprovision cleanup** | A signed uninstaller runs `launchctl bootout` + `SMAppService.unregister()` + Keychain cleanup; the watchdog self-`bootout`s if its `Program` path goes missing — `architecture.md` §7, fixes B-H2. | MSI uninstall runs the WiX **custom action** to unregister the Task Scheduler task + clear the Credential Manager entries; a watchdog-equivalent self-check (does the scheduled task's target executable still exist) triggers self-unregistration. | **Resolved (design) — owner-gated (MSI uninstall + orphan test)**, ADR-M9-005, §4 | Medium. The macOS guarantee ("drag to Trash doesn't orphan a login item") depends on the watchdog polling its own `Program` path. Task Scheduler doesn't have a `launchctl bootout`-equivalent single command; the port needs to confirm a scheduled task can reliably detect "my target binary vanished" and self-delete without an admin-elevated helper (Windows Task Scheduler task deletion for a per-user task is admin-free, so this should hold, but is unverified). **Decision (ADR-M9-005):** a scheduled-task self-check mirrors the watchdog's `Program`-path poll and self-unregisters, admin-free, per-user, same reasoning as `SMAppService.unregister()` needing none. *Note: this row was already marked Open-question with no corresponding numbered question in §3 below — a pre-existing gap in this doc, not introduced by M9-S0; flagged, not silently fixed by renumbering §3.* |

**11 boundary mechanisms tracked.**

## 2. Parity status legend

- **Designed-for** — a concrete Windows mechanism is named, the abstraction (Tauri plugin, `keyring` crate, etc.) already spans both platforms, and no invariant guarantee is known to weaken in the port.
- **Open-question** — a Windows mechanism exists but does not *cleanly* map to the same guarantee the macOS mechanism provides (weaker, differently-shaped, or missing a needed property); gated P4 until resolved. *(As of M9-S0/ADR-M9-001..006, none of the 11 rows carry this status anymore — every prior Open-question row is now Resolved per below. Retained in the legend because a future gap could reintroduce it.)*
- **Resolved (design/recommendation/conservative default/design checklist) — owner-gated (…)** — a decision has been made and reasoned through (ADR-M9-00X, §4); the guarantee is believed to hold **structurally** on Windows by construction of the design. It has **not** been observed to hold on real Windows hardware — the parenthetical names exactly what a human still has to verify on a real Windows box/EV cert/MDM console before this is more than a well-reasoned plan. See the honesty stamp at the top of this doc and `../06-deployment/m9-owner-gated-split.md`.
- **Blocked** — cannot be resolved from the Windows side at all; gated on an unrelated, still-open upstream decision (used only for Q5, §3 — the macOS kiosk question, `architecture.md` §11 item 3, has to land first).
- **Not-started** — no Windows mechanism has been evaluated yet. *(None of the 11 rows above are Not-started — all have at least a candidate mechanism named.)*

## 3. Open questions — RESOLVED (M9-S0, ADR-M9-001..006)

> Status change: these six questions gated P4 *design* start. As of M9-S0 all six have been given a decision (Q1–Q4, Q6) or explicitly deferred (Q5) — see §4 for the full ADR reasoning. **"Resolved" here means design-resolved, never Windows-verified** — re-read the honesty stamp at the top of this doc before treating any of the below as more than a well-reasoned plan. Nothing below authorizes skipping Stream-Z's verification matrix or the owner-gated bring-up runbook.

1. **Crash-only watchdog parity (#1) — RESOLVED, ADR-M9-002.** Decision: failure-triggered restart only, explicit retry cap, gated on exit code, wired to the SAME `updater::circuit_breaker` + `updater::heartbeat` hang-detection the macOS build already uses — never Task Scheduler's "repeat every N minutes" trigger. **Owner-gated residual:** does this actually behave crash-only under real Task Scheduler conditions, including a real hang, on real hardware.
2. **Is there a true forced/managed-only config domain on Windows that a local admin cannot override? (#3) — RESOLVED, ADR-M9-003 (sec-review pending).** Decision: `HKLM\...\Policies` is honored as forced ONLY when the machine is domain-joined/MDM-enrolled (`dsregcmd`/MDM-enrollment API); otherwise Control Tower falls back to the compiled-in trust root only, exactly as it already does on macOS with no profile present. Same key names, never `HKCU`. **This ADR is flagged for mandatory @agent-sec sign-off before Accepted status** (per task 70's own instruction — this is the single hardest #4 mapping in the tracker). **Owner-gated residual:** enrollment-detection correctness across every Intune/GPO enrollment state, on a real domain-joined box.
3. **SmartScreen reputation vs. deterministic offline Gatekeeper (#5) — RESOLVED (recommendation), ADR-M9-004.** Decision: verify-not-resign ports directly to `signtool verify`; the updater's pre-promote check becomes Authenticode-valid + version-monotonicity (no staple exists to check); for air-gapped fleets, recommend an EV cert + MDM-pushed SmartScreen allow-list (`SmartScreenForTrustedAppsEnabled`) over relying on reputation accrual. **This is a mitigation, not achieved parity** — the offline-deterministic first-launch guarantee stays structurally weaker on Windows than notarize+staple; that gap is named, not closed. **Owner-gated residual:** does the allow-list policy actually suppress SmartScreen offline, on a real EV cert + real air-gapped fleet.
4. **Notification force-enable centralization (#8) — RESOLVED (conservative default), ADR-M9-005.** The empirical question ("can Intune/GPO force per-app notification permission on Windows 11") cannot be answered from this machine and is not guessed at. The **decision** made instead: treat the fallback-to-IT-channel path as the **primary** escalation path on Windows (not a fallback), per invariant #5's actor-competence routing, until a real Intune/GPO test proves centralized force-enable exists. **Owner-gated residual:** the capability test itself.
5. **Kiosk/shared-machine credential path on Windows — BLOCKED, not resolved (ADR-M9-006 names why).** This is genuinely downstream of the still-open macOS kiosk decision (`architecture.md` §11 item 3 — "first-class machine-credential path now, or defer"). No Windows design decision is made here; manufacturing one before the macOS decision lands would mean designing it twice, once on a guess. **Unblocks when:** the macOS kiosk decision is ratified — not gated on Windows-box access at all.
6. **Path/DLL-hijack hardening checklist (#7) — RESOLVED (design checklist), ADR-M9-005.** Decision: resolve the vendored CLI via the MSI-recorded install path (registry uninstall key or compiled-in relative-to-exe path), never bare `PATH`; restrict DLL search order if any dynamic loading is ever introduced (today none exists in this crate — confirm, don't assume, at Windows-build time); verify Authenticode signature before invoking, at the same call site translocation-safety already occupies. **Owner-gated residual:** live hijack-resistance testing (Process Monitor / a planted decoy binary in `%PATH%`) on a real Windows box.

Full ADR reasoning (Context/Decision/Consequences/Alternatives-rejected) for all six lives in §4 below and, in complete form, in the WP store (`tc wp get 53`, superseding the M9-S0 planning draft `tc wp get 52`).

## 4. Decisions — ADR-M9-001..006 (concise; full ADR text in `tc wp get 53`)

Every code seam cited below is real and checked against `src-tauri/src/` as of this writing; the `platform/` module itself does not exist yet (Stream-B's parallel work) — these ADRs describe the seams it must expose, not code this stream wrote.

- **ADR-M9-001 — Light platform-abstraction consolidation.** `src-tauri/src/platform/`: `trait`s only where a mock exists/is needed (`PlatformForcedConfig`/`PlatformLoginItem`/`PlatformWatchdogSignal`/`PlatformSecretStore`), zero-cost `cfg`-gated `pub use` aliasing elsewhere (tray glyph, CLI install-path, packaging). macOS impl is a THIN wrapper over existing, already-tested code (pure refactor) — mirrors the pattern `managed::forced::real_key_is_forced`'s `#[cfg(not(target_os = "macos"))]` stub already anticipates by name. Folds in three seam notes: **Credential Manager/DPAPI** (invariant #6) via the `keyring` crate behind `PlatformSecretStore`, DPAPI re-verification owner-gated per `credentials-and-boundary.md` §6.5's own flag; **tray light/dark** (invariant #1 — parse, never compute) — Windows has no `NSStatusItem`-style template-image auto-recolor, so `render::glyph`'s Windows sibling ships two pre-rasterized light/dark asset variants selected by an OS theme read, never by a new computed judgment, still driven only by `StatusState`/`BadgeState`; **`PlatformLoginItem`** — folds into ADR-M9-005 (packaging, not a trait boundary).
- **ADR-M9-002 — Crash-only watchdog on Task Scheduler (resolves Q1, invariant #2).** See §3 item 1.
- **ADR-M9-003 — Forced config refuse-unless-enrolled (resolves Q2, invariant #4) — @agent-sec review required, not yet Accepted.** See §3 item 2.
- **ADR-M9-004 — Authenticode vs. notarize+staple gap (resolves Q3, invariant #4/#5).** See §3 item 3.
- **ADR-M9-005 — Owner-gated vs. autonomous split (+ Q4 default, Q6 checklist, MSI never-orphan).** Buildable now (macOS-green, `cfg`-gated): the `platform/` consolidation, all 8 Windows seams, MSI/winget config (per-user, matching the admin-free constraint `architecture.md` §7 states as hard), Authenticode scripts (authored, not run), all docs. Owner-gated: full list in `../06-deployment/m9-owner-gated-split.md`. Also resolves Q4 (§3 item 4), Q6 (§3 item 6), and the **per-user MSI never-orphan** design (invariant #3): a scheduled-task self-check mirrors the watchdog's `Program`-path poll and self-unregisters admin-free, per-user — mirroring §1 row 11's pre-existing doc gap (flagged there, not silently fixed).
- **ADR-M9-006 — Scope-realism cut (+ Q5 blocked, not resolved).** Full `cfg`-gated impls now for seams C–H; stub-and-document only where correctness needs live Windows behavior (Task-Scheduler hang-timing tuning, SmartScreen reputation/air-gapped path). Q5 (kiosk DPAPI machine-scope) is explicitly **not** resolved here — blocked on the still-open macOS kiosk decision (`architecture.md` §11 item 3); see §3 item 5.

**Verification boundary (honest, restated):** DoD for this ADR bundle = macOS `cargo test` green + `fmt`/`clippy` clean + Windows code proven `#[cfg(windows)]`-gated out (source-scan) + (if available) a windows-target `cargo check`. No Windows runtime/GUI verification is possible from this machine or claimed by any ADR above.

## Summary

Windows remains a **committed re-skin** over the shared Tauri core (process model, state machine, CLI `--json` contract, escalation model, and update mechanism are already platform-neutral by construction). Of the 11 OS-integration boundary mechanisms tracked here, five were already Designed-for (tray, packaging, secret store baseline, self-update, login persistence); as of M9-S0 (ADR-M9-001..006, §4) the remaining six — crash-only watchdog, forced/managed config domain, code signing/gatekeeping, translocation-safe path, notifications, and uninstall/deprovision cleanup — are now **design-resolved**, with the forced-config decision (ADR-M9-003) additionally gated on @agent-sec sign-off before it's Accepted. **Design-resolved is not Windows-verified.** Every one of those six resolutions carries an explicit owner-gated residual (an empirical claim only a real Windows box, EV cert, or MDM console can confirm) — see the honesty stamp at the top of this doc and the full split in `../06-deployment/m9-owner-gated-split.md`. The one genuinely unresolved item, Q5 (kiosk/shared-machine DPAPI scope), is **blocked** on the still-open macOS kiosk decision (`architecture.md` §11 item 3), not owner-gated — no amount of Windows-box access unblocks it.
