> **Why this exists before any Windows code.** `CLAUDE.md`'s invariants (single process, crash-only watchdog, never-destroy, security posture inherited-never-weakened, actor-competence routing) are asserted as holding "identically on Windows." That claim is only true if every macOS-specific mechanism has a Windows mapping that preserves the *same guarantee*, not just the same surface behavior. This doc is where that mapping is checked, gap by gap, before P4 starts — not discovered mid-port.

## 1. The OS-integration boundary

| # | Mechanism | macOS implementation | Windows equivalent (re-skin target) | Parity status | Invariant risk |
|---|---|---|---|---|---|
| 1 | **Crash-only watchdog** | `launchd` per-user LaunchAgent, `KeepAlive={SuccessfulExit:false}`, `RunAtLoad=false`, `ThrottleInterval` + an app-level launch-failure circuit breaker (N non-zero exits in a window → stop relaunching, surface "reinstall"). Distinguishes a clean `Quit` (exit 0, no relaunch) from a crash (non-zero exit, relaunch) — `architecture.md` §3. | **Task Scheduler** logon/on-event trigger with "restart the task if it fails" (`<RestartOnFailure>`, retry count + interval), gated on the app's own exit code so a clean Quit (exit 0) is not a "failure" and is never restarted. | **Open-question** | **Highest invariant risk in this document.** Invariant #2 says `launchd` is crash-only and **never** `KeepAlive=true` (auto-restart-always) because that resurrects the app after an intentional Quit and crash-loops a bad build. Task Scheduler's restart-on-failure is *nominally* the same shape (retry-with-limit on non-zero exit), but it is commonly misconfigured as "always restart" and, unlike `launchd`, has no native equivalent of `ThrottleInterval` backoff — the retry interval is fixed, not exponential. **The port must not use Task Scheduler's simpler "repeat task every N minutes" trigger** (that IS the auto-restart-always anti-pattern) — only the failure-triggered restart with an explicit retry cap, wired to the app's own circuit breaker (same app-level logic as macOS, just fed a different OS signal). |
| 2 | **Login-launch persistence** | `SMAppService.mainApp.register()` (macOS 13+, admin-free, user-visible in System Settings); MDM pushes a managed login-item payload (`com.apple.servicemanagement`) so it's force-approved and non-toggleable — `architecture.md` §3, §8.3. | **Task Scheduler logon trigger** (per-user, no admin) via `tauri-plugin-autostart`'s Windows path, or a `Run` registry key (`HKCU\...\Run`) as the simpler fallback. GPO/Intune can push a **required** scheduled task so a local admin can't disable it (parity to "force-approved, non-toggleable"). | **Designed-for** | Low — this mechanism has no crash-only coupling; it only governs launch-at-login, not resurrection. Risk is UX parity only: Windows Task Scheduler's login task is less discoverable to a user than macOS's Login Items UI, which matters for the "Bob sees background-running is off" detection (`architecture.md` §3, fixes B-H3) — the Windows probe for "is my logon task still enabled" needs its own equivalent check (`schtasks /query`), not yet designed. |
| 3 | **Managed / forced config domain** | `.mobileconfig` via `com.apple.ManagedClient.preferences` writing the `dev.enac.controltower` domain; **security-sensitive keys are read via `CFPreferencesAppValueIsForced`** and a value present only in the user domain is ignored + logged as tamper — `architecture.md` §8.3, fixes B-C5. | **Group Policy (ADMX) or Intune configuration profile** writing `HKLM\Software\Policies\ENAC\ControlTower` (the `Policies` hive path is Windows' closest analog to "forced," since GPO-managed policy keys under `HKLM\...\Policies\` are refreshed by the policy engine and a standard user cannot write to `HKLM` at all). Same key *names* as the macOS managed domain (already a stated design goal in `design-distribution.md` §6). | **Open-question — the single hardest mapping in this table besides #1.** | See §3 Open Questions below — `HKLM\...\Policies` is administratively forced (standard users can't write `HKLM`), but it is **not** cryptographically or structurally distinct from a merely-elevated local admin the way `CFPreferencesAppValueIsForced` is distinct from a plain user-domain `defaults write`: on macOS, *only* an MDM-pushed profile satisfies "forced," full stop, regardless of local admin rights. On Windows, a local admin with an unmanaged machine *can* write to `HKLM\...\Policies` directly (e.g. via `reg add` or `gpedit.msc` on Pro/Enterprise editions) and there is no OS-level distinction between "IT's MDM wrote this" and "a local admin wrote this" the way there is on macOS. This matters directly for invariant #4 ("security posture is inherited and enforced, never weakened... honored only from the forced/managed MDM domain") — the macOS guarantee is stronger than anything Windows natively offers for an unmanaged/BYOD machine. |
| 4 | **Secret store** | OS Keychain (`Security.framework`, `SecItemAdd`/`kSecClassGenericPassword`), per-user, service ID `com.enac.copilot.<integration>` — `credentials-and-boundary.md` §1.4. SSH push-credential private keys live in the Keychain-backed `ssh-agent` — §6.1. | **Windows Credential Manager** (DPAPI-backed, per-user profile encryption key). The `keyring` crate (already the abstraction layer named in `design-distribution.md` §6) targets both backends with the same call shape. SSH private keys use the platform `ssh-agent` service + Credential Manager, exactly as `credentials-and-boundary.md` §6.1 already specifies for the Windows re-skin. | **Designed-for** | Low-medium. DPAPI ties the encryption key to the Windows user profile (parity to per-user Keychain), but DPAPI-protected secrets are recoverable by anything running as that same logged-in user (no separate unlock/ACL prompt the way macOS Keychain can require), so the "same OS secure-storage guarantee" claim in `credentials-and-boundary.md` §6.5 needs a Windows-side re-verification pass before ship, not before design. |
| 5 | **Code signing + gatekeeping** | Developer ID Application cert, hardened runtime, `notarytool submit --wait`, **staple** both `.app` and `.dmg` for offline Gatekeeper — `architecture.md` §7, `design-distribution.md` §1. Vendored `copilot`/`cc` binaries are a **cross-repo signing contract**: already-signed/notarized/universal artifacts at a pinned SHA, verified (`codesign`/`spctl`) never re-signed. | **Authenticode** code-signing (EV or OV cert), `signtool sign /tr <timestamp> /td sha256 /fd sha256`; **SmartScreen** reputation (built via download volume + EV cert reputation, or purchased EV reputation bypass) is the closest analog to Gatekeeper, but it is a **reputation system**, not a binary pass/fail gate the way a stapled notarization ticket is. | **Open-question** | Medium-high. Notarization+staple gives a **deterministic, offline-verifiable** trust decision at first launch. SmartScreen has **no staple equivalent** — a brand-new signed binary can still show the "Windows protected your PC" interstitial until the cert/binary accumulates reputation, and that reputation is opaque and non-deterministic (Microsoft doesn't publish the threshold). The cross-repo vendored-CLI signing contract (verify-not-resign, pinned SHA, "block release if vendored CLI < compat floor") ports directly to Authenticode verification (`signtool verify`) — that half is Designed-for. The **open half** is that there's no Windows mechanism that gives the same *hard* guarantee notarization+staple gives on an air-gapped/offline first launch (`design-distribution.md` §7's air-gapped path assumes offline Gatekeeper clears via the staple; SmartScreen's reputation check for a brand-new install can require phone-home in ways staple does not). |
| 6 | **Tray / menu-bar presence** | `NSStatusItem` via Tauri's `tray-icon` feature; Dock icon hidden (`LSUIElement`/`ActivationPolicy::Accessory`) — `design-distribution.md` §2. | **System tray / notification area** — the *same* Tauri `tray-icon` API (cross-platform by construction; this is the one row where the framework already abstracts the OS difference). | **Designed-for** | Low. Windows' notification-area icon can be auto-hidden by the user into the overflow tray ("hidden icons" chevron) in a way `NSStatusItem` cannot be dismissed — a UX parity gap (a hidden tray icon means Bob can't see status at a glance) but not an invariant risk; no security/crash-only coupling. |
| 7 | **Translocation-safe path** | The CLI is invoked by an **absolute, translocation-safe path** (`Bundle.main.bundleURL`), never a bare `copilot`, to survive macOS App Translocation (Gatekeeper quarantining a downloaded, unstapled `.app` to a randomized read-only path) and to avoid the `gh copilot` name collision — `architecture.md` header invariants, `cli-contract.md`. | **Fully-qualified install-path resolution** — resolve the vendored CLI via the MSI-installed path (`%ProgramFiles%\...` or per-user `%LocalAppData%\Programs\...`) read from the registry uninstall key or a compiled-in relative-to-executable path, never `PATH` lookup (Windows has its own hazard: DLL/EXE search-order and `PATH`-planted shadow binaries, the rough analog to the `gh copilot` collision). | **Open-question** | Medium. macOS App Translocation is a *specific* Gatekeeper behavior with a known fix (staple, or resolve `Bundle.main.bundleURL` post-translocation). Windows has no direct translocation equivalent, but has its own path-hardening hazards (a malicious `copilot.exe` earlier in `%PATH%`, or DLL search-order hijacking if the app loads a same-named DLL from its working directory instead of its install directory). <!-- TODO: enumerate the Windows-side path/DLL-hijack hardening checklist once WS-D's cross-repo signing contract is ported; not yet designed. --> |
| 8 | **Notifications** | `UNUserNotificationCenter`, runtime permission prompt; MDM can push a **notifications configuration profile** (`com.apple.notificationsettings`) to force-enable so the safety-escalation channel (`architecture.md` §9) is never silently defeated by a denied permission — fixes A-H10, B-M7. | **Windows toast notifications** (WinRT `ToastNotificationManager` / Action Center), surfaced via Tauri's notification plugin. GPO/Intune can push Focus Assist / notification policy, but Windows' "force an app's notifications on" lever is less centralized than the single `.mobileconfig` payload macOS uses. | **Open-question** | Medium — this feeds directly into invariant-adjacent behavior (§9's "safety escalation is on by default for managed machines" and the notify-denied fallback to the IT channel). <!-- TODO: confirm whether Intune/GPO can force-enable per-app notification permission on Windows 11 the way the macOS notifications profile does, or whether the fallback-to-IT-channel path becomes the *primary* path on Windows rather than a fallback. --> |
| 9 | **Self-update** | Tauri's signed-manifest updater (`tauri-plugin-updater`), minisign key independent of the Apple chain; watchdog verifies the staged bundle is **stapled offline** before promoting — `architecture.md` §7. | **Same Tauri updater**, MSI-aware (swaps via `msiexec` reinstall rather than an atomic `.app` bundle swap). The minisign signature check is identical cross-platform (already independent of the OS signing chain by design). | **Designed-for** | Low-medium. The updater mechanism itself is genuinely platform-neutral (this was a stated reason for choosing Tauri's updater over Sparkle in `design-distribution.md` §4 — "in-stack, cross-platform... Windows re-skin gets it free"). The residual risk is the "staple-verify before promoting" step (#5 above) — there's no staple to verify on Windows, so the watchdog's pre-promotion check needs a different verification (Authenticode signature + version monotonicity), not yet specified. |
| 10 | **Packaging / delivery** | `.dmg` for direct download; signed `.pkg` (Developer ID Installer cert) for MDM push via Jamf/Kandji/Intune-for-Mac. | **MSI** (WiX, Tauri's `wix` bundler) for Intune/SCCM push + a **winget** manifest for direct/discoverable install. Per-user MSI install (no admin) to preserve the admin-free constraint. | **Designed-for** | Low. Tauri's bundler already supports WiX/MSI output; the open item is packaging as **per-user** (matching the admin-free posture `architecture.md` §7 states as a hard constraint — "no admin, no privileged helper") since MSI defaults to per-machine (`ALLUSERS=1`) unless explicitly configured per-user. |
| 11 | **Signed uninstaller / deprovision cleanup** | A signed uninstaller runs `launchctl bootout` + `SMAppService.unregister()` + Keychain cleanup; the watchdog self-`bootout`s if its `Program` path goes missing — `architecture.md` §7, fixes B-H2. | MSI uninstall runs the WiX **custom action** to unregister the Task Scheduler task + clear the Credential Manager entries; a watchdog-equivalent self-check (does the scheduled task's target executable still exist) triggers self-unregistration. | **Open-question** | Medium. The macOS guarantee ("drag to Trash doesn't orphan a login item") depends on the watchdog polling its own `Program` path. Task Scheduler doesn't have a `launchctl bootout`-equivalent single command; the port needs to confirm a scheduled task can reliably detect "my target binary vanished" and self-delete without an admin-elevated helper (Windows Task Scheduler task deletion for a per-user task is admin-free, so this should hold, but is unverified). |

**11 boundary mechanisms tracked.**

## 2. Parity status legend

- **Designed-for** — a concrete Windows mechanism is named, the abstraction (Tauri plugin, `keyring` crate, etc.) already spans both platforms, and no invariant guarantee is known to weaken in the port.
- **Open-question** — a Windows mechanism exists but does not *cleanly* map to the same guarantee the macOS mechanism provides (weaker, differently-shaped, or missing a needed property); gates P4 until resolved.
- **Not-started** — no Windows mechanism has been evaluated yet. *(None of the 11 rows above are Not-started — all have at least a candidate mechanism named; genuinely unresolved sub-questions are flagged inline or in §3.)*

## 3. Open questions (gate P4)

1. **Crash-only watchdog parity (#1).** Does Task Scheduler's failure-triggered restart, configured with a retry cap and wired to the app's own circuit breaker, actually behave crash-only (never resurrecting a clean Quit) under real-world conditions — including the case where the app hangs rather than exits non-zero (a hang produces no "failure" exit code at all, and needs its own liveness-heartbeat detection separate from Task Scheduler's own trigger, mirroring the self-update watchdog's heartbeat file idea from `architecture.md` §3)? <!-- TODO: no Windows hang-detection design exists yet. -->
2. **Is there a true forced/managed-only config domain on Windows that a local admin cannot override?** This is the single question that most directly threatens invariant #4 on an unmanaged or BYOD Windows machine. `HKLM\...\Policies\` is the closest analog and is sufficient for **fleet-managed** machines (GPO/Intune-pushed, local admin rights removed from the end user per standard enterprise policy) — but on a machine where the logged-in user *is* a local admin, nothing stops them from writing that same registry path directly, unlike macOS where only an actual MDM enrollment can write the managed preferences domain regardless of local admin status. **Recommendation to evaluate, not yet decided:** whether Control Tower should refuse to treat `HKLM\...\Policies` values as "forced" at all on a machine that isn't domain-joined/MDM-enrolled (detectable via `dsregcmd`/MDM-enrollment APIs), falling back to a stricter default (compiled-in trust root only) exactly as it already does today when no managed profile is present on macOS.
3. **SmartScreen reputation vs. deterministic offline Gatekeeper (#5).** Is there a Windows-native mechanism that gives the same *offline, deterministic* first-launch trust decision that a stapled notarization ticket gives, for the air-gapped fleet scenario in `design-distribution.md` §7? Candidate: EV cert + an internally-distributed (MDM-pushed) SmartScreen allow-list policy (`SmartScreenForTrustedAppsEnabled` / Attachment Manager zone-identifier stripping via GPO) rather than relying on reputation accrual. <!-- TODO: not yet validated against a real air-gapped Windows fleet. -->
4. **Notification force-enable centralization (#8).** Confirm whether Intune/GPO can force per-app notification permission the way the macOS notifications profile does, and whether that changes the Bob-agency escalation model's assumption (`architecture.md` §9) that the notify-tier is reliably live on managed machines.
5. **Kiosk/shared-machine credential path on Windows.** `credentials-and-boundary.md` §1.5's machine-credential exception for unattended kiosks is designed against macOS's system keychain; the DPAPI machine-scope equivalent (vs. per-user scope) needs its own evaluation — this is downstream of the still-open macOS kiosk decision (`architecture.md` §11 item 3) and should not be designed twice.
6. **Path/DLL-hijack hardening checklist (#7).** <!-- TODO --> No enumerated Windows equivalent yet exists for the translocation-safe-path guardrail; needs its own pass alongside WS-D's cross-repo signing contract port.

## Summary

Windows remains a **committed re-skin** over the shared Tauri core (process model, state machine, CLI `--json` contract, escalation model, and update mechanism are already platform-neutral by construction). Of the 11 OS-integration boundary mechanisms tracked here, most have a named Windows candidate mechanism (tray, packaging, secret store, self-update, login persistence are Designed-for); the crash-only watchdog and the forced/managed config domain are the two mechanisms where the Windows analog is **structurally weaker or ambiguous** relative to the macOS guarantee, and both bear directly on `CLAUDE.md` invariants #2 and #4. Neither should be considered resolved by naming a plausible-sounding Windows API — each needs its own validation pass before P4 implementation starts, per the open questions in §3.
