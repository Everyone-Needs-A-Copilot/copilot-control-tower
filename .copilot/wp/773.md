CONTEXT
Security WP-772 proves that a repo-local compiled launcher, adjacent manifest, ad-hoc signature, local HEAD, and canonical-looking origin are circular: a modified checkout can rebuild and commit all of them, then self-authorize. The public repository and every byte reachable from it must therefore begin untrusted and hold zero release authority.

DECISION: EXTERNALLY INSTALLED PUBLISHER ANCHOR
Provision a separately Developer-ID-signed, Apple-notarized and stapled macOS app bundle at the canonical protected path:
  /Applications/Copilot Control Tower Publisher Bootstrap.app
Executable:
  Contents/MacOS/ct-publisher-bootstrap
Bundle identifier:
  com.everyoneneedsacopilot.controltower.publisher-bootstrap
Expected Team ID:
  3SYGVX2HB8
The bundle and every ancestor/component must be root:wheel, non-symlink, and not group/world writable; executable must be a regular non-symlink 0755-style file. Verification requires `codesign --verify --deep --strict`, exact TeamIdentifier, exact identifier/designated requirement, `spctl --assess --type execute`, and `stapler validate` on the app bundle. The anchor never trusts a path/config/manifest supplied by a repo checkout.

TRUST FLOW
1. Public repo entry `scripts/package-user-release` becomes an inert, source-visible adapter. It contains no Git, credential, signing, notary, build, or release logic. It accepts public non-secret intent only and `execve`s the fixed anchor executable with a closed argument set.
2. The installed anchor embeds the exact canonical HTTPS endpoint and expected Team ID/bundle identity. It rejects release/Git/shell authority in the initial environment; creates its own 0700 workspace/empty HOME; resolves and fetches only the operator-supplied exact public ref with config-null HTTPS-only Git; uses a bare object store and blob materialization with no checkout/.git; rejects symlinks/gitlinks/unsafe paths; verifies complete commit/tree.
3. Only code materialized from that immutable public tree may become the inner release program. The anchor does not execute a repo-local launcher or program. It streams or invokes the verified materialized program under a sanitized environment only after source verification.
4. Release authority is loaded by the independently trusted installed anchor after immutable source verification, never by repo code before that point. The anchor supplies only the minimum closed authority set to the verified inner program.
5. Repo-local launcher/source may contain source for a future anchor update, but cannot install, replace, invoke as trusted, or make it authoritative. Anchor update is a separate operation performed by the currently installed trusted anchor: fetch exact operator-approved public ref; build candidate anchor from fetched source; verify deterministic source binding; sign/notarize/staple; verify exact Team ID/designated requirement/Gatekeeper/ticket; record commit/tree/bundle digest; require explicit operator confirmation; atomically install through an administrator-authorized root operation with rollback to the prior verified app. Public repository bytes alone cannot trigger it.

INITIAL PROVISIONING CEREMONY
Because no anchor exists yet, initial provisioning is an explicit one-time owner/operator ceremony outside repo authority:
- create a fresh 0700 directory outside every repository;
- under env-i/config-null/HTTPS-only Git, anonymously resolve and fetch an exact reviewed public commit into a bare store;
- verify exact commit/tree and materialize blobs without `.git`;
- compile the anchor from that materialized source;
- sign the `.app` with the expected Developer ID identity/hardened runtime and exact bundle identifier;
- archive/submit to `notarytool`, wait for Accepted, staple the app, then verify codesign, exact Team ID/designated requirement, Gatekeeper, and staple;
- install to the canonical `/Applications` path as root:wheel and non-writable; verify again in place;
- record source ref/commit/tree, source-file blob, built executable SHA-256, bundle digest, signing requirement, notarization submission ID/status, installed inode/path/owner/mode, prior-state backup, and rollback command.
The ceremony receives no app-candidate or publication authority beyond the bootstrap-specific signing/notary operation. If any prerequisite, credential probe, notarization response, or protected install verification fails, stop and leave the old/absent anchor unchanged.

ROLLBACK
Initial install: if no prior anchor exists and post-install verification fails, move the failed bundle to a root-owned quarantine path and restore absence. Update: retain the previous fully verified bundle in a root-owned versioned backup until post-install verification passes; on failure atomically restore and re-verify it. Never delete the only verified anchor during an update.

REPO IMPLEMENTATION BOUNDARIES
- New anchor source is isolated from shipping app Swift and from the repo adapter.
- Existing bare-store/config-null algorithms may be ported into anchor source, but the repo-built binary is never trusted as the installed anchor.
- The public adapter may expose `--help` and forward only `--source-ref`, `--output-dir`, and a source-verification mode to the fixed installed anchor. It must reject all inner/private flags.
- Remove local-HEAD/adjacent-manifest/codesign self-authentication as a trust decision. Those may remain build-integrity tests only, never authority.
- App release program remains credential-free until invoked by the installed anchor with independently verified source identity.
- Actions remain disabled. No Control Tower app candidate, release, or publication occurs in this task phase.

FITNESS FUNCTIONS / ATTACKS
- Locally modify anchor Swift, rebuild/ad-hoc sign, regenerate manifest, commit with canonical origin: repo adapter and rebuilt binary cannot reach network, authority, installed-anchor IPC, or release side effects.
- Copy, symlink, hardlink, rename, chmod 0777, replace ancestors, or fake bundle around the installed executable: rejected before remote/authority.
- Repo script directly executes private inner flags or supplies a launcher path/env marker: rejected.
- Wrong Team ID, identifier, designated requirement, ad-hoc/copied signature, unstapled/not-assessed app: rejected.
- Mutable Git config, helper, include, hooks, proxy, redirect, protocol, alternates/object DB, shell startup: inert.
- Wrong/moved/ambiguous ref, tree mismatch, blob/path/mode mismatch, symlink/gitlink, dirty materialization: rejected.
- Positive: exact installed anchor verifies exact public immutable source without Git metadata and without pre-trust authority.
- Timeout every malicious subprocess; outputs remain value-suppressed.

REJECTED ALTERNATIVES
- Repo-local HEAD/origin/manifest/ad-hoc signature: circular, proven exploitable by WP-772.
- Pinning one repo-launcher hash in another repo file: same circular authority.
- Keychain secret/hash read by repo launcher: grants mutable pre-trust code secret access and creates an unsafe update/rotation path.
- Interpreted Swift/Bash parent or environment marker: forgeable/replayable and exposes startup/interpreter authority.
- Relying only on Team ID for arbitrary repo-built bootstrap: lets any same-team signed code become release bootstrap; exact identifier/designated requirement, protected install path, and current-anchor-controlled updates are required.
- Making the app release workflow itself the anchor: conflates source verification, app candidate authority, and publication; violates the distinct-gate doctrine.

4. Store notarization/install/provenance evidence without secret values.
