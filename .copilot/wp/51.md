## 3. Adversarial matrix — every named scenario, actually run

- **Opted-out ⇒ zero telemetry emitted, proven against a transport that
  panics if ever called** —
  `emitter_is_a_no_op_when_disabled_zero_transport_calls`,
  `real_emit_entry_point_is_disabled_by_default`, and
  `opted_out_doctor_poll_reaches_no_transport_call` (this last one drives a
  verdict that GENUINELY changed status AND carries a revoked-auth safety
  signal through `TelemetryState::emit_for_doctor_verdict`, still zero
  calls) — all pass, all using `PanicIfCalledTransport`, the strongest
  available proof of "never attempted," not merely "zero successful calls."
- **A `FleetEvent` cannot represent a personal name** — traced by hand: every
  field is a bare enum, a number/bool, or one of 3 single-purpose newtypes
  (`SchemaVersion`/`MachineId`/`OccurredAt`), each constructible only via a
  narrow, non-free-text constructor (a hash, a fixed version tag, a
  fixed-format timestamp) — confirmed by reading the actual struct/impl
  blocks, not just the doc's claim. `fleet_event_json_has_no_slot_for_a_
  fabricated_personal_value` independently confirms none of
  `detail/name/path/item/layer/identity/org/title/message/repo/url/text`
  exist as keys.
- **The fleet dashboard renders per-host worst-wins with NO score** —
  confirmed both structurally (§2 above) and live in the headless sweep
  (§6): `mixed-worst-wins.json`'s 5 hosts render 5 genuinely distinct
  statuses/badges (healthy/needs-attention/signed-out/offline/
  waiting-for-network), never blended into one number.
- **Multisig k-1/same-root/wrong-key/downgrade all refused** — all four
  scenarios pass via `updater::verify`'s own adversarial tests AND the
  crate-level `fitness_m7_two_of_n_signing.rs` re-proving them through the
  PUBLIC `verify_update_multisig` entrypoint: `k_minus_one_valid_
  signatures_are_refused`, `two_valid_signatures_from_the_same_root_do_not_
  count_twice`, `a_signature_from_a_key_outside_the_compiled_in_set_never_
  counts`, `a_downgrade_is_refused_even_with_k_valid_distinct_signatures`.
  **Real-world finding (already honestly documented, not a new gap):** the
  live self-update path (`updater::check.rs`) calls `verify::verify_update`
  (M4's single-root path) — `verify_update_multisig`/`multisig::trust_
  roots()` have **no production call site anywhere in the crate** (grepped
  outside `#[cfg(test)]`), confirmed independently by a `strings` scan of
  the release binary finding none of the 3 compiled-in dev root literals
  (dead-code-eliminated, since nothing calls them in the live binary).
  `docs/05-security/signing-custody.md` itself states this plainly ("The
  verifier is real; the custody is not... the live self-update path still
  calls the single-key `verify_update`") — this is a deliberate,
  documented deferral (G-M7-4: real keys + custodian assignment + the
  cutover decision), not a silently-hidden gap. Confirmed honest, not newly
  flagged.
- **The seed generator refuses a secret-bearing seed** —
  `generate_refuses_a_secret_shaped_org_value`,
  `..._foundation_mirror`, `..._policy_signer`, `..._telemetry_endpoint`,
  `..._department_lead` all pass, reusing M5's `looks_like_a_secret` scan
  (not a second, drifting copy).
- **Preflight fail-closes an unknown check to non-Pass, never fabricated
  green** — `an_uncheckable_item_is_unknown_never_a_fabricated_pass` (4 of 5
  externally-supplied facts resolve `Unknown` when absent, never `Pass`) and
  `a_seed_that_is_not_valid_yaml_is_red_on_parse_and_unknown_downstream`
  (every downstream check honestly `Unknown` when the seed doesn't even
  parse, never skipped or fabricated) both pass.
- **The two new telemetry managed keys can't be smuggled into
  `copilot.layers.yml`** —
  `ff_m7_optin_telemetry_keys_are_in_the_settings_guard_deny_list` (top-level
  AND per-layer, both refused with `GuardErrorKind::DisallowedField`) passes;
  independently confirmed `telemetryenabled`/`telemetryendpoint` present in

**D1 (informational, not blocking) — FF-M7-NO-CLOSED-COMPONENT has no
dedicated fitness test file**, unlike its 4 siblings. The task's own file
list names 5 fitness functions but the repo ships tests for only 4
(`fitness_m7_telemetry_schema_content_free.rs`,

are structurally guarded. Low-medium priority: a future session should add a
`fitness_m7_no_closed_component.rs` source/dependency scan mirroring this
crate's established pattern.

narrower than its name implies.** `fleet_view_json_has_no_slot_for_a_
fabricated_score`'s exact-key-match forbidden list
(`score`/`health`/`rating`/`percent`/`grade`) did not catch a `health_score`
field addition during mutation testing — only the sibling closed-field-set
test did. The overall FF-M7-NOSCORE guard holds (two tests, one caught it),
but a future edit to that forbidden-key list should consider substring
matching or explicitly naming `health_score`/`fleet_score`/`overall_score`
as compound-word variants, not just the bare words.

**D3 (informational, housekeeping, not blocking) — all of M7 (S1–S9) is
uncommitted**, same pattern M3–M6 QA's own housekeeping notes already
flagged for their milestones. `git status` shows every M7 file as untracked.

## Verdict

**M7 = ACCEPT.**

Every SOUL/CLAUDE non-negotiable this milestone touches is structurally
enforced and, for 4 of 5 named fitness functions, LIVE mutation-tested (not
merely asserted): a fabricated fleet-health-score field is caught
(FF-M7-NOSCORE); a payload-bearing `FleetEventKind` variant is caught, and
this one compiled cleanly through to a real test failure rather than
cascading into unrelated compile errors the way the M6 `ItSignal` precedent

structurally guard. The dashboard's no-score claim, the telemetry opt-in
gate's zero-emission-on-disable claim, the seed generator's secret-refusal,
and preflight's fail-closed-to-Unknown discipline were all independently
confirmed live (unit tests + a 5-fixture headless CDP sweep with 0 console

release binary shows no leaked dev-seam env markers, test secrets, or mock
