# Semantic Inheritance Readiness Audit — six daily-use cases

Audited 2026-08-01 by @agent-ta, read-only, traced to consumers in real code and real content on this machine. Every verdict below carries file:line or live-state evidence. Nothing was mutated.

## Headline

The 16/16 setup completes the **plumbing**, not the **content**. Layer resolution, materialization, never-destroy guarding, precedence, and pruning are all real, tested, working code. What is missing is that **every shared layer above foundation is empty**: `claude-copilot-internal` (org) ships `copilot.layer.yml` + `ecosystem.yml` and nothing else; `codex-copilot-internal` ships one file; all four `*-accounting` department repos are empty or seed-only; and there is no `product: knowledge` layer in the manifest at all. So on the day 16/16 goes green, a session gets exactly what it gets today: foundation content plus whatever the project holds. Additionally, one P0 defect is already live and has already destroyed org content.

## P0 — live cross-tier write incident (must be handled before any further `cc update`)

`cc update` materialized the **personal** layer's `knowledge` dimension through the `~/.claude/knowledge` symlink into `/Volumes/Dev/Sites/COPILOT/knowledge-copilot-internal` — the **org** knowledge repo — and reconcile-deleted everything else under the four paths it owns. The Obsidian vault-backup cron then committed and pushed it.

Evidence chain: `~/.claude/knowledge` is a symlink to `knowledge-copilot-internal` (`ls -ld`, created 2026-07-17). `paths.claude_materialize_root = ~/.claude` (`claude-copilot/tools/cc/src/cc/core/config.py:78`) and `PRODUCT_TARGET_ALLOWLIST["claude"]["knowledge"] = "knowledge"` (`core/ecosystem/materialize.py:83`), so the write target is `~/.claude/knowledge/<item>`, which resolves through the symlink into the org working tree. The lockfile `/Users/pabs/.claude/cc/copilot.lock.json` records `claude-personal` contributing exactly 4 knowledge items: `.claude`, `docs`, `knowledge-manifest`, `skills`. Those 4 paths in the org repo have mtime `Jul 27 16:34` (the materialize run) and are **byte-identical** to `~/.copilot/mirrors/claude-personal/knowledge/` (verified by `diff -q` on all 4 files). Commit `3433854d` "vault backup: 2026-07-27 16:40:42" is `58 D, 2 A, 1 M, 1 R100 — 12,537 deletions`, and it is contained in `origin/main`.

Destroyed: all 5 org agent extensions (`.claude/extensions/{cw,do,ind,sd,uxd}.*.md` — including `cw.extension.md`, the **brand-voice** binding), `.claude/agents` (16), `.claude/commands`, `.claude/memory`, `.claude/hooks`, `.claude/skills`, 10 of 11 `docs/` files (including `docs/00-knowledge-copilot/02-consumption-contract.md`, which 6 installed agents cite by path), and `knowledge-manifest.json` v1.4.0 (222 registered skills + 5 extensions) replaced by the personal 1-entry template. Survived: `01-company` (145 files), `02-products` (122), `03-ai-enabling` (486), `04-shared-systems` (14,063), `00-best-practices` (59) — the personal layer only owned 4 top-level names, so the bulk company knowledge is intact.

Root cause is two-fold and both halves are in code. First, `guard_personal()` (`materialize.py:136-171`) protects a tree only if it is a registered `personal_root` **or currently dirty**; a clean authoring repo is unprotected. Second, `personal_roots` has no production feeder — `commands/update.py:97` declares `_personal_roots: Iterable[Any] = ()` and it is only ever passed through at line 271; nothing in the real call path populates it. So the guard ran, found the repo clean, and allowed the overwrite. Recovery is available and cheap: everything is recoverable from `3433854d^`, which is still in the repo and on the remote.

## Case 1 — company information in a project

**VERDICT: WORKS-TODAY (single-layer, not a fold), with one broken pointer.**

The mechanism is not the layer resolver at all. It is `paths.knowledge_repo` -> `cc env` -> `$CC_KNOWLEDGE_REPO` -> agents reading canonical sub-paths by prose instruction. `cc env` emits `CC_KNOWLEDGE_REPO=/Volumes/Dev/Sites/COPILOT/knowledge-copilot-internal`, and the content is there: `01-company/03-services/` has 8 service files, `01-company/` has 145 files across brand/voice/services/gtm/methodologies. The contract that names those paths is `knowledge-copilot/docs/00-knowledge-copilot/02-consumption-contract.md`, and agents follow it by instruction (e.g. installed `~/.claude/agents/cw.md:25`, and my own `ta` definition). This works today and will keep working.

Two caveats. `knowledge` is explicitly **excluded from materialization**: `commands/update.py:172` sets `externally_consumed_products = {"knowledge", "cli"}` and line 236 filters those out of the materialize set, so knowledge is never layer-folded even if you added a `product: knowledge` entry — it would be mirrored and ignored. And the consumption contract itself is now **missing from the org repo** (destroyed by the P0), so the 6 agents that cite `docs/00-knowledge-copilot/02-consumption-contract.md` relative to `$CC_KNOWLEDGE_REPO` hit a dead path; the file still exists in the public foundation checkout.

## Case 2 — project-specific agent/skill is correctly used

**VERDICT: WORKS-TODAY.**

This is delivered by Claude Code's own project-over-machine precedence plus `cc skill`'s explicit ordering, not by the layer system. `cc skill`'s `_load_all_skills` (`commands/skill.py:24-50`) scans `<repo>/.claude/skills` as `project` then `~/.claude/skills` as `machine`, "resolution order: project -> machine". Live: `cc skill list --json` in this repo returns 71 skills, 33 `project` + 38 `machine`, and project-only skills (`admin-bootstrap`, `codex-copilot`) resolve correctly. Projects are never a materialize target — `materialize_roots` is `{claude: ~/.claude, codex: ~/.copilot/materialized/codex}` (`core/config.py:78-79`) — so a project's `.claude/` is its own tree and is never overwritten by layer sync. Working as intended.

## Case 3 — writing as ME vs as my company's brand

**VERDICT: CONTENT-GAP, compounded to near-MECHANISM-GAP by the P0.**

The selection mechanism was never code; it is the "Extension Resolution" section of `protocol.md` (`claude-copilot/.claude/commands/protocol.md:537-565`), which instructs an agent to read `~/.claude/knowledge/knowledge-manifest.json`, find an entry matching the agent id, and apply `override` (replace) or `extension` (merge). `/extensions` (`commands/extensions.md`) is a **status reporter only** — it counts manifests and skills, it never loads them. No Python/Swift code consumes `knowledge-manifest.json`; the only code hits are a test and two audit tools.

Brand voice existed and was bound: the pre-incident manifest had `{agent: cw, type: extension, file: .claude/extensions/cw.extension.md, description: "Authentic Provocateur voice and company tone guidelines"}`. Both the entry and the file were destroyed by the P0. The underlying brand content survives (`01-company/02-voice/` 10 files, `01-company/01-brand/02-tone-of-voice.md`), and `cw.md:25` still instructs reading it directly, so brand voice is reachable — but no longer *bound* to the agent.

Personal voice has **no content at all**. The foundation ships templates (`knowledge-copilot/templates/personal/how-i-communicate.md`, `how-i-decide.md`, `working-preferences.md`, +7) and they are **never instantiated anywhere on this machine**; the personal knowledge layer is a 4-file shell whose own manifest self-describes as `"TEMPLATE -- inert example ... matches no real framework agent id, so this has zero effect"`. Worse, even if you filled them in, agents could not see them: `paths.knowledge_repo` **is** correctly list-valued (`core/config.py:155` `LIST_VALUED_KEYS`) and resolves to `[knowledge-copilot-internal, claude-copilot-private/knowledge]`, but `commands/env.py:81` truncates the agent-facing alias to the first entry — `exports["CC_KNOWLEDGE_REPO"] = exports["CC_KNOWLEDGE_REPO"].split(",")[0].strip()`. The full ordered list survives only as `CC_PATHS_KNOWLEDGE_REPO`, which no agent references. So today, personal knowledge is structurally invisible to every agent instruction.

So: nothing today differentiates "write as me" from "write as the company". There is no writing-profile router, and the one binding that made brand voice explicit is gone.

## Case 4 — company protocol vs project protocol

**VERDICT: WORKS-AFTER-APPLY for the project half; CONTENT-GAP for the company half.**

Precedence works and is proven: `~/.claude/commands/protocol.md` and `<project>/.claude/commands/protocol.md` both exist (31,910 bytes, byte-identical today because both are foundation copies), and Claude Code prefers the project copy. A project that edits its `protocol.md` gets its own protocol immediately.

A *company* protocol cannot exist today. The `protocol` dimension is declared with `OVERRIDE` semantics (`core/ecosystem/dimensions.py:28`) and allowlisted for claude (`materialize.py:82`), but it is **empty in every layer** — no `protocol/` directory in `claude-foundation`, `claude-organization`, or `claude-personal` mirrors, and no `~/.claude/protocol` exists. The real protocol ships inside the `commands` dimension as `commands/protocol.md`. Since `claude-organization` contributes zero items (lockfile shows the layer present with no dimensions), there is no org protocol to override the foundation one. The fold that would make this work is live and correct — it just has nothing to fold.

## Case 5 — budget work uses the Accounting department's skills and agents

**VERDICT: CONTENT-GAP plus a second, independent MECHANISM-GAP.**

Three separate failures, each sufficient on its own.

**(a) No department layer is joined, and the catalog cannot feed one.** `copilot.layers.yml` declares 8 layers across products `claude` (3), `cli` (2), `codex` (3) and roles `foundation` (3), `org`/`organization` (3), `personal` (2) — **zero `role: department`**. The join path exists (`cc layers join`, `commands/layers.py`) and reuses `cc update`'s pipeline properly, but its catalog comes from `ecosystem_config.departments()` reading `~/.claude/ecosystem.yml`, which is **absent** on this machine, so the catalog is `[]`. Even when materialized, the shape mismatches: the org's `ecosystem.yml` declares `departments: [{unit: accounting, topology: separate}]`, while `commands/layers.py:264-266` requires `id` and `repo` and *silently skips* entries lacking them. And `_new_manifest_layer` (`layers.py:352`) defaults `product: "cli"`, so a join would add a single CLI-product layer, not the claude/codex/knowledge fan the department actually needs.

**(b) The department repos are empty.** Verified via `gh api`: `knowledge-copilot-accounting` and `cli-copilot-accounting` are **truly empty** (no commits, HTTP 404 on contents); `claude-copilot-accounting` and `codex-copilot-accounting` contain **only** a 127-byte `copilot.layer.yml` with `dimensions: []`. The "ready" status these report means "seeded and reachable", not "has content". This is by design of the setup path — `commands/onboard.py:415` and `:1050` write `"dimensions": []` into every seeded layer.

**(c) The finance skills exist but are invisible to the skill system.** The knowledge repo holds 279 `SKILL.md` files under `03-ai-enabling/01-skills/`, including a whole `13-business-finance/` family — `05-budget-analysis`, `06-expense-categorization`, `07-tax-planning`, `04-cash-flow-forecasting`, `02-owner-compensation`, `09-tax-calendar` — and they carry real routing frontmatter (`budget-analysis/SKILL.md`: `triggers: {files: ["**/finance/**","**/budget/**"], keywords: ["budget","spending","expenses",...]}`). **Nothing consumes `triggers`.** A repo-wide grep for `triggers` across `cc` and `copilot_cli` finds only FTS5 SQL triggers and one unused Pydantic field (`copilot_cli/services/skill/models.py:62`). And `cc skill` never scans the knowledge repo at all — only `.claude/skills` and `~/.claude/skills`. Live proof: `cc skill list --json` returns 71 skills and the only finance-adjacent name is `account-research`; zero budget/tax/expense skills are discoverable. So even with a fully populated Accounting layer, a budget task would not route to these skills, because the routing table is inert and the skill tree is off the search path.

## Case 6 — elevating a project agent/skill to org or department

**VERDICT: MECHANISM-GAP (formally deferred), with an undocumented but safe manual path.**

`cc publish` does not exist and was formally deferred by **ADR-008** (`docs/40-initiatives/02-enac-self-onboarding/decisions/ADR-008-repair-and-publish-deferred.md`, Accepted 2026-07-31, §3). Confirmed by directory listing: no `publish.py`, no `promote`, no `elevate` in `cc/commands/`. No other mechanism substitutes — `admin-bootstrap` and `cc onboard` create repos and seed `dimensions: []`; neither moves content upward.

The important discovery is that **the interim manual path is trivially safe and requires no code**, because `copilot.layer.yml` is inert: a full grep shows **nothing in the resolution path ever reads it** — only `onboard.py` writes it. Contribution is purely directory-based via `discover_contributions()` (`core/ecosystem/discovery.py:82-96`), which scans `<layer_root>/<dimension>/` and hashes what it finds. So elevation today is: copy the item from the project into a clone of `claude-copilot-internal` under `agents/`, `skills/`, or `commands/`, commit, push, `cc update`. The nearest-tier-wins fold (`resolver.py` + `dimensions.py:25-27` `OVERRIDE`) then makes the org copy win over foundation for every machine, and `shadowed[]` reports the foundation copy it displaced. This path is **safe** (it is an ordinary human `git push` to a shared remote, exactly the "separate, human-invoked, distinctly-credentialed action" invariant #6 requires) but it is **not documented anywhere** — and it must be documented with the P0's lesson attached, because the failure mode is precisely a personal tree and a shared tree being confused.

## Adjacent use cases

**Project aftercare / integration (`cc workspace`)** — WORKS-TODAY. Note the verb is `cc workspace`, not `workspaces` (the plural errors out). `cc workspace --all --json` returns schema 1.1 and 53 projects with per-component classification: claude 22 ready / 21 guided-integration / 9 could-not-verify / 1 safe-finish; codex 23 ready / 14 safe-finish / 13 could-not-verify / 3 guided-integration. The subcommand surface (`verify`, `finish`, `configure`, `plan`, `hold`, `revert`, `approve-root`) is real and read-only-by-default. `project_integration.py` is fail-closed inspection: it never follows an external symlink, never returns file contents, never trusts self-report. This is the healthiest part of the system. Worth noting this repo has **no** `copilot.lock.json`, which is why control-tower itself classifies as guided-integration.

**Update fan-out** — WORKS-TODAY, but it is a *framework version bump*, not layer-content delivery. `cc update --fanout` sweeps discovered projects and re-materializes stale components against each project's `copilot.lock.json` (e.g. `knowledge-copilot-internal/copilot.lock.json` records `codex 0.6.1`). It reuses `guard_personal()` unweakened for the `held` preview (`core/ecosystem/projects.py:405-413`). It does not push org/department layer content into projects — nothing does; layers land in `~/.claude` and reach projects only via Claude Code's machine-level precedence.

**Freshness** — DEGRADED. `cc freshness --json` returns `{current_lock_sha: null, latest_lock_sha: null, stale: null, offline: false}`. This is the module behaving honestly (its docstring explicitly amends the schema so `null` means "couldn't check" rather than fabricating "fresh"), but it means the cheap-poll signal Control Tower renders is permanently "unknown" until a tier publishes a `refs/copilot/lock` pointer (`CC_LAYERS_LOCK_REF=refs/copilot/lock`). Nothing publishes one today.

**Doctor** — WORKS, score 65, status `update-available`. All path checks pass. All 8 sync checkers warn with the same shape: `local none behind remote <sha>`. "local none" is suspicious — the lockfile *does* carry `_meta.source_sha` per layer — so doctor appears to be reading a different local pin than `update` writes. Worth a targeted look; it makes every layer permanently appear behind.

**`cc resolve` is blind** — a real inconsistency worth fixing cheaply. `cc resolve --json` returns **0 resolved items** even though materialize demonstrably works. Cause: `discover_contributions()` requires a static `source.path` in the manifest (`discovery.py:70-72`), and the live manifest has none; `update.py` synthesizes `source["path"]` from the mirror at runtime (`commands/update.py:193-221`) but `resolve` does not. So the operator's only "explain the fold" tool shows nothing.

## Control Tower's boundary — confirmed correct

The app is a renderer and is **not** the cause of any gap here. `native/cli-client.swift` invokes only `doctor`, `freshness`, `update` (`--fanout`, `--project`, `--products`, `--components`), `layers join`, `onboard`, and `workspace` subcommands, all with `--json` behind a `SchemaGate`. It performs no resolution, no fold, no routing. Every gap above assigns to the CLI (`claude-copilot/tools/cc`), the knowledge repo content, or the empty layer repos — never to the app. Invariant #1 is holding.

## Prioritized plan

Complexity is Low/Medium/High; no time estimates. "Owner" means a human decision or credentialed action; "code" means a session on this machine can do it.

**Phase 0 — Stop the bleeding (do before any further `cc update`). Blocking; nothing else should run first.**

P0.1 (owner decision, then code; Low) — Restore the org knowledge repo from `3433854d^`: the 5 agent extensions, `knowledge-manifest.json` v1.4.0, `docs/00-knowledge-copilot/`, and the `.claude/` tree. This is a revert of a known-bad commit, fully recoverable, but it touches a pushed shared repo so the owner should approve the method (revert commit vs restore-paths commit).

P0.2 (code; Low) — Break the symlink vector. `~/.claude/knowledge` must not point into a real authoring repo while it is also a materialize target. Either repoint knowledge materialization away from it or stop symlinking `~/.claude/knowledge` to the org checkout. Independent of P0.3, and the fastest single action that prevents recurrence.

P0.3 (code, in `claude-copilot/tools/cc`; Medium) — Close the guard hole properly. Two changes: (a) populate `personal_roots` in production — `commands/update.py:97` currently defaults to `()` with no feeder, and every configured `paths.knowledge_repo` entry plus every `projects.roots` project is a known human-owned tree that belongs in that set; (b) make `guard_personal()` refuse to write through a **symlink** whose target escapes the materialize root, and treat a clean-but-tracked git repo that is not a layer mirror as protected. Unit tests required (this is the never-destroy invariant; it needs a regression test that reproduces the exact symlink-into-authoring-repo shape). This is the one item that is genuinely a code defect rather than missing content.

**Phase 1 — Make the org layer real (unblocks cases 3, 4, 5; depends on Phase 0 only).**

P1.1 (owner + code; Low, high leverage) — Push content directories into `claude-copilot-internal`. Because `copilot.layer.yml` is inert and discovery is directory-based, this needs **zero code**: `agents/`, `skills/`, `commands/` at the repo root are picked up on the next `cc update`. Start with the restored agent extensions and any company-specific agent overrides. This single action converts "org layer exists" into "org layer works" and is the highest value-per-effort item in the audit.

P1.2 (owner; Low) — Author the company protocol as `commands/protocol.md` in `claude-copilot-internal`. `OVERRIDE` semantics then make it beat the foundation copy machine-wide, while any project keeping its own `.claude/commands/protocol.md` still wins locally — which is exactly case 4's requested behavior, with no code change.

P1.3 (code; Low) — Materialize `ecosystem.yml` to `~/.claude/ecosystem.yml` and reconcile its shape. `ecosystem_config.py` expects `{id, name, repo}`; the org file has `{unit, topology}`. Fix the producer or the reader (the reader's fail-open skip at `layers.py:266` currently hides the mismatch silently — at minimum it should warn). Prerequisite for P2.1.

**Phase 2 — Department routing (case 5; depends on P1.3).**

P2.1 (owner + code; Medium) — Populate the Accounting layer and join it. Requires: the department catalog to actually list `{id, repo}` (P1.3); `_new_manifest_layer`'s `product` default (`layers.py:352`) to stop hardcoding `"cli"` so a department can join per-product; and real content pushed to `claude-copilot-accounting` (agents/skills for budget work). Note `knowledge-copilot-accounting` cannot participate in the fold at all while `knowledge` is in `externally_consumed_products` — decide whether department knowledge rides `paths.knowledge_repo` as a third list entry instead.

P2.2 (code; Medium) — Make the 279 knowledge skills discoverable. Today `cc skill` cannot see them and `triggers:` is dead metadata. Minimal mechanism, consistent with parse-never-compute: extend `cc skill`'s discovery to include the configured `paths.knowledge_repo` entries' skill trees, and have `cc skill` surface `triggers` in its `--json` so the *agent* does the routing from CLI-provided data rather than the CLI inventing semantics. This is the single change that makes case 5 possible at all — without it, a populated Accounting layer still would not be reached for a budget task.

**Phase 3 — Personal voice (case 3; depends on P0.2, independent of Phase 2).**

P3.1 (code; Low) — Stop truncating `CC_KNOWLEDGE_REPO`. `commands/env.py:81` reduces the ordered list to its first element, which makes the personal knowledge layer invisible to every agent. Either emit the list and teach the consumption contract to search in order, or add a distinct `CC_PERSONAL_KNOWLEDGE_REPO`. Low complexity, but it gates everything personal.

P3.2 (owner; Low) — Instantiate `templates/personal/how-i-communicate.md` (and siblings) into `claude-copilot-private/knowledge/`. This is content only the owner can write.

P3.3 (owner + code; Low) — Restore the `cw` binding and add its personal counterpart, so "write as me" vs "write as the company" is an explicit, declared choice rather than an inference. Update the consumption contract to name both paths.

**Phase 4 — Elevation (case 6) — genuinely a next initiative.**

P4.1 (code, documentation only; Low — do this now) — Document the interim manual elevation path: copy into a clone of the tier repo under the dimension directory, commit, push, `cc update`. It is safe and it works today. It must carry an explicit warning derived from the P0: never elevate by pointing a materialize target at an authoring checkout. This is closable immediately and removes the practical blocker even though the verb is deferred.

P4.2 (owner; High) — `cc publish` remains deferred per ADR-008 §3, and its stated blocker is real: `inheritance-and-publish.md:188` names the credentials-carrier (F16) as "the single largest dependency" that "gates whether any of §3 can ship". Do not re-scope it into this initiative. Superseding ADR-008 requires a new ADR.

**Phase 5 — Observability repairs (low risk, independent, can run anytime after Phase 0).**

P5.1 (code; Low) — Fix `cc resolve` blindness by having it synthesize mirror source paths the way `update.py:193-221` already does. Restores the only "explain the fold" tool.
P5.2 (code; Low) — Investigate doctor's `local none` on all 8 sync checkers against the lockfile's `_meta.source_sha`.
P5.3 (owner + code; Medium) — Decide whether to publish `refs/copilot/lock` so `cc freshness` stops returning nulls; until then Control Tower's freshness tile is permanently "unknown" by honest design.
