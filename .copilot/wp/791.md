Critical finding — canonical executable remains replaceable before verification (CWE-426/CWE-829; high likelihood, critical impact)
ARTIFACT: file-check|canonical-parent "/Applications is root:admin mode 0775; logged-in publisher uid 501 is a member of admin; test -w /Applications returned yes"
The adapter directly execve's:
  /Applications/Copilot Control Tower Publisher Bootstrap.app/Contents/MacOS/ct-publisher-bootstrap
The installed binary then verifies its own path, root ownership/modes, code signature, requirement, Gatekeeper, staple, and approval. That ordering is circular when the app bundle's parent is writable by the attacker. An admin-group process can rename/remove the entire root-owned bundle and place an arbitrary executable at the same canonical pathname. The replacement is the first code executed and can omit every self-check; it need not preserve root ownership, Team ID, bundle ID, notarization, or approval validation. Root ownership of the current child objects prevents in-place edits but does not prevent directory-entry replacement by a writer to /Applications. On the next adapter invocation, no independent code exists ahead of the replacement.

This violates WP-773's explicit requirement that every ancestor/component be non-group/world-writable and reopens WP-772's mutable pre-trust code path. The production anchor checks only /Applications owner/type, not its 0022 mode. The verifier likewise checks owner/non-symlink but not parent mode. Because /Applications mode 0775 is normal for this Mac, changing the system-wide directory mode is not an appropriate fix.

Exploit consequence
A repo/local process running without an administrator prompt can replace the canonical entry bundle, wait for the operator to invoke scripts/package-user-release, then receive the operator's existing environment and run arbitrary publisher-side actions. Even if outer authority variables are absent, malicious replacement code can read the user-owned authority file/keychain contexts directly or alter release behavior. All later checks are attacker-selected because they live inside the replacement.

Required mitigation
1. Move the executable entry trust root out of /Applications into a dedicated root-owned, root-only-writable directory under ancestors the publisher account cannot replace (for example a dedicated root:wheel 0755 subtree under /Library/Application Support, with the exact design reviewed).
2. Point the repo adapter only at that protected executable. It must be the first executed code.
3. In the protected entry code and external verifier, lstat every path component from the trusted system ancestor to executable and approval: regular/directory as appropriate, no symlink, uid 0, and mode & 0022 == 0. Add a regression that detects a writable ancestor and proves a same-path replacement cannot become first code.
4. Preserve exact Developer ID Team ID, identifier/designated requirement, strict codesign, Gatekeeper, staple, and root approval checks after relocation. Those controls are valid defense in depth but cannot authenticate code that is already executing.
5. Re-provision through the authorized administrator ceremony, verify in place, then rerun independent QA and security. Do not build a Control Tower candidate before approval.

Additional finding — provenance is evidence, not a trust root (low runtime impact; medium audit-evidence impact)
The provenance ledger is user-owned mode 0600. It cannot safely prove historical installation state against the same logged-in attacker because that user can rewrite ref/tree/hash/notary/rollback claims. Runtime trust does not consume it; the root-owned approval and live Apple/filesystem checks remain the operative controls. Treat provenance as a convenience report unless it is moved to root-owned protected storage or cryptographically authenticated and independently verified.
