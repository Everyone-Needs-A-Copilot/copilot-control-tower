# Self-service store provisioning — service design specification

**Doc:** `docs/05-security/self-service-store-provisioning.md` (DESIGN FOR REVIEW) · **Commit:** 1e4b95f on `app-build`, not pushed · **Next:** security threat-model pass extends §7.

## Problem reframe

**Brief:** "Use GitHub as the authentication method to connect to my Infisical setup and automatically create that username, Client ID, and Client Secret."

**Reframed JTBD:** *When my department's tools need a key I don't have and shouldn't have, I want the work to just run, so I can close the month without asking a colleague to DM me something I know I'm not supposed to have.*

**Assumption challenged:** the brief describes federation (Infisical trusts GitHub). Research shows GitHub is an OAuth 2.0 provider for user login, not an OIDC identity provider, and it exports no team-membership claim. Infisical's GitHub sign-in proves who someone is and says nothing about which teams they are on. **No configuration of GitHub plus Infisical, at any licence tier, maps "on the accounting team" to "may read /departments/accounting" without a third component in between.** The translation is unavoidable. The only real question: does the translator ISSUE ASSERTIONS or DISPENSE SECRETS?

**Second assumption challenged:** "no admin ceremony" is the user-visible goal. The operational goal is stronger — the number of acts an admin must remember for offboarding to be complete must be exactly one, and it must be an act they were already going to perform.

## Vendor capability research (verification status per claim)

Documented: Infisical Universal Auth; client secrets createable via API with `ttl`/`numUsesLimit`, plaintext returned once, individually revocable; short-lived renewable access tokens with trusted-IP restriction; **OIDC Auth for machine identities** (`oidcDiscoveryUrl`/`boundIssuer`/`boundAudiences`/`boundSubject`/`boundClaims`) — the pivot the recommendation turns on; GitHub Actions OIDC supported as an issuer; identity creation, project membership, path-scoped additional privileges; GitHub social sign-in on self-hosted via `CLIENT_ID_GITHUB_LOGIN`; built-in audit log. GitHub: org SAML SSO requires Enterprise Cloud; App installation token with Members:read reads team membership and enables team webhooks; the org's GitHub App already exists (`Ov23li2VmVUyOGXbwyDX` in live `ecosystem.yml`); the CLI already requests `write:public_key`.

Reported (confirm before budgeting): Infisical SAML/OIDC SSO = paid tier, SCIM/LDAP = Enterprise; GitHub rejects an SSH key already registered to another account. Assessed: Infisical does not sync GitHub teams into Infisical groups.

## Concepts considered — 3 framings, Three Lenses

| | A1 full federation | A2 GitHub login + reconciler | B mint | **B′ assert (selected)** |
|---|---|---|---|---|
| Desirable | High | Medium (second sign-in, or it becomes B) | High | High |
| Feasible | Low (GHEC + Infisical Enterprise + SCIM + IdP programme) | Medium (worse custody: user-management credential) | Medium | Medium |
| Viable | Low now, high at scale | Low (per-seat + worst custody) | Medium (6 permanent lifecycle ops + total-blast-radius component) | **High** |
| Closes G-12 | Yes, by directory | Yes, at reconciler latency | **No** — sweep-dependent | **Yes, by construction** |

**Selection rationale (B′):** the broker is an OIDC issuer Infisical already trusts, holding only its own signing key. It can assert claims that pre-existing admin-created per-scope identities are bound to; it cannot create a scope, widen one, or read a secret. **An identity-minting credential is transitively a secret-reading credential** — anything that can mint and grant can mint for itself — so B's broker has store-equivalent blast radius (the F16 credentials-carrier class ADR-008 names as a publish blocker). B′ bounds compromise to user impersonation for the compromise window. Nothing store-related is at rest on the laptop, so `_NEVER_FROM_STORE` stops being a paradox, machine loss and offboarding collapse to one GitHub act, and revocation needs no revocation because every access requires a fresh membership check.

**Rejection rationale:** A1/A2 rejected as prerequisites (priced dependency chain on both sides, and federation relocates rather than removes the translator) but A1 kept as a supported end state — B′ is designed to be replaceable by it with zero change on the user's machine. **B rejected as a stepping stone, not merely as a destination:** B and B′ share the hard half (GitHub App membership verification, `team_scopes`, the CLI verb, app surface, copy, failure routing) and differ only in what the broker returns. Building B first de-risks nothing and adds exactly what B′ exists to delete, then requires decommissioning it. B survives only for headless/automation actors, minted deliberately by an admin.

## Service blueprint (frontstage / backstage)

**Day zero (admin):** frontstage — paste URL, name teams, and Control Tower proves the claim before making it. Backstage — `cc store verify --json` [NEW] does a live end-to-end proof including a **negative** test (an unentitled read must fail; a positive-only test cannot distinguish correctly-scoped from everything-readable); one-time console setup creates per-scope Infisical identities with OIDC Auth bound to the broker, broker deployed with TLS beside Infisical, signing key generated on-host, GitHub App granted Members:read and subscribed to `membership`/`organization`, `team_scopes` published. Failure points: OIDC trust misconfigured so any claim validates; bound audience omitted making assertions cross-instance replayable; `team_scopes` written but not published; App installed without Members:read so everyone is silently unentitled.

**Day one (Bob):** frontstage — the GitHub device code he already does; a stage named "Getting your team's shared keys ready"; step 6 as a receipt. Backstage — CLI generates a machine keypair and registers the public key on GitHub (already-scoped `write:public_key`), signs a broker nonce, broker verifies against `<login>.keys`, resolves teams with the **App installation token** (user token proves who; App token proves entitlement), maps through `team_scopes` failing closed, returns a short-lived JWT, CLI exchanges at `/api/v1/auth/oidc-auth/login` and performs one real read to prove the chain. On disk: the keypair plus a non-secret registration record. Nothing store-derived.

**Transition designed:** step 2 → step 8 is invisible and asynchronous; it must be idempotent and resumable (closing the wizard between them must not double-register or add a duplicate SSH key). **Named as not-fixed:** step 6 asks about connections before step 8 materializes org config — a wizard-sequencing defect this design neither causes nor cures.

**Steady state:** nothing frontstage. One tunable — cache the Infisical access token within its own `accessTokenTTL` and no independent lifetime, so there is exactly one number and the admin sets it at the store via inherited config.

**Lifecycle:** provision / list-mine / re-provision / machine loss / team change / offboarding / orphan cleanup — six operations in B collapse to two in B′.

**Offboarding reconciliation — pick and justify:** both, with the **scheduled sweep as the authority** (GitHub Actions in the org repo, Actions-OIDC to Infisical, no static secret) and webhooks as a latency optimization. Justification: webhook delivery is best-effort; a design whose security depends on receiving an event fails silently when it does not. In B′ neither is needed for correctness, so the sweep's job becomes drift detection as an assurance control (identities `team_scopes` cannot explain, OIDC trusts that are not the current broker, privileges wider than their entry) — a quarterly access review on a cron.

**Audit:** three logs (broker = per-person attribution and every denial with reason; Infisical = which identity read which path; GitHub = membership, App and key changes), correlated on the machine id carried in the assertion `sub`. **Named residual:** per-scope identities mean Infisical's own log attributes reads to `enac-accounting-reader`, not Bob — B's one genuine advantage. Hybrid (per-person identity with `boundSubject`) sketched, not chosen; flagged for the sec pass.

## Deviations from ratified credentials-and-boundary.md §1.6

1. **§1.6.3 rung 1 re-specified** — no machine identity or service token on the device; a per-invocation assertion instead. Stricter than the ratified text, and it deletes the bootstrap-credential paradox that text implicitly created.
2. **§1.6.2 step 3's "point it at the same IdP already gating GitHub SSO" is not achievable with GitHub alone.** The ratified sentence assumes a federation GitHub does not offer for user identity. §1.6.2 step 3 should be amended rather than left as an unbuildable instruction.

## What fills team_scopes (G-9) — shape plus illustrative ENAC mapping

List of entries keyed by GitHub team **slug** within the `org:` already in `ecosystem.yml`; reserved slug `everyone` = any verified org member; per-entry `environment`, `secret_path`, `access`, optional `workspace_id`. Illustrative ENAC: `everyone → prod:/shared read`, `accounting → prod:/departments/accounting read`. Embedded decisions: slugs not display names; `everyone` as an ordinary row so there is one code path; `access: read` is the only self-serviceable value; **union across entries, no precedence, no deny rules**; unknown team ⇒ no grant, no wildcards; the map generates the admin's setup checklist 1:1 with the identities to create.

## Bob's experience delta (walkthrough 15)

Step 6's step-6 receipt becomes true for every entitled person rather than aspirational — shared rows read Ready with no button, the "Available to connect" card cannot render because the yours-but-not-connected state cannot occur. **The claim-code flow (4TQ9-KMD2 sheet, admin Requests panel, six pending/stale/declined states) becomes unnecessary for interactive users and should be marked as such rather than built**, surviving only as the shape for an admin minting a headless identity. Step 8 keeps its name and earns promotion out of the completion-rule exemption. Step 9's "Still to do" card disappears in the entitled case. The three failure sentences survive verbatim, because they remain three situations with three different next actors.

## Acceptance criteria

1. No user-facing surface displays, masks, truncates or copies a credential value or a credential **name**.
2. Every terminal state names an actor — Control Tower itself or a human — and no state's only instruction is to retry.
3. `cc store verify` passes only when a positive read succeeds **and** an unentitled read fails.
4. Removing a person from a GitHub team removes store access within one stated TTL, with no second admin act.
5. A machine with no entitled team gets the unentitled sentence, never a decline and never a button.
6. Unknown team or malformed `team_scopes` grants nothing and says which.
7. The bootstrap path is documented, short, and verifiable by the product itself.
