# Initiative 05 post-handoff work audit

## Decision

**No — the work does not yet achieve the full set of goals defined across the initiative and its handoff.** It successfully achieved the original audit-and-harness goal: the ecosystem was inventoried from consumer behavior, ambiguous policy calls were ratified, and the one-shot audit became a real, tested `cc conformance` command. It did **not** achieve the expanded outcome goal: the live ecosystem is not conformant, the complete installer round-trip is not correct, and organization/department content has not been shown to change real agent output.

The honest status is therefore:

| Goal level | Verdict | Reason |
| --- | --- | --- |
| Original initiative: evidence-based fleet audit | **Achieved** | The 76-row/75-directory source audit, 13-dimension rubric, classification, gap report, and 27 owner decisions are present and mutually traceable. |
| Original initiative: replace the manual audit with a rerunnable command | **Achieved** | `cc conformance check|report|baseline|explain|list` exists on `claude-copilot/main`, runs against the live machine, and has an active fixture-based CI workflow. |
| Evolved session goal: fix systemic causes and fan the fixes out | **Partially achieved** | All five registered RC checks pass live and major wiring/security defects were fixed, but live full-mode still has three S0 failures and the explicit round-trip adds a fourth S0. |
| Closing outcome: foundation + organization + department + personal produces company-specific, human-centered work | **Not achieved** | Resolution mechanics are exercised, but no real organization or department agent/command content wins attribution, `uids`/`cco` have no declared extension content, and there is no behavioral proof that real agent output changes. |
| Claim that initiative 05 is complete without qualification | **Rejected** | “Complete” is accurate only for the historical audit and harness-delivery phase, not for ecosystem conformance or effectiveness. |

This split verdict follows [`SOUL.md`](../../../../SOUL.md)'s priority order: say only what can be proved before relying on mechanism. A passing harness test suite proves that the harness can detect modeled states; it does not prove that the live ecosystem is healthy. The architecture principles likewise support locating state computation in `cc`, but they do not permit a synthetic install probe to stand in for real organization-specific behavior.

## Goal-driven target: the Copilot Solution Ecosystem

The Copilot Solution Ecosystem should give ordinary people the practical capabilities of a highly technical, multidisciplinary solution team.

A person should be able to begin with a real problem—not with software configuration—and receive the right combination of company knowledge, departmental expertise, specialist methods, tools, and guided workflows needed to create a useful solution. That solution might be software, automation, research, analysis, documentation, a service, or a physical-digital experience.

The ecosystem should make the result specific to the person, their department, and their organization—not generic AI output—without requiring them to understand terminals, repositories, agents, manifests, or infrastructure.

It should also remove Pablo as the person who must manually connect everything. Improvements made once at the appropriate level should safely reach everyone entitled to receive them.

### What each component does

| Component | Plain-language role |
| --- | --- |
| Knowledge Copilot | Supplies the knowledge and expertise: company context, standards, methodologies, department practices, writing guidance, research, and reusable skills. |
| Claude Copilot | Supplies one execution environment: specialist agents, workflows, commands, safety rules, and the protocol that decides which specialists should help with a problem. |
| Codex Copilot | Supplies the equivalent operating model inside Codex, so Codex can use the same specialist roles, standards, and project practices instead of behaving like an unrelated generic coding assistant. |
| `cc` CLI | Owns ecosystem truth. It discovers layers, resolves precedence, installs material into projects, updates it, verifies it, and runs conformance checks. Other surfaces should render its conclusions rather than recomputing them. |
| CLI Copilot / `copilot` CLI | Gives solutions controlled access to operational services such as infrastructure, deployment, secrets references, integrations, and communications. It provides capabilities without embedding credentials in inherited content. |
| Task Copilot / `tc` | Preserves execution state: plans, tasks, decisions, handoffs, test evidence, and durable work products. It allows complex solution work to continue across agents and sessions without relying on chat history. |
| Copilot Control Tower | Makes the ecosystem installable and dependable for a non-technical person. It supervises `cc`/`copilot`, keeps the machine synchronized, and reports verified status in plain language. It does not decide ecosystem state itself. |
| The project or solution | The destination of all this support. It remains self-contained and owned by the people creating it. Control Tower distributes the tools used to build solutions; it does not synchronize or take ownership of the solutions themselves. |

Claude and Codex are two execution faces of the same ecosystem. They should differ where their runtimes require it, but they should receive the same organizational intent, specialist model, safety posture, and knowledge.

There are also two distinct command-line responsibilities:

- `cc` manages and verifies the Copilot ecosystem.
- `copilot` provides operational and service capabilities.

They should integrate, but they should not duplicate each other's decisions.

### How the layers work

Each of the four component families—Claude, Codex, CLI, and Knowledge—can participate at four levels. Together, that creates the 16-layer ecosystem.

| Layer | What belongs there |
| --- | --- |
| Foundation / Core | Universal capabilities that should work for everyone: specialist roles, general methods, security rules, basic commands, and safe defaults. |
| Organization | What makes the ecosystem belong to this company: its purpose, language, operating principles, shared services, policies, standards, and organization-wide methods. |
| Department | What makes the help appropriate to a particular discipline or team: accounting practices, legal workflows, product methods, technical conventions, or other domain expertise. |
| Personal | What belongs only to one person: their preferences, private knowledge, memory, working style, and intentional personal overrides. It must never leak upward into shared layers. |

The layers should behave like inheritance, not four separate installations:

- Foundation fills the gaps.
- Organization makes the foundation company-specific.
- Department makes it appropriate to the person's area of work.
- Personal makes it useful to the individual.

When a nearer layer intentionally replaces something, the nearer version should win. When content is additive, the applicable layers should combine safely. If a layer has nothing substantive to contribute, it should fall through to the next layer rather than shadowing useful content with an empty placeholder.

### How everything should work together

The intended journey is:

1. **Access establishes entitlement.** GitHub repository access determines which organization, department, and personal layers a person may receive.
2. **`cc` resolves the correct ecosystem.** It reads the signed manifests and pins, walks the four-layer hierarchy, and determines the exact tools and content applicable to that person and project.
3. **The resolved result is installed and recorded.** Claude agents, Codex skills, commands, knowledge, hooks, and operational integrations are materialized into the project. The lock records where they came from and what was installed.
4. **Control Tower keeps it working.** It invokes the CLI on a safe cadence, renders verified status, and asks the person only about decisions that genuinely belong to them.
5. **The person begins with a problem.** They should not need to choose infrastructure or assemble agents manually.
6. **The protocol assembles the right specialist workflow.** Depending on the work, this might involve service design, UX, visual design, architecture, engineering, QA, security, documentation, operations, finance, or another specialist combination.
7. **The specialists receive the right context.** Their general expertise comes from the foundation, their company understanding from the organization, their domain expertise from the department, and their personal context from the individual layer.
8. **Operational tools help turn the work into reality.** The ecosystem can research, design, build, test, deploy, document, and operate a solution while keeping credentials and authority within the proper boundaries.
9. **Task Copilot preserves the evidence.** Plans, decisions, implementation records, verification, and handoffs remain durable across sessions.
10. **The resulting solution belongs to its creators.** It remains a self-contained project. The ecosystem can keep improving the tools used to create it without taking control of the product itself.

### The outcome this should produce

When the system works, people should be able to create solutions that are:

- grounded in a real human need;
- informed by company and department knowledge;
- produced through appropriate specialist methods;
- technically and operationally sound;
- secure and auditable;
- specific rather than generic;
- maintainable after the original session ends;
- achievable without Pablo manually wiring the system together.

The organization should be able to improve its collective ability once—by improving the proper shared layer—and have that improvement safely reach the people and projects that should receive it.

The individual should gain leverage without surrendering ownership or privacy.

### Important boundaries

This ecosystem is not meant to become:

- a generic chatbot layered over company documents;
- an autonomous decision-maker that replaces human judgment;
- a fleet-management or employee-monitoring system;
- a mechanism for synchronizing the products people build;
- a path through which personal content can move into shared repositories;
- a second implementation of state already computed by `cc`;
- a system that appears healthy when it cannot prove that it is.

The simplest expression of the goal is:

> Give every person access to a trustworthy, company-aware, multidisciplinary solution team—one that helps them turn real problems into working solutions without requiring technical expertise, while safely carrying the organization's accumulated knowledge and capabilities to them.

The ultimate goal is democratizing high-quality solution creation, not merely installing and maintaining a collection of copilots.

## Findings, ordered by consequence

### 1. The mechanism exists; the intended company-specific outcome does not

The best work in this initiative is the late distinction between **INSTALLED**, **WIRED**, and **EFFECTIVE**. That distinction is correct and should remain the organizing model. The work then stops one layer early: current E-1 proves that a synthetic organization marker can pass through the installer, while the live ladder contains no organization/department agent or command winner to exercise. No tier declares `uids` or `cco` extension content. There is no behavioral evaluation showing that a real agent produces organization-specific, human-centered work because of inherited content.

This is the binding reason the answer to the owner's closing question remains “not yet.”

### 2. Installer ownership is still split at a contract boundary

Three related facts show the same unresolved architecture:

1. `/setup-project` cannot create the Codex half of the reference install.
2. `cc workspace` and `/setup-project` install different Claude command sets; 23 live repos fail `repo.d01.command_set_exact`.
3. The effectiveness layer exercises the literal `/setup-project` bash path, not `workspaces.py`'s independent Python-native activation path.

The system therefore has no single end-to-end installer whose output defines “correct.” Passing component-level tests cannot close that ownership gap.

### 3. The advertised full verification is not actually full

`HARNESS-DESIGN.md` ADR-003 says full mode adds the round-trip. The shipped help says round-trip is opt-in, and ordinary `--full` produced zero round-trip checks. This matters because the omitted layer contains the additional S0. An operator following the initiative README's “run `cc conformance check --full` for the complete sweep” instruction misses it.

### 4. Live truth and regression truth are both visible, but not reconciled

The harness is admirably willing to fail. However, the live baseline comparison exits 3 with 82 regressions while the fixture CI remains green. That combination is explainable—World A and World B are different—but the operator evidence is not in a closure-ready state. Intentional exclusions, new checks, and genuine drift need to be reconciled into a new reviewed baseline before “no regressions” can be claimed.

### 5. Documentation and provenance drift weaken the handoff

- `tools/cc/docs/conformance-harness.md` still says the CLI has not landed and the branch is unmerged.
- The initiative README's `Current Summary` still lists merge/fan-out work as remaining even though the handoff says both happened.
- `handoff/00-what-happened.md` records 2,632 tests and invokes `python`; the current collection is 2,607 and `python` is not on PATH (`python3` and the venv interpreter work).
- The initiative cites `PRD-22` and tasks `264–276`, but the current `claude-copilot` task database contains neither. The source commits are strong; the claimed Task Copilot provenance is not recoverable from the referenced live store.

These are not cosmetic under the project's product doctrine. A conformance system's documentation is part of its proof surface.

## What the work did well

- Converted a costly manual investigation into executable checks with structured evidence and honest exit codes.
- Preserved a no-score severity model rather than manufacturing a misleading fleet percentage.
- Added paired positive/negative fixtures and a read-only World-B guard.
- Found and fixed real defects that structural inspection had missed: shell behavior, lock-key confusion, waiver holes, orphan-tag provenance, stale version-only fan-out, and inert tier resolution.
- Added the effectiveness layer after recognizing that structural conformance was measuring the wrong property.
- Kept the harness in the CLI that owns ecosystem state, consistent with Control Tower's parse-never-compute boundary.
- Shipped an unconditional World-A CI workflow that is green on current `main`.

## Required closure sequence

1. **Choose one canonical project-install transaction.** It must produce the complete Claude + Codex reference install, and both `/setup-project` and `cc workspace` must either call it or become explicitly non-equivalent surfaces with separate contracts.
2. **Restore the missing end-to-end assertions.** Full mode must include round-trip as designed, or the docs/command name must stop calling it complete. Prove degraded-install repair and final Layer-3 parity, not only degradation detection.
3. **Fix the three E-4 S0 attribution/materialization mismatches.** Do not weaken the check; repair personal-tier plugin lock recording.
4. **Reconcile the live baseline deliberately.** Classify the 82 PASS→FAIL pairs into ratified intentional change versus real regression, resolve the latter, then regenerate with an auditable reason. Update `expected_today` metadata to current truth.
5. **Author real organization/department content.** At minimum, add substantive agent/command contributions and the missing `uids`/`cco` extensions at the appropriate tiers.
6. **Add behavioral effectiveness evidence.** Run real agents against controlled prompts with and without the nearer-tier content and verify the intended organization-specific behavior, while preserving the existing structural checks.
7. **Repair the durable record.** Update the operator docs and initiative summary, and either recover/import PRD-22/tasks 264–276 or explicitly mark those references historical and unavailable.
8. **Re-run both verification surfaces.** Require ordinary full mode plus explicit round-trip (until they are unified), zero S0, zero unexplained could-not-run results, and a baseline comparison with zero unreviewed regressions before changing the outcome verdict.
