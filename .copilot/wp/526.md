# Harden CT_CLI_PATH override against unverified helper execution

Fixes Finding A from security work product WP-525 (task 248, PRD 18 stream 37 — Phase 9.2 shipped-artifact security review of Control Tower 0.6.0 / cc 2.7.0). Branch `app-build`. Changes are uncommitted in the working tree for the integrator to review.

## The defect

`CliLocator.locate()` in `native/cli-client.swift` honored the `CT_CLI_PATH` environment variable to override which `cc` binary the app executes, with no signature or checksum verification on the override target — only `FileManager.isExecutableFile`. In the shipped, notarized 0.6.0 app, a local attacker able to set the app's process environment (e.g. `launchctl setenv CT_CLI_PATH ...`) could redirect every `cc` invocation the app makes, including the Terminal-launched reconciliation assistant, to an arbitrary unverified binary — a direct violation of CLAUDE.md invariant #4 ("nothing security-critical comes from user-editable local config").

## The fix

Added a compiled-in trust anchor, `ProductionTrustAnchor` (`native/cli-client.swift`), that checks a file's code signature via the Security framework (`SecStaticCodeCreateWithPath` / `SecRequirementCreateWithString` / `SecStaticCodeCheckValidity`) against the literal requirement `anchor apple generic and certificate leaf[subject.OU] = "3SYGVX2HB8"` — this project's own Developer ID team, already public (printed by `codesign -dvv` on every artifact this project ships, and already quoted in `CLAUDE.md`/`docs/01-architecture/architecture.md`). `anchor apple generic` is what makes this unforgeable by a locally-generated self-signed certificate; a bare string compare against the embedded team-identifier field without that anchor clause would not be.

`CliLocator.locate()` gained a second injectable parameter, `runningExecutablePath` (defaults to `Bundle.main.executablePath`, mirroring the existing `bundledResourceURL` test seam). It first checks whether the CURRENTLY RUNNING process itself satisfies `ProductionTrustAnchor` — i.e. whether this is the shipped, Developer-ID-signed article (the only shape Gatekeeper/notarization ever lets an ordinary user launch). If not (every dev/test build in this repo is ad-hoc signed, or briefly unsigned mid-release-pipeline — see below), `CT_CLI_PATH` behaves exactly as before: any executable file wins. If the running process IS the production-signed article, an override is only honored when the override target ALSO satisfies `ProductionTrustAnchor`; otherwise it falls through to the bundled/standard resolution exactly as an unset override already does. This is a fail-safe fallthrough, never a crash or hard error — matching the existing "unset/non-executable override just falls through" semantics documented in the original code's own comment.

This was chosen over the WP's other suggested option (`#if DEBUG` compile-time gating) because this repo's build scripts (`scripts/build-user.command`) never pass `-D DEBUG` to `swiftc` for ANY build, including the shipped one — `#if DEBUG` would simply never be true anywhere, silently disabling the override everywhere including the legitimate dev/test seam, or (if inverted) leaving it enabled everywhere including the shipped binary. A runtime signature check on the running process itself works correctly across every existing build invocation without any new build flag.

## A conflict this fix exposed, and its resolution

`scripts/package-user-release.sh` (the real release pipeline) runs `scripts/headless-setup-transaction.sh` — which drives the app through `CT_CLI_PATH=<repo>/src-tauri/fixtures/mock-cc` to prove the real `WizardModel` Set up → Verify wiring without a live mutation — AFTER `scripts/sign.sh` applies the real Developer ID signature to the app bundle. Under the new fix, at that point in the pipeline the running app IS the production-signed article, so it would refuse the mock-cc override and silently fall back to the REAL vendored `cc`, turning an inert proof into a live `onboard --apply` invocation on the release-signing machine.

Verified this was a real, not hypothetical, problem: manually built the app with `CT_SKIP_ADHOC_SIGN=1 CT_VENDORED_CC_PATH=packaging/cc/cc` (matching the release script's own build step), signed it with this machine's real Developer ID Application identity (`security find-identity`), then ran `scripts/headless-setup-transaction.sh` against it — it failed (`SELFTEST setupTransaction timeout=fail`) because `CliLocator` correctly refused mock-cc and the real `cc onboard --apply` call hung/timed out rather than completing (the app's own selftest harness has an internal timeout that killed it cleanly; no filesystem mutation resulted — verified via `git status --short` in this repo and `claude-copilot` afterward, both clean).

Fixed by reordering `scripts/package-user-release.sh`: the two headless proofs (`headless-detect.sh`, `headless-setup-transaction.sh`) now run BEFORE `scripts/sign.sh`, while the app wrapper is still only ad-hoc/linker-signed (`CT_SKIP_ADHOC_SIGN=1` skips the bundle-level ad-hoc pass, but swiftc's own linker still ad-hoc-signs the raw binary — confirmed via `codesign -dvv`: `flags=0x20002(adhoc,linker-signed)`, `TeamIdentifier=not set`), so `ProductionTrustAnchor` correctly does not recognize it as the production article and the override keeps working. Re-verified this exact scenario end to end: pre-sign, `headless-setup-transaction.sh --skip-topology-leg` against the reordered build produced `SELFTEST setupTransaction apply=ready layerManifest=applied onboardDoctor=healthy verify=healthy` as expected. `scripts/verify-user-automation.sh` (which reads entitlements off the real signature) and the embedded-cc checksum/`verify-vendored-cc.sh --release` checks stay exactly where they were, after `scripts/sign.sh`, since none of them depend on ordering relative to the headless proofs.

This reorder was NOT run end-to-end through the full `package-user-release.sh` (that needs notarization credentials and 10+ minutes; not part of this task's required gates), so the integrator should treat the next real release cut as the first full validation of the new order, though every individual piece (build → pre-sign headless proofs → sign → automation/checksum verification → notarize) was independently exercised above.

## Finding B assessment (Python `claude` PATH fallback) — not fixed, per task scope

Read `claude-copilot/tools/cc/src/cc/core/ecosystem/reconciliation_assistant.py:340-369` (`_supported_claude_path`). Confirms the WP's characterization: resolution order is an explicit param, then `CC_ASSISTANT_CLAUDE_PATH`, then `shutil.which("claude")` (PATH-order-dependent). Real but properly bounded: the resolved path is post-checked (regular file, owned by root or the current euid, no group/other-write bits, executable) before use, and the resulting Claude Code subprocess runs with `--tools "" --permission-mode plan` regardless of which binary answered, so a substituted binary gains no write authority over any project — at most it could return a `candidate_id` string, which `_validated_selections` schema-validates against the legitimately-offered id set. Left unfixed per this task's explicit instruction to treat the Swift `CT_CLI_PATH` issue as the primary fix; flagging for a future, separately-scoped follow-up (e.g. requiring `CC_ASSISTANT_CLAUDE_PATH` outright and dropping the `shutil.which` fallback, or applying the same anchor-apple-generic team check used here) if the team wants Finding B closed too.
