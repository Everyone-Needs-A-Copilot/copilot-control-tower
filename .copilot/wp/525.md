# Phase 9.2 shipped-artifact security review — Control Tower 0.6.0 / cc 2.7.0

Task 248 (PRD 18, stream 37). Reviewer: security engineer (STRIDE+DREAD). Scope: read-only review of the SHIPPED artifacts only — no live project was touched, no apply was run, no mutation was performed against any repository during this review. The `.claude/skills/security/stride-dread/SKILL.md` file referenced by the agent brief does not exist in this repo (only `admin-bootstrap` and `codex-copilot` skills are installed); the methodology below is applied directly from the security-engineer role definition instead.

## Trust boundary map

1. **Apple / notarization service** — external, signs off on Developer ID artifacts; trusted only via `spctl`/`notarytool` verification, never bypassed.
2. **Control Tower app process** (`/Applications/Copilot Control Tower.app`) — runs as the logged-in user, holds the `com.apple.security.automation.apple-events` entitlement (needed to drive Terminal via AppleScript) and nothing else.
3. **Embedded `cc` helper** (`Contents/Resources/cc`, cc 2.7.0) — a separately signed/notarized, checksum-pinned Python-frozen binary. This is the sole place with filesystem write authority over selected projects.
4. **Terminal + user shell** — launched by the app via AppleScript `do script`; this is the handoff point from GUI to a visible, user-auditable shell session.
5. **Claude Code subprocess**, spawned by `cc reconcile assistant-run` — runs in a private, mode-0700 per-session workspace, `--tools ""`, `--permission-mode plan`, filtered environment. This is the one boundary where an external LLM agent is deliberately given *zero* write authority and a content-free packet.
6. **Selected Git projects on disk** — the actual mutation target; reached only through `AnchoredProject` (dir-fd-anchored, `O_NOFOLLOW`, containment-checked) under a per-project `flock`.
7. **Private helper state** (`machine_diagnostics_root()/reconciliation/assistant/**`) — sessions/proposals/diagnostics; mode 0700 dirs / 0600 files, never inside a selected project's own tree.

Entry points reviewed: the app→Terminal→`cc` launch surface (native Swift), the `cc reconcile assistant-prepare/-run/-status` verbs and their session/proposal store (Python), the Claude Code subprocess invocation, the durable-diagnostics writer, the release/signing pipeline, and the committed provenance/config in this repo.

### 2. Terminal launch carries only the exact bundled `cc` path + `reconcile assistant-run --session-id <opaque-id>` — CONFIRMED, with one adjacent design note

- `native/cli-client.swift:267-309` (`ReconciliationAssistantTerminalCommand`): `arguments = ["reconcile", "assistant-run", "--session-id", sessionId]`, full stop — a `struct` deliberately kept literal/`Equatable` "so the security boundary is reviewable." No project path, prompt, patch, or free-form text is concatenated anywhere in `commandLine`/`appleScriptSource`. `native/wizard.swift:190-217` (`ReconciliationAssistantLauncher`) confirms the doc comment: "no generated prompt is copied, no project directory is passed, and no assistant executable is resolved from the shell."
- **Adjacent finding (not a violation of the literal claim, but relevant to invariant #4):** `CliLocator.locate()` (`native/cli-client.swift:217-264`), which supplies the `executableURL` for *every* `cc` invocation including this one, checks a `CT_CLI_PATH` environment-variable override *before* the bundled, checksum-pinned `Contents/Resources/cc` path, and accepts any executable file at that path with no signature or checksum check. Confirmed present in the shipped, notarized production binary (`strings` on the release Mach-O shows the literal `CT_CLI_PATH` string; no `#if DEBUG` guard around it in source). This is a pre-existing, previously-documented dev/test seam (used pervasively by `scripts/tests/smoke-scenarios.sh` and referenced in `docs/04-validation/evidence-2026-08-02-code-ground-truth.md`), not a Phase 9.2 regression, and the sibling `control-tower-tray.swift:2748` selftest path shows the team already has the right hardening pattern elsewhere ("`CT_CLI_PATH` must never turn a selftest into a live mutation"). It is not applied to `CliLocator` itself. See Findings section below.

### 3. Claude Code receives a content-free, candidate-id-only packet with no write authority — CONFIRMED

Reviewed `claude-copilot/tools/cc/src/cc/core/ecosystem/reconciliation_assistant.py` (969 lines) in full, at the exact shipped commit `3630821e...`.

- The packet built in `_candidate_catalog` contains only `project_ref` (`project_<32 hex>`, opaque, freshly random per session), `component` (`"claude"`/`"codex"`), `candidate_ids` (`candidate_<64 hex>`, opaque, freshly random), and a fixed `evidence_codes: ["customized-setup-present"]` — never a filesystem path, file content, diff, or command. `_PROHIBITED_ASSISTANT_KEYS = {"command", "path", "content", "patch", "operation"}` is actively checked against the wrapper Claude returns (`_contains_prohibited_assistant_key`), and the accepted output shape is constrained to `{"selections": [{"candidate_id": <enum of offered ids>}]}` via a JSON Schema passed to Claude Code itself (`--json-schema`) *and* independently re-validated server-side in `_validated_selections` (bounded JSON depth/node count, strict UTF-8, duplicate-key rejection, `additionalProperties: false`, exactly-one-per-required-group enforcement).
- Claude Code is invoked with `--safe-mode --tools "" --permission-mode plan --strict-mcp-config --disable-slash-commands --no-session-persistence --no-chrome --print --input-format text --output-format json --json-schema <schema>` (`_invoke_claude:490-508`) — an empty tool list plus plan-only permission mode means the subprocess has no file-write or command-execution capability at all, independent of the packet content.
- Working directory is a private per-session dir created with `mode=0o700`, and its `lstat()` is checked post-creation for `S_ISDIR`, not-a-symlink, owner-uid match, and no group/other bits (`0o077` mask) before use — matching claim 4's directory-mode requirement.
- `_safe_environment()` allowlists a minimal environment (`HOME, USER, LOGNAME, SHELL, PATH, TMPDIR, LANG, LC_ALL, LC_CTYPE, TERM, HTTPS_PROXY, HTTP_PROXY, NO_PROXY, SSL_CERT_FILE, SSL_CERT_DIR, NODE_EXTRA_CA_CERTS, CLAUDE_CONFIG_DIR`) and explicitly strips any `HTTPS_PROXY`/`HTTP_PROXY` value carrying embedded Basic-auth credentials.
- `_supported_claude_path()` validates the resolved `claude` executable is a regular file, owned by root or the current euid, and has no group/other-writable bits before exec — a real (if PATH-order-dependent, see Findings) safety check.
- Raw stdout/stderr from the Claude subprocess are written to `0600` files opened with `O_EXCL|O_NOFOLLOW` and are `unlink()`-ed in the `finally` block regardless of outcome (`:509-577`); only the schema-validated `{"candidate_id": ...}` selections ever leave this function. No raw model output, prompt echo, or transcript is persisted to the durable diagnostic or session store.
- `_resolved_request`/`resolve_assistant_request` then re-validate, at proposal-resolution time, that Claude's selection did not expand project/component authority, cannot silently override an already-explicit deterministic recipe choice ("assistant-authority-overlap"), and that the resolved request's `roots`/project set is byte-identical to the originally requested one.
- Conclusion: **claim holds** — Claude Code genuinely has no path, content, patch, command, or write authority, by construction (empty tool list + plan permission mode) and by defense-in-depth (schema + prohibited-key + bounded-JSON validation on its output).

### 4. Durable diagnostics — CONFIRMED

`claude-copilot/tools/cc/src/cc/core/ecosystem/migration_diagnostics.py`:

- Directories created via `_ensure_private_directory` at `0700` (`boundary.chmod(0o700); path.chmod(0o700)`); files written via `tempfile.mkstemp` in the same directory, `chmod(0o600)`, then `os.replace()` (atomic same-directory rename) followed by an `fsync` of the containing directory descriptor — genuine atomic same-directory replacement, not a cross-directory move.
- Symlinked-boundary rejection: `_ensure_private_directory` checks `boundary.parent.is_symlink() or boundary.is_symlink() or path.is_symlink()` both before and after `mkdir`, raising `OSError` on either check — closes the TOCTOU window between existence check and directory creation.
- Retention: `DEFAULT_RETENTION = 20`; `_prune()` sorts existing `workspace-migration-*.json` records by mtime and unlinks everything past the newest `max(1, retention)` — confirmed keeps 20 by default.
- Redaction: `_redact()` recursively walks the payload; keys named `api_key/access_token/authorization/password/secret/token` are replaced outright, remaining string values are scrubbed by three regexes (`key: value`/`key=value` secret-assignment patterns, `Bearer <token>`, and known token prefixes `ghp_/gho_/ghu_/ghs_/ghr_` and `sk-`), and any string is truncated to 8000 chars. Non-JSON-primitive values (anything not `dict/list/tuple/str/None/bool/int/float`) are replaced by their type name only, never serialized — this is the mechanism that prevents accidental leakage of e.g. an `os.stat_result` or exception object with embedded raw content.
- The assistant lifecycle specifically never routes raw subprocess stdout/stderr, env values, or stdin into this or any other durable record — see claim 3 above; those files are deleted in the same function that produces them, before any diagnostic write occurs.
- Failure handling: `write_workspace_migration_diagnostic` catches `OSError` and returns a `state: "unavailable"` reference without raising — matches "diagnostic-write failure must not falsify the in-memory action receipt."
- The private assistant session/proposal store (`assistant_job_store.py`) applies the identical 0700/0600 + no-symlink + `O_NOFOLLOW` discipline via `ensure_private_directory`/`atomic_json_write` (`project_locking.py`), and additionally binds every record to a SHA-256 fingerprint over its immutable fields plus a separate fingerprint over its mutable state, so any on-disk tampering (edited JSON, swapped file) is detected as `AssistantBindingMismatch` on next read — this is the "reject tampered/unsafe" behavior claim 18 in the handoff describes.
- **Live verification, not just static review**: ran `uv run pytest tests/test_reconciliation_assistant_security.py tests/test_reconciliation_assistant_store_security.py` at the shipped commit (`3630821e...`) in an isolated `tmp_path` sandbox — **23/23 passed**, including `test_session_artifacts_are_private_regular_single_link_files`, `test_session_tampering_is_rejected`, `test_session_expiry_and_single_claim_fail_closed`, `test_session_record_cannot_be_swapped_under_another_session_id`, `test_two_concurrent_claims_have_exactly_one_winner`, and `test_proposal_tampering_is_rejected`. The `claude-copilot` working tree remained clean (`git status --short` empty) after the run — no project or repo state was mutated by this review.

### 6. Path containment: bounded targets, symlink/traversal refusal, dirty/held/unreadable projects remain unmutated — CONFIRMED

`claude-copilot/tools/cc/src/cc/core/ecosystem/project_locking.py`:

- `normalize_relative_target()` rejects absolute paths, null bytes, backslashes, and any `.`/`..`/empty path segment outright — traversal is refused at parse time, not just at open time.
- Every filesystem traversal (`AnchoredProject._open_parent`, `.lstat`, `.read_bytes`, `.export_tree`, `.install_tree`, `.atomic_write`, `.atomic_symlink`, `.fingerprint`, `.remove`) walks the path component-by-component using `os.open(..., dir_fd=parent, flags=O_NOFOLLOW|O_DIRECTORY)`, so a symlink planted at *any* level of a target path causes an `OSError` → `UnsafeProjectPath`, not a followed link. `atomic_symlink()` additionally walks the *link value itself* to reject one that would resolve outside the project root, unless the caller explicitly passes `allow_external_restore=True` (used only to restore a symlink that already existed and pointed outward before the transaction began — reviewed, not a general escape hatch).
- `inspect_project_identity()` refuses a symlinked project root, requires root/`.git` ownership to match the effective uid, and binds a `ProjectIdentity` to `(device, inode, git_device, git_inode, head_oid, head_ref)`. `project_lock()` re-inspects this identity *twice* — once before acquiring the `flock`, once again immediately after — and raises `ProjectIdentityMismatch` ("The project changed while its lock was acquired") if anything drifted, which is exactly the "re-inspect immediately before mutation" / "refuse a stale plan" requirement in handoff §6.5.
- Writes are same-directory temp-then-`os.replace()` with `fsync` of both the file and the parent directory descriptor (`atomic_write`, `install_tree`) — same atomic-replacement discipline as the diagnostics writer.
- A dirty/unreadable/non-Git project fails `_git_path`/`_git_head`/`inspect_project_identity` outright (each raises `ProjectIdentityMismatch` with a specific reason) before any target is touched, and `project_lock()`'s cross-process `flock` (`advisory_file_lock`, `LOCK_EX|LOCK_NB`) makes a concurrently-running reconciliation fail closed with `ProjectLockContention` rather than racing a second process onto the same tree.
- This module is shared by both the deterministic reconciliation path and the bounded-assistant resolve path (`reconciliation_assistant.resolve_assistant_request` ultimately calls `prepare_reconciliation`, which uses the same `project_lock`/`AnchoredProject` machinery) — there is no separate, less-guarded write path for assistant-originated proposals.
- I did not execute a live apply (out of scope, per instructions); this is a static-plus-unit-test review of the enforcement code and its adversarial test suite (`test_reconciliation_assistant_security.py`, `test_reconciliation_assistant_store_security.py`, both run and passing above), not a fresh fault-injection run against a real fixture repo.

## STRIDE classification and DREAD scoring of findings

### Finding A — `CT_CLI_PATH` environment override can redirect every native-side `cc` invocation, including the Terminal launch, to an unpinned, unverified binary

- **STRIDE:** Tampering (the invoked binary is substituted) leading to potential Elevation of Privilege (arbitrary code runs with the user's privileges inside a visible Terminal session, and via every other `cc` call the app makes).
- **Evidence:** `native/cli-client.swift:217-264` (`CliLocator.overrideEnvVar = "CT_CLI_PATH"`, checked before the bundled `Contents/Resources/cc` path, validated only with `FileManager.isExecutableFile` — no signature or checksum check); `strings` on the installed release binary confirms the literal `CT_CLI_PATH` string is present in the shipped Mach-O with no `#if DEBUG` guard in source.
- **DREAD:** Damage 7 (arbitrary binary execution as the logged-in user, in a visible Terminal, across every `cc` call the app makes) / Reproducibility 9 (trivial once the env var is set) / Exploitability 6 (requires the ability to set an environment variable that propagates into the app's process — e.g. `launchctl setenv CT_CLI_PATH ...` for the current user session, or launching the app from a crafted environment; this is unprivileged but requires the attacker already have local code-execution as the same user) / Affected users 5 (every installation carries the same design; blast radius per exploitation is the single user session) / Discoverability 7 (documented in-repo comments and prior ground-truth docs, plus a trivial `strings` check) → **average ≈ 6.8, High**.
- **Context that bounds severity:** this is a pre-existing, previously-reviewed dev/test seam (not introduced by Phase 9.2), used extensively by the app's own smoke-test harness, and exploitation requires a precondition (local ability to set the app's process environment) that is itself a meaningful bar — an attacker who already clears that bar has other avenues on the same machine. It does not weaken the *release pipeline's* signing/notarization guarantees (Finding covers the *installed app's* trust decision at launch time, not the artifact's authenticity).
- **Why it is still a genuine finding against this review's claims:** it directly contradicts invariant #4 ("nothing security-critical comes from user-editable local config") for the specific code path this review was asked to verify (claim 2), and the resolved binary is checked for *executability* only, not against `PINNED_SHA256` or a signature, unlike the `Contents/Resources/cc` path it can preempt.
- **Remediation (code fix, not a WAF):** gate `CT_CLI_PATH` behind a compile-time `#if DEBUG`/test-configuration flag so it cannot exist in a notarized Release build at all, or — if a release-time override must remain for support/reinstall scenarios — require the override target to satisfy the same Developer-ID-signature check the bundled binary implicitly gets from Gatekeeper (e.g., `codesign --verify` against the app's own signing identity) before `CliLocator.locate()` accepts it, mirroring the existing "`CT_CLI_PATH` must never turn a selftest into a live mutation" pattern already used in `control-tower-tray.swift:2748-2750`.
- **Route:** @agent-me (native Swift fix — compile-time guard or signature check in `CliLocator.locate()`).

### Finding B (informational / not a warning) — `claude` executable resolution falls back to `shutil.which("claude")` (PATH-order dependent) when `CC_ASSISTANT_CLAUDE_PATH` is unset

- **STRIDE:** Tampering (a different `claude` binary could be resolved via PATH order).
- **Evidence:** `reconciliation_assistant.py:340-351,`_supported_claude_path`.
- **DREAD:** Damage 5 / Reproducibility 6 / Exploitability 4 (requires attacker-controlled PATH ordering, i.e. already-local code execution as the same user) / Affected users 3 / Discoverability 4 → **average ≈ 4.4, Medium-low**. Meaningfully mitigated by the post-resolution ownership/permission check (must be owned by root or the current euid, no group/other-write bits) and by the fact that even a substituted `claude` binary would still run with `--tools ""`/`--permission-mode plan` inside a 0700 workspace, so a malicious binary standing in for `claude` gains no more write authority over a selected project than the real one has (none) — it could only return a bogus `candidate_id`, which Python's `_validated_selections` would reject unless it happens to be one of the legitimately offered ids. Logged as a warning, not blocking.

No other Critical or High findings were identified. One further observation, not scored (informational, does not rise to "warning"): the migration-diagnostics redaction regexes (`_SECRET_ASSIGNMENT`, `_BEARER_VALUE`, `_KNOWN_TOKEN`) are a defense-in-depth backstop; the assistant lifecycle's own design (never writing raw model/stdout content to any diagnostic in the first place) is the real guarantee, consistent with this review's "confirm the code, don't just add a scanner" posture.

## Risk rating and conclusion

**Overall risk: LOW-MEDIUM.** Every one of the six specific claims in this review's brief is substantiated by source-level evidence, independent checksum/signature verification against the actual installed artifacts, and (for the assistant lifecycle and its store) a live, passing run of the dedicated adversarial test suite (23/23) at the exact shipped commit. The bounded-Claude design is unusually rigorous for a "give an LLM a job" feature: empty tool list, plan-only permission mode, fingerprint-bound tamper-evident session/proposal storage, dir-fd-anchored no-follow filesystem access, and a defense-in-depth-redacted diagnostic trail that also structurally never touches raw model output. The one finding that matters (Finding A, `CT_CLI_PATH`) is real, contradicts the letter of invariant #4, and should be fixed, but it is a pre-existing, previously-known, local-attacker-precondition issue, not a defect introduced by or specific to this release, and it does not compromise the release pipeline's signing/notarization/provenance guarantees, which are all independently verified and hold.

**Conclusion: APPROVED-WITH-FINDINGS.** Recommend Finding A be scheduled as a near-term follow-up (route to @agent-me) rather than treated as a release blocker, given its local-precondition-gated exploitability and its pre-existing status across the whole app rather than something newly shipped in Phase 9.2. Finding B is recorded for awareness only.
