## Blocking findings

### P1 — Published release tag is not server-immutable

Repository and inherited ruleset count is zero; no observable tag protection exists. Branch protection governs `main`, not `refs/tags/v1.0.0`. A writer/admin can therefore delete or replace the tag ref. An unsigned replacement should fail the downstream signer check, but deletion causes denial of service and a newly signed replacement from the trusted key would retain cryptographic validity while violating the non-moving-tag contract.

GitHub documents tag rulesets as the control for tag interaction, including update/deletion restrictions; branch protection is branch-scoped.

Required remediation: create an active repository or organization tag ruleset targeting release tags (at least `v*`) that blocks updates and deletions with no routine bypass. Verify via the effective rules API and negative update/delete probes against a disposable test tag, never the published tag. Record the ruleset identity and effective bypass actors.

### P1 — Sensitive-content regression gate is advisory, not merge-enforced

Accounting has no `.github/workflows` directory, `main.required_status_checks` is null, and no ruleset supplies an equivalent required workflow. The 24 tests and whole-tree scanner pass manually, but a signed/reviewed PR can merge without running them. That leaves accidental or collusive reintroduction dependent on human memory.

Required remediation: add a minimal reviewed CI workflow that runs the value-suppressing no-argument scanner and its focused tests without secrets or artifact upload; require its exact check from an expected GitHub App on `main`. Because this changes the approved tree, use a new reviewed signed commit and new non-moving corrective tag, then update the pin and repeat QA/security. Never move `v1.0.0`.

### P1 — Need-to-have access is not established while hosted legacy data remains directly reachable

Current access is private and has zero direct/outside collaborators, but organization default read grants the repository to the inherited roster. WP-749 explicitly says no evidence proved whether removal was authorized or operationally safe, while task metadata says `accessReviewCompleted=true`. Resolving names and retaining them as exceptions is not proof of present business need. This matters because the legacy commit is still directly addressable to entitled readers.

Required remediation: perform the approved private named-roster review with a human owner, recording an explicit retain/remove decision and business role for every inherited admin/read entitlement and the Accounting team. If broad organization default read is not intended for department-sensitive content, replace it with a repository/team entitlement model without inferring individual removals. Until then use `rosterResolved=true`, `needToHaveConfirmed=false`, and do not claim the access review complete.

### P2 — Knowledge consumer proof is a current snapshot, not enforced immutable loading

The effective layer manifest records `v1.0.0` and the allowed signer, and current `cc skill path/get` bytes match the sanitized checkout. However, the live skill loader enumerates `paths.knowledge_repo` directories and reads `SKILL.md` from the mutable local filesystem; it does not consult `layers.manifest`, resolve the tag, or verify the signer during `skill get`. A same-user edit can therefore change consumed bytes while the recorded pin remains unchanged.

Required remediation: correct WP/task language from “consumer bind” to “current-byte snapshot verified” and record `knowledgeRuntimeImmutableEnforcement=false`. For durable AC-23 proof, route Knowledge reads through a verified tag/tree materialization or add an authenticated pre-read binding that fails closed on ref/tree/signer or dirty-byte mismatch. Until then revalidate tag/tree/clean worktree/scanner immediately before every controlled use and do not claim runtime-enforced immutability.

## Existing P1 residual — hosted and external history containment

All advertised remote refs are sanitized, but status-only reproduction confirms the legacy commit still resolves by direct GitHub OID. GitHub documentation says Support is required to remove cached views/references and run server-side garbage collection after a sensitive-data rewrite. No Support request or purge proof exists. Prior clones, backups, devices, snapshots, and other copies remain unobservable.

Required remediation remains exactly WP-752/WP-754: private GitHub Support request, provider garbage collection/cache removal, then repeated value-suppressing direct-OID denial proof. Coordinate prior readers to discard or sanitize clones. Do not equate no advertised ref with full purge, and do not claim external-copy containment.

## Rollback and recontamination assessment

The value-free rollback record correctly forbids restoring old history, and local old objects are gone. However, direct-OID availability means an entitled actor can still recover the old object until provider cleanup. Current branch review/signature controls make direct restoration harder, but the missing required scanner means a reviewed signed change can reintroduce the same data classes. The missing tag rule also permits deletion/replacement of the published identity.

Safe rollback remains: preserve `v1.0.0`, pin a newly reviewed corrective signed tag when needed, and never move an existing tag or restore the recorded old lineage. Provider cleanup, tag rules, required scanning, and access confirmation must precede release completion.
