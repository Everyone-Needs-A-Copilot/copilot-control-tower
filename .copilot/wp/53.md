# M9 Windows re-skin — ADR bundle (ADR-M9-001..006), RATIFIED

Phase P4 (final, deferred). Canonical spec: `docs/01-architecture/windows-parity.md`
(11 OS-integration mechanisms, §1) and its §3 open questions (Q1–Q6). Governing
constraint, unchanged from the WP-52 draft this bundle supersedes: **no Windows
toolchain on this machine** — every line of Windows code lands behind
`#[cfg(windows)]` (or `#[cfg(not(target_os = "macos"))]`, matching the pattern
`managed/forced.rs` already established); the macOS build/test suite stays
green throughout; Windows build/test/EV-sign/enrollment is **owner-gated**
(`docs/06-deployment/m9-owner-gated-split.md`). This bundle resolves
`windows-parity.md` §3 Q1–Q3 by direct mapping (ADR-M9-002/003/004) and folds
Q4–Q6 plus the DPAPI/MSI/tray seam notes into ADR-M9-001/005/006 below; Q5 is
explicitly **not** resolved (blocked on an upstream open decision, not a
Windows question).

## ADR-M9-001: Light platform-abstraction consolidation (not big-bang traits)

**Status:** Accepted

**Context:** The codebase already uses a "neutral DECIDE + thin
`#[cfg(target_os = "macos")]` HOW seam" pattern —
`managed::forced::real_key_is_forced`/`real_forced_string` already ship a
`#[cfg(not(target_os = "macos"))]` fail-closed stub (returns `false`/`Absent`,
never guesses) whose own doc comment names M9/WS-I by number as the future
consumer. A dynamic-dispatch trait rewrite across the whole crate would risk
proven-green macOS code for uncertain benefit and can't be Windows-verified on
this machine anyway.

**Decision:** Introduce `src-tauri/src/platform/` (Stream-B's module, referenced
here for the seams it must expose, not built by this WP): `trait`s ONLY where a
mock already exists or is needed —
`PlatformForcedConfig`/`PlatformLoginItem`/`PlatformWatchdogSignal`/
`PlatformSecretStore` — zero-cost `cfg`-gated `pub use` aliasing everywhere else
(tray glyph selection, CLI install-path resolution, packaging). The macOS impl
is a THIN wrapper over existing, already-tested functions (move no logic — pure
refactor); the Windows impl is a new `#[cfg(windows)]` sibling. Three
named seam notes fold in here rather than getting their own ADR number:

- **`PlatformSecretStore` (Credential Manager/DPAPI, invariant #6).** The
  `keyring` crate (already named as the cross-platform abstraction in
  `design-distribution.md` §6 and `credentials-and-boundary.md` §1.4/§6.1)
  backs both `Security.framework` Keychain and Windows Credential Manager
  behind the one trait; SSH private keys use the platform `ssh-agent` +
  Credential Manager exactly as `credentials-and-boundary.md` §6.1 already
  specifies. DPAPI ties the encryption key to the logged-in Windows profile
  (parity to per-user Keychain scoping) but — per
  `credentials-and-boundary.md` §6.5's own flag — is recoverable by anything
  running as that same user, with no separate unlock/ACL prompt the way
  Keychain can require. That gap is real and owner-gated
  (`m9-owner-gated-split.md` — "DPAPI re-verify"), not something a trait
  boundary can close by construction.
- **Tray glyph light/dark (invariant #1 — parse, never compute).**
  `render::glyph`'s macOS path composites an alpha-only silhouette into a
  `tauri::image::Image` and relies on `NSStatusItem`'s native template-image
  auto-recolor to track the menu-bar's light/dark state — Windows' system
  tray has no equivalent auto-recolor primitive. The Windows re-skin must
  ship two pre-rasterized asset variants (light-taskbar, dark-taskbar) and
  select between them by reading the OS theme signal
  (`HKCU\...\Personalize\AppsUseLightTheme` or the WinRT `UISettings` theme
  API) via the `cfg`-aliased seam, not a trait (no mock needed — this is a
  pure asset-selection branch). The constraint invariant #1 imposes is
  unchanged by the theme swap: selection is driven **only** by the same
  `StatusState`/`BadgeState` vocabulary `render::glyph::treatment_for`
  already maps from — the theme swap changes which color asset is drawn,
  never which state is inferred. No new computed judgment is introduced.
- **`PlatformLoginItem` (per-user MSI, invariant #3 — never-destroy /
  never-orphan).** Folds into ADR-M9-005 below (packaging is a seam, not a
  trait — the never-orphan guarantee is a packaging-plus-watchdog property,
  discussed there alongside its owner-gated verification).

**Consequences:** Easier — a seam-by-seam auditable re-skin; macOS tests stay
green, unchanged, throughout. Harder — one careful refactor stream (Stream-B)
must prove behavior-preservation for the macOS thin wrapper; a reviewer must
check that no logic (not just syntax) moved.

**Alternatives rejected:** Big-bang dynamic-dispatch trait objects for every
seam (risks macOS regression, `dyn` overhead, an unverifiable Windows half);
leaving `cfg` scattered ad hoc with no `platform/` module (not auditable as a
re-skin — the exact drift invariant #2's "one signed binary, one codebase"
framing warns against).

## ADR-M9-002: Crash-only watchdog on Task Scheduler (resolves parity Q1, invariant #2)

**Status:** Accepted

**Context:** `windows-parity.md` §1 row 1 / §3 Q1: Task Scheduler's
"restart on failure" trigger is nominally `launchd`-shaped but has no
`ThrottleInterval`-style backoff, is trivially misconfigured as a "repeat every
N minutes" trigger (which IS the resurrect-always anti-pattern invariant #2
forbids), and cannot detect a hang — a hung process produces no non-zero exit
at all, so a pure exit-code trigger sees nothing to restart.

**Decision:** ONLY the failure-triggered restart trigger, with an explicit
retry cap, gated on the app's own exit code — a clean `Quit` (exit 0) is never
treated as a failure and is never restarted. Wired to the SAME
`updater::circuit_breaker` (ADR-M4-001's app-level launch-failure breaker,
reused unchanged) for the "N non-zero exits in a window → stop relaunching,
surface reinstall" guarantee, and hang-detected via the SAME
`updater::heartbeat` file contract (ADR-M4-002, reused unchanged) rather than
inventing a second liveness mechanism. **Never** the "repeat task every N
minutes" trigger — that is the anti-pattern, full stop.

**Resolves parity Q1 as:** design-resolved. The retry-interval and
heartbeat-timeout numbers this needs (owner-ratification-pending on macOS too,
per `updater::circuit_breaker`'s own module doc) are NOT independently
re-derived for Windows — same constants, same file, same reused logic. What
remains genuinely open is empirical: does Task Scheduler's failure trigger
behave crash-only under real-world conditions (including the hang case) on an
actual Windows box. That half is **owner-gated**, not designed-for.

**Consequences:** Easier — crash-only guarantee (#2) holds structurally by
construction (same reused breaker + heartbeat code, different OS-level
trigger feeding it). Harder — retry-interval/heartbeat-timeout tuning under
real Task Scheduler behavior needs a real Windows box; cannot be validated by
`cargo test` alone.

**Alternatives rejected:** Task Scheduler's "repeat every N minutes" trigger
(is the anti-pattern); a Windows service configured auto-restart-always
(violates #2 identically to a bare `launchd` `KeepAlive=true`).

## ADR-M9-003: Forced config refuse-unless-enrolled (resolves parity Q2, invariant #4 — hardest mapping) — REQUIRES @agent-sec SIGN-OFF

**Status:** Proposed pending @agent-sec review (not yet Accepted — flagged per
task 70's own instruction: "the two hard invariant decisions (#2, #4) FLAG for
@agent-sec sign-off"; #2 is ADR-M9-002 above, #4 is this one)

**Context:** `windows-parity.md` §1 row 3 / §3 Q2, the single hardest mapping
in the whole tracker. `HKLM\...\Policies` is administratively forced (a
standard user cannot write `HKLM`) but is **not** structurally distinct from a
merely-elevated local admin the way `CFPreferencesAppValueIsForced` is
distinct from a plain user-domain `defaults write` — on macOS, *only* an
MDM-pushed profile satisfies "forced," full stop, regardless of local admin
rights; on an unmanaged/BYOD Windows machine, a local admin can write
`HKLM\...\Policies` directly (`reg add`, `gpedit.msc` on Pro/Enterprise) and
nothing distinguishes that from "IT's MDM wrote this."

**Decision:** Treat `HKLM\Software\Policies\ENAC\ControlTower` as "forced"
**only** when the machine is domain-joined or MDM-enrolled (detected via
`dsregcmd /status` parsing or the MDM enrollment API), mirroring
`managed::forced`'s exact key-name registry
(`managed::keys::MANAGED_KEYS`) unchanged — same names, same
`forced_only`/`security_sensitive` flags. On a machine that is NOT
domain-joined/MDM-enrolled, fall back to the compiled-in trust root ONLY —
exactly the behavior `managed::forced::real_key_is_forced`'s
`#[cfg(not(target_os = "macos"))]` stub already has today (returns `false`),
just replacing "always false" with "false unless enrollment is confirmed."
Never read `HKCU` as forced (the Windows analog of "never honor the
user-domain value as forced").

**Resolves parity Q2 as:** design-resolved, matching the WP-52 draft's
recommendation exactly ("Recommendation to evaluate, not yet decided" in
`windows-parity.md` §3 item 2 — this ADR is that evaluation, ratifying it).
Enrollment-**detection correctness** (does `dsregcmd` parsing reliably detect
every enrollment state Intune/GPO can produce) is **owner-gated** — needs a
real domain-joined/MDM-enrolled Windows box; `cargo test` can only prove the
decision-logic branch (enrolled → read HKLM; not enrolled → compiled-in
default), the same way `managed/forced.rs`'s dev-seam
(`CT_FORCED_OVERRIDE_*`) proves the three `ForcedLookup` variants today without
a real MDM push.

**Consequences:** Easier — invariant #4's "honored only from the
forced/managed domain, never weakened" holds **structurally** on Windows, not
just nominally; a BYOD local admin cannot silently manufacture "forced" status.
Harder — one more FFI/API surface (`dsregcmd` output parsing or an MDM
enrollment API call) to get right, and it fails closed (treats ambiguous
enrollment state as "not enrolled" → compiled-in default) rather than
failing open.

**Alternatives rejected:** Trust `HKLM\...\Policies` unconditionally (a local
admin on BYOD defeats #4 exactly as an unmanaged `defaults write` would if
macOS didn't gate on `CFPreferencesAppValueIsForced`); require MDM enrollment
always, even to read the compiled-in default (breaks the graceful-default
parity macOS already has for an unmanaged machine with no profile at all).

## ADR-M9-004: Authenticode vs. notarize+staple gap (resolves parity Q3, invariant #4/#5)

**Status:** Accepted

**Context:** `windows-parity.md` §1 row 5 / §3 Q3. Notarize+staple gives a
deterministic, offline-verifiable trust decision at first launch. SmartScreen
is opaque reputation (download volume + EV cert reputation) — no staple
equivalent; a brand-new signed binary can still show the "Windows protected
your PC" interstitial until reputation accrues, and Microsoft doesn't publish
the threshold.

**Decision:** The cross-repo vendored-CLI signing contract (verify-not-resign
at a pinned SHA, "block release if the vendored CLI is older than the compat
floor" — `architecture.md` §7) ports directly: `signtool verify` replaces
`codesign`/`spctl`, same pinned-SHA-first shape, no re-signing. The updater's
pre-promote check (today: "stapled offline" per `updater::watchdog`) has no
staple to check on Windows — its Windows equivalent is **Authenticode
signature valid + version-monotonicity**, not a substitute staple check. For
air-gapped fleets (`design-distribution.md` §7's offline-Gatekeeper scenario),
recommend an **EV cert + an MDM-pushed SmartScreen allow-list policy**
(`SmartScreenForTrustedAppsEnabled`, or Attachment-Manager zone-identifier
stripping via GPO) rather than relying on reputation accrual, which cannot
work offline/air-gapped by definition.

**Resolves parity Q3 as:** design-resolved (a named, concrete recommendation
replaces "candidate, not yet decided"). The **offline-deterministic first-launch
guarantee itself is structurally weaker on Windows than on macOS** — this ADR
does not claim otherwise, and no design choice closes that gap; it only names
the best available mitigation. Whether the MDM-pushed allow-list actually
suppresses SmartScreen offline on a real air-gapped fleet is **owner-gated**
(needs an EV cert + a real fleet — `m9-owner-gated-split.md`).

**Consequences:** Easier — verify-not-resign guarantee preserved identically;
the compat-floor release gate needs no new logic, only a new verify command.
Harder — the residual "no staple equivalent" gap is real and is flagged, not
solved; a reader must not read this ADR as "Windows now has staple parity."

**Alternatives rejected:** Relying on SmartScreen reputation accrual alone
(non-deterministic, undocumented threshold, fails the air-gapped case
entirely — no phone-home path exists to accrue reputation offline).

## ADR-M9-005: Owner-gated vs. autonomous split (+ Q4 default posture, Q6 hardening checklist, MSI never-orphan)

**Status:** Accepted

**Buildable now, macOS-green, behind `cfg`:** the `platform/` consolidation
(ADR-M9-001), all 8 Windows seams C–H (crash-only Task Scheduler trigger
config, forced-domain refuse-unless-enrolled logic, Credential
Manager/DPAPI via `keyring`, tray light/dark asset selection, translocation-safe
install-path resolution, toast notifications wiring, self-update Authenticode
pre-promote check), MSI/winget packaging config (WiX, **per-user** —
`ALLUSERS` unset, matching the admin-free constraint `architecture.md` §7
states as hard), Authenticode signing scripts (authored, not run), and all
docs (this bundle, Stream-Z's verification matrix).

**Owner-gated (needs a Windows box / EV cert / real MDM console — the full
list lives in `docs/06-deployment/m9-owner-gated-split.md`, not restated
here):** Windows `cargo build`+`cargo test`, `signtool` execution +
SmartScreen behavior, real `dsregcmd`/GPO/Intune enrollment test (ADR-M9-003's
residual), DPAPI re-verification (ADR-M9-001's residual), MSI per-user
install + **uninstall-orphan test**, live tray theme-switch (ADR-M9-001's
residual), air-gapped SmartScreen allow-list validation (ADR-M9-004's
residual).

**Q4 resolved — notification force-enable centralization, conservative
default.** `windows-parity.md` §3 Q4 asks whether Intune/GPO can force
per-app notification permission the way the macOS `.mobileconfig`
notifications payload does. This cannot be answered from this machine — no
guess is offered. The **decision** (distinct from that unanswerable empirical
question) is a safe default per invariant #5's actor-competence routing:
**do not assume centralized force-enable exists on Windows**; treat the
notify-tier's fallback-to-IT-channel path as the Windows **primary** path,
not a fallback, until a real Intune/GPO test proves otherwise. This is
resolved as policy; the empirical capability question remains owner-gated.

**Q6 resolved — path/DLL-hijack hardening checklist.** `windows-parity.md`
§3 Q6 asks for a Windows equivalent of the translocation-safe-path
guardrail. Resolved as a design checklist (no live Windows box needed to
enumerate it): (a) resolve the vendored `copilot.exe`/`cc.exe` path via the
MSI-recorded install location (registry uninstall-key value or a compiled-in
path relative to the running executable), **never** a bare `PATH` lookup —
the direct Windows analog of "never invoke bare `copilot`"; (b) if this crate
ever dynamically loads a DLL (today: it does not — confirm this holds at
Windows-build time, don't assume), call `SetDefaultDllDirectories` restricting
search to `LOAD_LIBRARY_SEARCH_SYSTEM32 | LOAD_LIBRARY_SEARCH_APPLICATION_DIR`,
never load from the current working directory; (c) verify the vendored CLI's
Authenticode signature before invocation (ADR-M9-004's verify-not-resign,
applied at the same call site translocation-safety already occupies). Live
hijack-resistance testing (Process Monitor / a deliberately-planted decoy
binary earlier in `%PATH%`) is owner-gated.

**Per-user MSI never-orphan (invariant #3).** The macOS guarantee ("drag to
Trash doesn't orphan a login item," `architecture.md` §7, fixes B-H2) depends
on the watchdog polling its own `Program` path and self-`bootout`-ing if it
vanishes. The Windows design mirror: a scheduled-task self-check (does the
task's target executable still exist) triggers self-unregistration via the
same admin-free per-user Task Scheduler API a per-user task already uses to
register — no admin-elevated helper needed, by the same reasoning
`SMAppService.unregister()` needs none. Whether Task Scheduler genuinely
supports a per-user task deleting itself without elevation, and whether MSI
uninstall reliably triggers it, is **owner-gated** (the "MSI uninstall +
orphan test" item above) — this is a real gap `windows-parity.md` §1 row 11
already marks "Open-question" without a corresponding numbered §3 question
(a pre-existing doc gap, noted here, not newly introduced by this ADR).

## ADR-M9-006: Scope-realism cut

**Status:** Accepted

**Decision:** Implement full `cfg`-gated impls now for seams C–H (they exist,
are code-reviewable, and carry zero macOS blast-radius); **stub-and-document
only** where correctness genuinely needs live Windows behavior to get right:
(a) Task-Scheduler hang-timing tuning (the retry-cap/heartbeat-timeout
numbers ADR-M9-002 reuses from macOS as a starting point, not a validated
Windows-native value), and (b) the SmartScreen reputation/air-gapped
allow-list path (ADR-M9-004's residual). Everything else is worth writing in
full now — an owner inherits a **buildable start**, not a spec to re-derive
from scratch.

**Q5 — NOT resolved, blocked on an upstream open decision.**
`windows-parity.md` §3 Q5 (kiosk/shared-machine DPAPI machine-scope) is
explicitly downstream of the still-open macOS kiosk decision
(`architecture.md` §11 item 3 — "Kiosk/lab support depth: first-class
machine-credential path now, or defer"). Designing the Windows DPAPI
machine-scope equivalent before the macOS System-Keychain kiosk decision
lands would mean designing it twice, once on a guess. This ADR deliberately
does **not** manufacture an answer — Q5 stays open in `windows-parity.md`,
re-flagged as blocked (not owner-gated — no amount of Windows-box access
unblocks it; only the macOS architecture decision does).

**Verification boundary (honest, restated from the WP-52 draft this bundle
supersedes):** DoD here = macOS `cargo test` green + `fmt`/`clippy` clean +
Windows code proven `#[cfg(windows)]`-gated out (source-scan) + (if available)
a `windows-target cargo check`. **No Windows runtime/GUI/screenshot
verification is possible from this machine; no ADR above, and no task in this
milestone, claims a Windows behavior is verified.** Windows support is
**built-but-unverified-on-Windows** until Stream-Z's bring-up runbook is run
by a human on real hardware — see `docs/06-deployment/m9-owner-gated-split.md`.
