## Deliverable 1 — company protocol scaffold + OVERRIDE fold

Scaffolded `commands/protocol.md` in claude-copilot-internal (org, private): a 16-line HTML-comment + "Company overrides (ENAC)" heading block with three illustrative, non-invented override points, followed by the foundation protocol body kept byte-identical (verified via diff on every edit). Live-verified the fold mechanism is correct: `cc resolve --explain --json` shows `commands/protocol` winning_layer=claude-organization with claude-foundation correctly reported in `shadowed[]` — this only became visible after fixing a real cc defect (below); before the fix, `cc resolve` never discovered claude-foundation's content at all because it silently dropped `source.subpath` for any layer with an explicit `source.path` (the now-default "visible checkout" case).

Critical finding: live materialize (`cc update --json`) reports the org protocol.md as `blocked: reason=unverified`, and this is NOT a code defect — it is `cc`'s fail-closed signature policy (`policy.py`) working exactly as designed. `onboard.py` only ever populates `allowed_signers` for the FOUNDATION role; org/department/personal tiers always get `[]`. There is currently no established mechanism for the org tier to have a trusted signer, so EVERY executable-dimension item (agents/skills/commands/protocol/cli-integrations/plugins) contributed by the org tier is permanently blocked until a real org-signer-provisioning mechanism ships (a next initiative, per `docs/06-deployment/foundation-release-signing.md`'s own "Current status" note). This is not something I forced around, per the fail-closed HARD RULE.

Second-order consequence discovered late in the session: because OVERRIDE-dimension fold picks exactly one winning layer and never falls back to a shadowed layer when the winner is blocked, adding the org scaffold means `~/.claude/commands/protocol.md` is now FROZEN at its last-good (pre-session) content and will not receive new foundation updates to `protocol.md` either, until the org-signer gap is closed. Verified live: the machine's materialized file's sha256 no longer matches the checked-out foundation repo's current content. This is a real, inherent property of the existing fold+policy design, not a new bug, and it is the single root cause blocking BOTH Deliverable 1's "materialized live" claim and part of Deliverable 3's end-to-end verification.

cc fix shipped (genuine defect, unrelated to the above): `cc resolve --explain` failed to join `source.subpath` onto an already-explicit `source.path`, so it never discovered any visible-checkout foundation layer's content and always disagreed with what `cc update` actually does. Fixed in `resolve.py`'s `_synthesize_effective_layers()`, mirroring `update.py`'s existing subpath-join branch exactly. Regression tests added (join case + escape-path rejection). Shipped as cc 2.1.3.

## Deliverable 2 — project protocol precedence + never-destroy

2.1: Empirically tested Claude Code's real precedence for a same-named command (headless `claude -p`, isolated scratch project, controlled markers, real installed binary v2.1.220, HOME-preserving so auth still worked). Result, reproduced twice with an isolating control: PERSONAL (`~/.claude/commands/`) wins over PROJECT (`.claude/commands/`) for a same-named command — the OPPOSITE of what both the prior audit (Case 4) and this task's premise assumed. Confirmed against the current, live, official Claude Code docs (fetched fresh): "enterprise overrides personal, and personal overrides project." This directly threatens the owner's "project protocol supersedes both" requirement for the SAME filename, for any machine where a company/foundation protocol.md has already materialized into `~/.claude`.

Note this does NOT invalidate Deliverable 1 (company beats foundation): both of those tiers fold into the SAME single `~/.claude/commands/protocol.md` by cc's own resolver before Claude Code ever runs, so Claude Code is never choosing between two files there. It only affects the project-vs-machine case, which is a real, separate file Claude Code itself must choose between.

2.2: Found and fixed a real, serious never-destroy defect via live testing (real `cc update --project`, not just code reading): a project's `ownership: framework` file (e.g. `.claude/commands/protocol.md`) that a human customized and COMMITTED (clean tree, the ordinary git workflow) was silently overwritten — `result: applied`, zero hold. The only prior guard (`guard_personal()`) is a git-dirty-tree check that has nothing to see once the tree is clean. Fixed with a new `locally_modified_paths()` helper (checksum-drift vs. the project's own recorded checksum, independent of git status), wired into both the real materialize path and `project_freshness()`'s read-only preview so they can't disagree. Regression tests added for both. Verified live end-to-end (customize+commit -> real `cc update --project` -> held, byte-preserved; re-run after reverting to matching content -> applies normally). Shipped as cc 2.1.4.

2.3: Confirmed no code in `cc` parses or validates `commands/protocol.md`'s content — every code path treats it as opaque bytes (existence checks + sha256 hashing only, for activation, verification, and never-destroy tracking alike). A non-software project protocol.md (documents, PowerPoint, image creation) would be handled identically. The remaining open problem for a true non-software project override is entirely the Claude-Code-native precedence finding in 2.1, not anything in `cc`.
