Architecture verdict

Decision
Under the stated threat model, a fully automated first install is impossible. If a hostile process already controls the publisher user's mutable checkout, package paths, and user session, and there is no previously installed trusted helper or independently controlled package-signing path, every local automation program that attempts to establish first trust is itself inside the adversary's boundary. Hashing itself, authenticating a different materialized script, chmod 0444, a read-only mount, or asking for administrator authorization does not change that fact.

TASK-287 must stop before signing, installation, or candidate authority. WP-812 remains useful as a package construction and source-verification prototype, but it cannot be the first-trust mechanism. Automation may begin only after one externally trusted, owner-attended provisioning ceremony establishes a root-owned anchor and anti-rollback policy.

Why the bootstrap cannot close itself
- Authenticated Git commit/tree bytes prove source identity only if an already trusted executor makes the authority decision. In WP-812, control returns to mutable checkout code before credentials and signing authority are used.
- A same-user process can replace a user-owned package pathname after verification. Mode 0444 protects file contents, not its directory entry.
- A package cannot embed its own final signed-package SHA-256 without a self-reference. The final package digest therefore needs an independent signed manifest or previously protected policy ledger.
- Apple package/application signatures prove signer and byte integrity, not that this is the exact ref, commit, tree, version, or package the owner intended today.
- Notarization proves Apple accepted a developer-signed artifact for distribution; it is not authorization, source provenance, freshness, or downgrade prevention.
- Installer receipts record package identity/version and installed payload facts, but they are not an external expected-package digest/source policy and must not be treated as general downgrade prevention.
- Administrator password or Touch ID authorizes elevation. It does not bind the elevated operation to reviewed bytes.
- A signed read-only DMG can make the selected mounted bytes stable, but does not prevent selection of a different validly signed or older DMG and does not establish source intent.
- An exact digest displayed or consumed by code in the compromised user session is not independent. Owner confirmation becomes meaningful only when the expected value arrives through an independent channel and the approved bytes are then staged where the hostile UID cannot replace them.

Independent inputs evaluated
1. Existing root-owned approval ledger: potentially useful, but insufficient alone. This Mac currently has a root-owned schema-1 ledger binding remote/ref/commit/tree 7a3b227d05ddc950737eaf8ed26c83c1a8ee4667 / 448bf828964aaa9272d5a83ba6276397ce2b9e9e. It contains no package identifier, monotonic version, final package digest, app CDHash, or bundle digest, and no protected anchor currently exists at the canonical root-only path. It can be retained as source-intent evidence only if the owner accepts its prior ceremony/provenance. The candidate package must never overwrite it before independent comparison and successful verification.
2. Developer ID Installer signature: necessary and strong only when the Installer private key is held or exercised outside the hostile user's control and signing policy admits only the reviewed intent tuple. No such identity is currently available, so no authoritative install package can presently be produced.
3. macOS Installer receipt/version: useful post-install corroboration. Require stable package identifier, strictly monotonic version, matching receipt, and installed payload verification, but never use receipt/version as the sole expected-source or anti-rollback authority.
4. Notarization/staple: required distribution evidence, not an owner-intent or freshness oracle.
5. Owner-attended exact digest: viable as the unavoidable first-install authorization if the expected digest and intent tuple come from an independent channel and the package is copied to root-owned staging before the digest is checked and consumed. A digest copied from the mutable checkout's own output is not viable.
6. Signed read-only DMG: optional transport hardening only. It reduces in-place mutation after mount, but cannot replace the independent digest/version/source authorization.
7. Hardware/admin authorization: [REDACTED:generic-secret-assignment] for protected placement, but not sufficient for byte authorization.
8. Postpone automation: required if the independent signer and owner-attended authorization cannot be provided. This is the current honest disposition.

Chosen first-install authority flow
Define one reviewed intent tuple:
- canonical remote and immutable ref
- exact 40-character commit and tree
- package identifier and strictly monotonic package version
- application bundle identifier and Team ID
- application CDHash and deterministic bundle digest
- final signed-package SHA-256

The feasible route is:
1. Review and freeze the exact source intent tuple. A mutable branch name alone is never authority.
2. On an independently trusted signing environment, not the hostile publisher account/session, materialize the exact Git commit/tree, build the script-free payload, verify its closed BOM and embedded source/app receipt, and sign it with the separately controlled Developer ID Application and Developer ID Installer identities. Notarize and staple it.
3. Produce an external release-approval manifest binding the complete tuple including final signed-package SHA-256. Sign that manifest with an independently controlled release-approval key, or have the owner record/approve the exact tuple through an out-of-band trusted channel. The Installer package signature covers the embedded payload receipt; the external manifest supplies the non-self-referential final package digest and freshness decision.
4. During the attended ceremony, obtain the expected tuple independently of the candidate checkout. Use only macOS system tools or a separately provisioned trusted bootstrap to copy the package into a root-owned, non-group/world-writable staging directory. Compute the digest after the copy from that protected path, compare it with the independently approved digest, verify Installer signer/package identity/notary and extracted payload/source tuple, then invoke /usr/sbin/installer on that same protected path.
5. Immediately verify the real installed state against the independently approved tuple: complete root-owned ancestry, package receipt identifier and monotonic version, app designated requirement/Team ID/CDHash/bundle digest, and embedded source ref/commit/tree. Do not accept a merely self-consistent installed app and adjacent receipt.
6. Only after all checks pass, atomically write or advance a separate root-owned authorization ledger recording the approved tuple and minimum accepted package version. Never let the package payload replace this policy ledger before comparison. On failure, preserve the previous anchor and ledger.
7. Only then may the installed root-owned anchor load release credentials or create a Control Tower candidate. Future updates can be automated by this established anchor: verify a separately signed manifest, enforce the version floor, stage exact bytes root-only, install, post-verify, and advance the ledger.

Exact downgrade/substitution rules
- Reject package B even when signed by the same Apple team if its SHA-256, version, source ref/commit/tree, app CDHash, or bundle digest differs from the independently approved tuple for package A.
- Reject version <= the root-owned minimum unless a separately authorized rollback tuple explicitly names that exact prior signed package and digest. A generic same-team rollback is forbidden.
- Never use a mutable package path between verification and Installer consumption; consume only the root-owned staged object whose post-copy digest was approved.
- Preserve the policy ledger outside package payload replacement. Package-carried provenance is evidence, not policy.
- A fresh machine has no local version floor, so preventing installation of an older still-valid package necessarily requires an external freshness decision: an owner-approved exact digest/version or a trusted signed current-release manifest. There is no purely local solution.

Minimal trusted computing base
- macOS kernel/filesystem ownership and root separation
- Apple Security.framework/codesign, Installer/pkgutil, Gatekeeper, and notarization verification
- independently controlled Developer ID Application and Installer private keys
- the independent release-approval manifest key or owner-controlled out-of-band digest channel
- the small root-owned staging/verification mechanism used for the first ceremony
- the root-owned authorization/version-floor ledger after successful provisioning

Explicitly excluded from the trusted computing base: the repository checkout shell, user-owned output directories, chmod 0444, mutable Git refs, package-evidence.json beside the package, the notary ticket alone, a DMG mount alone, and any candidate self-verifier before external authorization.

Unavoidable external provisioning and blocker
At least one of these must exist before first-install automation is possible:
- an independently built and Developer ID Installer-signed package plus an owner-attended root-staging/digest ceremony;
- a separately preinstalled trusted bootstrap/helper;
- or an equivalent organization provisioning authority.

MDM is rejected by the product's ratified scope, and no preinstalled helper or Developer ID Installer identity exists. Therefore the selected route is the first option, and it is presently blocked on acquiring/provisioning the Developer ID Installer identity in an independent trusted signing context and on owner-attended approval of the exact package digest/source tuple. If those cannot be supplied, postpone automation. Do not attempt another circular local provisioner.

Implementation and verification boundary after unblock
- Architecture/implementation must separate immutable package provenance from the non-overwritable root policy ledger.
- Package versions become monotonic and are included in every pre/post check.
- Add same-team A/B substitution and downgrade tests where B is cryptographically valid but differs from approved A; B must never become authority.
- Add a race test proving user-owned A can change without changing the already staged root-owned object.
- Real evidence must cover Installer identity, package/notary/staple, receipt/version, protected staging, installation failure preservation, installed app/ledger identity, and explicit rollback authorization.
- Route any new implementation to $me, then fresh $qa and $sec. No app candidate may be created from source-only evidence.

Disposition
Security-posture-never-weakened and SOUL's say-only-what-you-can-prove rule require an honest block. TASK-287 remains in progress and candidate-blocked. No local code change can remove the need for the independent signer/owner ceremony.
