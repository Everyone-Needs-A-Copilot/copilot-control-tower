### Defect found + fixed: `cargo test --release --lib` had 35 failures

Going one step further than the WP's literal ask (which specifies `cargo test`,
not `cargo test --release`), I ran the full suite under `--release` too and hit
**35 failures**, all across `cli::path`, `commands::wizard_ipc_tests`/
`settings_ipc_tests`, `settings::config_pointer`, and `wizard::managed_flow` —
every test anywhere in the crate that relies on the `CT_CLI_PATH` dev override
to redirect at `mock-cc`.

**Root cause:** M1's own QA pass (T9/D1) fixed a release-profile clippy failure
by widening `DEV_OVERRIDE_ENV`'s gate from `#[cfg(debug_assertions)]` to
`#[cfg(any(debug_assertions, test))]` — but only the **constant**, not
`dev_override()`, the function that actually reads it, nor `resolve()`'s call
site gating it. Both were still bare `#[cfg(debug_assertions)]`. `cargo build
--release`/`cargo clippy --release` never noticed because neither compiles test
code — so this has been a **latent bug since M1**, invisible because neither M1
nor M2 QA ever ran `cargo test --release` (confirmed by grep against both prior
acceptance reports).

**Fixed** (`src-tauri/src/cli/path.rs`): widened `dev_override()`'s own gate and
`resolve()`'s call-site gate to `#[cfg(any(debug_assertions, test))]`, matching
the constant. Re-verified: `cargo test --release --lib` now **240/240** passing
(240, not 239 — the one extra is `timer::tests::release_cadence_is_one_hour`,
a pre-existing, correctly `#[cfg(not(debug_assertions))]`-gated M1 test that
only runs under `--release`, unrelated to this fix). Re-ran clippy (both
profiles), fmt, and the full debug `cargo test` after the fix — all still clean.
Re-ran the release-binary `strings` scan after the fix — still **0** hits for
`CT_CLI_PATH`/`dev_override`, confirming the widened gate does not reintroduce
the override into a genuine shipped `cargo build --release` artifact (that
build has no `cfg(test)` either way).

**Residual, not fixed, non-blocking:** `cargo test --release` (all *targets*,
not just `--lib`) still fails one test —
`fitness_signin_seam_holds_no_secret::adversarial_leaked_field_never_survives_the_public_seam_end_to_end`.
This is a **structural Cargo limitation**, not a bug: `cfg(test)` is only set
when a crate is itself compiled with `--test`; an external integration-test
binary links the lib as a plain dependency, where `cfg(test)` is never true —
so no widening of the library's own gate can make this specific
release+external-integration-test combination work. The **actually-specified**
verification path — default (debug) `cargo test`, run 3× — is 100% green,
including this exact test (6/6 passing in `fitness_signin_seam_holds_no_secret`
every run). Noted for awareness, not release-blocking.

## 2. The cardinal invariant — no false-Healthy during setup

Read `wizard/state.rs`'s `transition()` directly: it is a single exhaustive
`match` with **no wildcard success arm** — `Done` is reachable from exactly one
call, `(Teach, TeachAcknowledged) -> Done`, and `Teach` is reachable from exactly
one call, `(Verify, Verified(status)) if status.is_healthy() -> Teach`. Every
other `Verified(status)` value routes to `Holding(VerifyFailed)`, proven for
**every** `CliStatus` variant (`verify_non_healthy_status_holds_never_completes`
loops `SignedOut/NeedsAttention/Offline/SetupNeeded/Syncing/UpdateAvailable/
ItConfigIncomplete/WaitingForNetwork/UpdatingApp`, asserting `!= Teach` and
`!= Done` for each). `done_is_unreachable_without_a_verified_healthy_event`
drives `TeachAcknowledged` from every other phase and asserts `Err`.

Live-wired proof, not just the pure state machine: `managed_flow.rs`'s own test
suite drives the **real orchestration** (`run()`) against actual doctor-body
fixtures via a local mock `cc`:
- `signed-out-claude-personal.json` → `Holding(VerifyFailed)`, never Done.
- `waiting-for-network-startup.json` → the dedicated `Holding(WaitingForNetwork)`.
- `invalid-missing-required-field.yml` managed profile → immediate
  `Holding(ItConfigIncomplete{key:"auth"})`, **never even touching the CLI**
  (confirmed no `CT_CLI_PATH` set in that test — the schema-validate-first gate
  really does short-circuit before any spawn).
- An absent profile → retries across the settling window, then holds with
  `PROFILE_ABSENT_KEY`.
- An unreachable CLI (`/nonexistent/...`) → `Holding(EngineUnreadable)`, never a
  crash, never Done.
- A valid profile + `healthy-clean-fleet.json` → the only fixture that reaches
  `Done`.

`support::drive_verify` (shared by both managed and unmanaged flows) is the one
place `Verify`'s outcome is mapped from a fresh `RenderState` — its own tests
cover Healthy→Done, WaitingForNetwork→dedicated holding, any other status→
generic `VerifyFailed`, and `ClientState::CliUnreadable`→`EngineUnreadable`,
never Done. **PASS**, no path found to fabricate Healthy.

## 6. Never-destroy / resume — DEFECT: resumability is not actually wired

Everything ADR-M3-004 promises is real and correctly implemented **as a unit**
in `wizard/persistence.rs`: `save_checkpoint`/`load_checkpoint`/`resume_phase()`
all pass their own tests, including
`an_interrupted_run_resumes_at_materialize_with_its_answers_intact` (checkpoint
survives a simulated relaunch, lands back at `Materialize` with the same
answers, never re-enters `Question`) and
`a_checkpoint_write_preserves_unrelated_config_keys` (a checkpoint write leaves
`paths.*`/`layers.*` byte-identical). `mark_complete` correctly refuses every
phase except `Done` (`mark_complete_refuses_every_phase_except_done`).

**But grepping the whole crate for call sites outside `persistence.rs`'s own
`#[cfg(test)]` module turns up zero.** `save_checkpoint` is never called from
`managed_flow.rs`, `unmanaged_flow.rs`, `commands.rs`, or `lib.rs`,  and
`WizardIpcState::new()` (`commands.rs`) unconditionally constructs
`WizardRuntime::NotStarted { mode }` — it never calls `load_checkpoint()`/
`resume_phase()` at all. There is also no `UnmanagedFlow::resume(...)`
constructor anywhere — only `UnmanagedFlow::begin(...)`, which always starts
fresh.

**Practical effect:** if Bob quits mid-guided-setup (say, right after answering
ChooseProducts+LayerSetup, before finishing SignIn) and relaunches, `is_first_run()`
correctly still reads `true` (so the wizard re-opens — no false "already done"),
but the guided flow **restarts from ChooseProducts**, not from wherever he left
off. This doesn't corrupt anything (the personal-tier layers already written to
`copilot.layers.yml` by the prior `set_layers` call are preserved byte-for-byte
by the M2 never-destroy writer, and re-answering the same questions just
re-writes the same rows) — so this is **not** a never-destroy violation in the
narrow sense of "clobbers existing config" — but it directly fails the QA task's
own explicit check #6 ("an interrupted wizard resumes at the right phase") and
ADR-M3-004's stated design. **Reporting, not fixing** — reconstructing a live
`UnmanagedFlow` (which needs the catalog + manifest path + in-flight sign-in
session, not just a `WizardPhase`) from a checkpoint is real orchestration
design work, not a "small/safe" QA patch. **Route to @agent-me** (wire
`load_checkpoint()`/an `UnmanagedFlow::resume()` constructor into
`WizardIpcState::new()`, and call `save_checkpoint` after each step-driver IPC
call) or **@agent-ta** if the reconstruction needs a design decision first
(e.g., whether SignIn's in-flight ceremony can survive a relaunch at all, or
must always restart that one step).

## 7. Managed silent progress — DEFECT: live phase updates never actually stream

The progress-spectator UI (`buildProgress` in `render/wizard.ts`) is real,
correct, and renders every intermediate phase fixture cleanly (confirmed live,
§8: `ui-progress-managed-checking`, `ui-progress-managed-setting-up-claude`).
But tracing the **live wiring**: `commands::advance_wizard_runtime`'s managed
branch calls `wizard::managed_flow::run()` as **one single, synchronous,
blocking call** inside `spawn_blocking` — it internally loops through
Detect→Materialize→Verify→Teach→Done (potentially minutes, given
`materialize::run_materialize`'s 600s timeout) and returns only the **final**
phase. `wizard-main.ts`'s `runTauri()` calls `WIZARD_ADVANCE_CMD` exactly once
for a managed run (line ~145) and awaits that one promise — there is no
intermediate `get_wizard_state`/poll loop for the managed phase (unlike
sign-in's own `startSigninPoll`), and grepping the whole crate for `.emit(`
inside `wizard/`/`commands.rs` turns up **zero** hits — no Tauri event is ever
pushed. `capabilities/wizard.json`'s own doc even says so explicitly: "No
`core:event:allow-listen`... this is a get-on-open, drive-one-step-at-a-time
surface with no live push event to subscribe to."

`materialize.rs`'s own module doc claims "S6 forwards these as `wizard-phase`
events" — **this claim is false**; no such forwarding exists anywhere in the
landed code. It appears S6/S8 walked back the live-event design in favor of a
single blocking call (simpler, avoids widening the capability grant) without
updating that doc comment.

**Practical effect:** during a real managed silent first-run, Bob does not
actually watch phase names update live — he sees an initial render, then the
whole window is unresponsive to any state change until the entire
Detect→Materialize→Verify sequence finishes (up to ~10+ minutes for a real
`cc update`), at which point it jumps straight to the final Done/Holding
screen. The "Silent First Light" spectator experience the WP/S7 describe is
real UI code that the live product never actually drives with intermediate
data. **Not a trust violation** (no false progress is shown — nothing is shown
mid-run, which is honest, just not what was designed) but a genuine product
gap. **Reporting, not fixing** — closing it needs either (a) restructuring
`managed_flow::run()` into stepwise, IPC-polled phases (mirroring
`UnmanagedFlow`'s own incremental-step design) or (b) widening
`capabilities/wizard.json` to grant event-listen and having `managed_flow::run`
emit `wizard-phase` events — both are real architecture decisions, not a QA
patch. **Route to @agent-ta** (decide which of the two approaches) then
**@agent-me** to implement.

## Verdict

**M3 = ACCEPT-WITH-FOLLOWUPS.**

The cardinal promise — the icon cannot fabricate Healthy during setup, and the
app never holds a secret — held under sustained adversarial pressure across
both the pure state machine and the live-wired orchestration: every non-Healthy
doctor fixture, every malformed/absent managed profile, every unreachable-CLI

honest state, never a guess. Capability scoping is exact, the fixture corpus is
clean and self-validating, and the headless UI sweep confirms all 19 wizard
states render correctly with zero console/CSP violations and no ETA/celebration
string anywhere. One real, latent-since-M1 test-infrastructure bug (D1) was
