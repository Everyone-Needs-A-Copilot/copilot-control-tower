Finding SEC-1 — CRITICAL — verified source is mutable before authority-bearing execution
Exploit path:
1. The complete verifier authenticates the current no-.git materialization by path and returns successfully.
2. That materialization remains owned and writable by the publisher account. No file descriptor, content digest, root-owned snapshot, code signature, or other durable binding is carried from verification into execution.
3. The provisioner then exports publisher HOME/USER/LOGNAME, sources the authority file, and executes `$(pwd -P)/scripts/build-publisher-bootstrap.sh` from that same mutable tree. It later executes `$(pwd -P)/scripts/verify-publisher-bootstrap.sh` while the sourced authority environment is still inherited.
4. A concurrent same-user process can replace either script after its path was verified. Replacement build code can consume signing/notary authority, alter the anchor, sign/notarize attacker-selected same-team code, or expose authority. Replacement post-install verification can falsely approve an installed result and consume inherited authority.
Evidence:
- Static order gate: complete verifier < HOME/USER/LOGNAME export and authority source < mutable build-script execution < mutable post-install verifier execution.
- Current materialization and both scripts are uid 501 and writable by the publisher account.
- WP-804's hostile-startup test proves startup isolation but does not race or mutate a verified path after verification.
Impact: the core claim that authority appears only to exact immutable reviewed source is not established. An attacker can cross from user-writable bytes into Developer ID/notary authority and can cause a malicious same-team Publisher Bootstrap to become signed, notarized, and eligible for protected installation.
Required mitigation: do not execute any path from the verified user-writable materialization after authority becomes reachable. Carry exact authenticated bytes across the boundary through a non-replaceable mechanism. Examples include a small independently trusted launcher that fetches/verifies and executes authenticated code from protected storage, or an attended root step that copies the exact approved tree into a root-owned no-ACL/no-write snapshot, verifies its full tree again, and only then starts the authority-bearing publisher program from that protected snapshot. Bind the executing script/binary itself, all invoked helper source, and the post-install verifier. Add a deterministic post-verification replacement regression that proves replacement bytes cannot execute or approve state.

Finding SEC-2 — HIGH — root-stage app copy is not bound to the user-verified candidate
Exploit path:
1. The signed/stapled app is held below the caller-writable provisioning scratch directory until the administrator prompt.
2. Root copies that pathname into its private stage. Approval JSON is digest-bound, but the app bundle has no digest/CDHash binding passed into the privileged transaction.
3. Root runs only generic `codesign --verify --deep --strict`, `spctl`, and `stapler validate`. It does not enforce the exact Team ID and bundle identifier and does not compare the copied candidate to a pre-prompt digest or code-directory hash.
4. A concurrent same-user process can swap the supplied bundle for another valid notarized Developer-ID bundle, or a previously valid same-team/bundle build. Generic root checks accept it. The later verifier may reject a foreign identity, but installation has already occurred; an older same-team/bundle build can pass identity verification because no exact candidate binding exists. SEC-1 also permits replacing the post-install verifier.
Evidence:
- Exact privileged template contains no `--test-requirement` and no Security.framework equivalent.
- It hashes only `approved-source.json`; no verified.app content digest, CDHash, or designated requirement is bound to the root copy.
- The supplied app glob only establishes that the pathname is beneath the provisioning root, not that its bytes are the candidate verified before prompting.
Impact: root may install bytes other than the exact signed/notarized candidate the publisher reviewed, violating the protected trust-root transaction. Combined with SEC-1, malicious same-team code can persist as the canonical authority.
Required mitigation: before prompting, compute an exact candidate binding from the verified signed app; pass it as quoted positional data; after root copy, compare the root-stage app to that binding and enforce the exact Team ID and bundle identifier with `codesign --test-requirement` or Security.framework strict/all-architectures validation before any destination mutation. Prefer a signed manifest covering the complete bundle or an exact designated requirement plus a stable CDHash/executable/resource-envelope binding. Add substitution regressions for foreign notarized and older same-team/bundle candidates.

Finding SEC-3 — MEDIUM — privileged destination ancestors are not fully validated before mutation
Exploit path:
- The root script checks /Library/PrivilegedHelperTools owner and mode bits but does not reject an extended ACL there before backup/install/rollback operations.
- It does not lstat/type/owner/mode/ACL-validate the complete approval ancestor chain before mkdir, cp, and recursive chown/chmod.
- If an unsafe pre-existing ACL or redirected approval component exists, root follows that state during mutation. Post-install verification detects many unsafe final states, but detection occurs after privileged writes and rollback traverses the same insufficiently established paths.
Observed machine state: the reviewed current ancestors are root-owned and not group/world writable, and `ls -lde` showed no extended ACL marker. This is therefore a fail-closed deficiency rather than an observed active exploit on this Mac.
Required mitigation: in the privileged script, lstat every canonical and approval ancestor before mutation; require exact directory/file type, root ownership, no group/world write, no publisher effective write where meaningful, and no extended ACL. Reject symlinks and unexpected pre-existing objects. Repeat the checks after install and before rollback operations. Avoid recursive ownership changes until the complete target chain is established.

Abuse-case conclusions
- Hostile Python/shell startup or caller TMPDIR can influence pre-verification execution: NO; WP-801 SEC-1/SEC-2 direct vectors are closed.
- HOME/USER/LOGNAME retroactively influence the complete verifier: NO. They are exported afterward.
- Exact immutable bytes remain bound to all later authority-bearing execution: NO; SEC-1 is a critical TOCTOU boundary failure.
- Dynamic argv becomes privileged shell source: NO in bounded exact-template tests.
- Approval bytes can change unnoticed before root use: NO; their copied digest is checked.
- Candidate app bytes can change unnoticed before root use: YES; SEC-2.
- Rejected bytes are followed, quarantined, imported into PHT, or restored on rollback: NO in bounded exact-template and stress tests.
- Root destination ancestry/ACL state is fully fail-closed before writes: NO; SEC-3.
- Untrusted bytes can become executable or enter PHT: YES through SEC-1/SEC-2; the intended fixed adapter/anchor path otherwise rejects unsafe installed state.
