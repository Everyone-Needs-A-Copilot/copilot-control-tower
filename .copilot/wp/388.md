# Why wizard step 6 "Your connections" is empty — consumer-first trace (read-only)

**Date:** 2026-08-02. **App:** Control Tower 0.3.2, bundled helper `cc 2.1.2`. **Source helper:** `cc 2.1.5` (`/Volumes/Dev/Sites/COPILOT/claude-copilot/tools/cc`). **Machine:** ecosystem live at 16/16.

**Verdict in one line:** (b) mechanism gap + (c) defect. Not a content gap. The org's integrations already exist in a machine-readable, `requires_secret`-shaped declaration that `copilot --json layers` emits live today — and nothing in `cc` or Control Tower ever asks for it. On top of that, the one stage that *does* touch shared credentials calls a `copilot` subcommand that does not exist, so it can only ever return `deferred`.

## 1. THE SCREEN — the step is hardcoded, it has no data source at all

`native/wizard.swift:4547-4593` (`integrationsView`) is a static view. There is no list, no `ForEach`, no DTO, no model property behind either card:

- `4554-4576` "Ready to use" is a single literal `Text("GitHub")` card whose only dynamic value is `model.authorizedLogin` (`native/wizard.swift:921`, set from `AuthStatus.identity.login` at `1546` / `1666` / `1858`).
- `4578-4583` "Available to connect" is a literal `Text("No additional organization connections are available in Control Tower right now.")`. There is no branch that could ever render anything else.

This is deliberate and documented in the file header at `native/wizard.swift:29-32`:

> "Your connections (step 6) stays render-only until the CLI exposes an organization-scoped connections contract. It shows the GitHub connection established in step 2 and an honest empty state for additional connections; it never advertises providers that the organization has not made available."

The same holding pattern exists on the two sibling surfaces:
- Settings → "Your connections" (`native/user-settings.swift:444-445`, `615-647`) renders only GitHub, driven by `model.authState` (the `auth` verb), nothing else.
- Admin → Review → "Published integrations" (`native/admin-support.swift:2023-2030`) renders "None published yet." behind an explicit comment: *"CONTRACT SEAM: no seam reads per-repo registry manifests yet (admin-standup-contract.md §5)."*

**DTO layer:** `native/cli-dtos.swift` has no connection/integration type. `connectionState` (`cli-dtos.swift:629`) is per-*repository* reachability, and `integrationPaths`/`integrationPlan` (`855`, `940`) are *project* integration (whether a workspace has its `.claude`/`.codex` files) — a different sense of the word entirely. There is no `connections` decoder because there is no `connections` payload.

**Schema layer:** `docs/01-architecture/schemas/` has ten schemas (`auth`, `doctor`, `layers`, `freshness`, `update`, `onboard`, `projects`, `workspaces`, `resolve`, `deprovision`, `repair`, `publish`). There is no `connections.schema.json` and no connections section inside any of them.

## 2. THE VERB — the closest thing is one `secret-store` *stage*, and it is a device-identity provisioner, not an enumerator

The only connections-adjacent emitter in `cc` is `_provision_store` (`claude-copilot/tools/cc/src/cc/commands/onboard.py:2067-2127`), appended to the report as `{"stage": "secret-store", ...}` at `onboard.py:2870-2871`.

Its input is `handoff.get("store")` (`onboard.py:2869`) — the `store:` block of the org's `ecosystem.yml`, fetched from GitHub by `_load_handoff` (`onboard.py:637-668`) out of `<org>/<product>-copilot-internal/ecosystem.yml`, `schema_version: "2.0"`.

Its output shape is `{result, type, scope|detail}` — a single verdict about whether *this Mac* got a read-scoped Infisical machine identity. It never enumerates anything. **Confirmed by exhausting the handoff's consumed key set:** `handoff.get(...)` appears exactly seven times in `onboard.py` — `schema_version` (`651`), `org` (`655`), `harness` (`650`), `components` (`2678`), `foundation.refs` (`1373`), `departments` (`712`), `store` (`2869`). There is no `integrations` and no `connections` key anywhere in the contract.

That absence is by design, and the design says exactly where integrations were relocated to. `docs/01-architecture/admin-standup-contract.md:162`:

> "No `integrations` block (the admin declares none; existence lives in per-repo registries, §5)."

and `admin-standup-contract.md:440-442`, the v1→v2 supersession table:

| Removed from v1 | Superseded by |
|---|---|
| `integrations:` (per-layer declarations + `requires_secret` + `store_scope`) | The **per-repo integration registry manifest** (§5), gated by entitlement. |

### The shape the design requires (`admin-standup-contract.md:447-499`, §5)

- **Location:** `integrations.registry.json` at the **root of that layer's CLI Copilot component repo** — org: `<org>/cli-copilot-internal`; dept: `<org>/cli-copilot-<unit>`. One registry per layer, never per component.
- **Schema** (`schema_version: "1.0"`): `{schema_version, integrations: [{id, name, description, requires_secret, store_scope, introduced_by}]}`.
- **Publish semantics** (`:486`): presence on `main` = published, absence = non-existence. No flag, no tombstone.
- **Consumer contract** (`:490-496`): the user-face app renders the **union** of registries across repos the user has GitHub read on; the admin app renders the same union read-only.

**So the design's answer to "where must a connection be declared to appear available" is unambiguous — and no verb implements the consumer side of it.** `grep -rn "integrations.registry" claude-copilot/tools/cc/src` returns nothing. The only `cli-integrations` hits in `cc` (`core/ecosystem/dimensions.py:32`, `materialize.py:93`, `policy.py:26`) are a *materialization dimension* — a directory of files to copy — not a registry read.

## 6. VERDICT

**(b) mechanism gap, compounded by (c) a defect. Explicitly NOT (a) a content gap — with one caveat.**

1. **Mechanism gap (primary).** The design's consumer contract (`admin-standup-contract.md:490-496` — "renders the union of registries across the repos the user is entitled to") was never implemented on either side. No `cc` verb reads `integrations.registry.json`; no `connections.schema.json` exists; no Swift DTO exists; the view is hardcoded with a documented holding comment (`wizard.swift:29-32`). Even if the owner committed a perfect registry this afternoon, **the screen would still say "No additional organization connections are available."** Nothing would change.
2. **Defect (secondary, independent).** `secret-store` always defers because `copilot infisical identity provision` does not exist. Fixing #1 without fixing #2 would list connections that can never resolve their secrets on this Mac.
3. **Content caveat (tertiary).** The org's declarations live in `cli.overlay.yml` in the *tier-inheritance* shape, not in `integrations.registry.json` in the *§5 registry* shape, and `ecosystem.yml:21 team_scopes` is empty. So there is also a real content delta — but it is downstream of #1 and pointless to close first.

**Foundation clause: verified, with a nuance.** GitHub is genuinely the hardcoded minimum, but not because "foundation declares zero integrations" — it is because GitHub is never a declaration at all. It is a hardcoded card (`wizard.swift:4561`) over a structural precondition (`gh`, device SSH, `github_app.client_id`). And the foundation repos are genuinely bare: `cli-copilot` has no `cli.overlay.yml`, and all 20 live services are attributed `tier: org-internal`. The 12 `adopt` entries are the interesting nuance — their *code* lives in the foundation, but their *activation and config* are org-tier, which is why they read as org.

## 7. WHAT WOULD MAKE THEM APPEAR — the prescription

**Preferred: publish `cli.overlay.yml` through the projection that already exists (parse-never-compute, minimal new surface).**

The bridge belongs in `cc` (the app must stay a thin skin, invariant #1) and the source of truth stays in CLI Copilot (invariant: no resolution logic in the app). Three changes, smallest-first:

1. **CLI Copilot (`cli-copilot` foundation, `copilot_cli/config/layers.py` + the `layers` emitter):** add `requires_secret: [NAME…]` and `store_scope` to each row of the existing `services[]` projection in `copilot --json layers`. The data is already parsed (`load_tier_overlay` at `layers.py:465-495` builds `OverlayAdopt.requires_secret`); it is simply dropped from the output. **Names only, never values** — the §5 secret invariant holds unchanged.
2. **`cc` (`claude-copilot/tools/cc`, new `cc connections --json`, or a `connections[]` section on `onboard`):** shell `copilot --json layers`, take `services[]`, and emit one row per service with `{id, name, description, tier, mode, requires_secret[], secret_state}` where `secret_state ∈ {ready, needs-connect, no-store}` — computed by `cc` from the `secret-store` stage plus a keychain/store probe, never by the app. Publish `docs/01-architecture/schemas/connections.schema.json` alongside it. `cc` already shells `copilot` twice (`onboard.py:1987`, `2081`), so this is not a new trust boundary.
3. **Control Tower (`native/wizard.swift:4547-4593` + `native/cli-dtos.swift`):** replace the two literal cards with `ForEach` over the decoded rows — `secret_state == ready` into "Ready to use", everything else into "Available to connect" with a Connect button that calls the CLI. Delete the holding comment at `wizard.swift:29-32`. Mirror it in `user-settings.swift:615` and `admin-support.swift:2023`.

**Alternative (design-literal, if the ratified §5 registry is to be honored as written):** commit `integrations.registry.json` at the root of `Everyone-Needs-A-Copilot/cli-copilot-internal`, and have `cc` read it via `gh api repos/<org>/cli-copilot-internal/contents/integrations.registry.json` (same call `_load_handoff` already makes for `ecosystem.yml`, `onboard.py:627-634`), unioned across entitled layer repos. Two concrete entries from the owner's real data:

```json
{
  "schema_version": "1.0",
  "integrations": [
    {
      "id": "coolify",
      "name": "Coolify",
      "description": "Coolify infrastructure management.",
      "requires_secret": "COOLIFY_API_KEY",
      "store_scope": "org/shared",
      "introduced_by": "Everyone-Needs-A-Copilot/cli-copilot-internal"
    },
    {
      "id": "crm",
      "name": "NocoDB CRM",
      "description": "NocoDB CRM operations.",
      "requires_secret": "NOCODB_API_KEY",
      "store_scope": "org/shared",
      "introduced_by": "Everyone-Needs-A-Copilot/cli-copilot-internal"
    }
  ]
}
```

This alternative also requires populating `ecosystem.yml`'s empty `team_scopes:` (`claude-copilot-internal/ecosystem.yml:21`) with at least `- { team: <team>, scope: org/shared }`, since `store_scope` is defined as a key into it (`admin-standup-contract.md:483`).

**Recommendation: option 1, not the alternative.** The registry file would be a second, hand-maintained copy of facts `cli.overlay.yml` already carries authoritatively and that `copilot --json layers` already computes — guaranteed to drift, and it would mean an integration could be *runnable* but *invisible*, or *visible* but *not installed*. Projecting the overlay keeps one source of truth. If §5 is kept as the ratified contract, it should be amended so `integrations.registry.json` is **generated** from `cli.overlay.yml` by `copilot publish`, never hand-authored.

**Sequencing:** fix the `copilot infisical identity provision` defect (or make `cc` degrade with an honest "this CLI Copilot build has no identity provisioner" detail instead of a generic deferral) **before** shipping the list, so the first thing the owner sees is not ten connections that all say "not ready".

## 8. Trade-offs of the recommendation

- **Optimizing for:** single source of truth and zero drift between "declared", "installed" and "listed".
- **Sacrificing:** cross-component generality — the projection is CLI-Copilot-shaped, so a future non-CLI integration would need its own emitter; and it couples `cc`'s connections surface to CLI Copilot's `layers` schema version (mitigate with the same range-gate discipline `cli-client.swift:300-326` already applies).
- **Reversible?** Yes. It is additive on all three hops; the app change is a view swap behind a decoder that can fall back to today's empty state if the section is absent.
