# Milestone 3 Architecture — The First-Run Wizard (Silent First Light)

Thin-skin (parse-never-compute) first-run wizard: Surface 2 of the product (UX §IA). Two paths in one
window — a **managed silent first-run** (~0 questions) and an **unmanaged guided first-run** (≤3
questions) — plus the **device-flow sign-in** step that lands credentials in the OS keychain *via the
CLI*, the app holding nothing (invariant #6). The wizard renders CLI-computed setup **phases by name**,
computes no verdict, and reaches Healthy only from a fresh `doctor status:healthy` — else it holds
honestly, never a false-Healthy.

Builds on M1 WP (`.copilot/wp/1.md`) and M2 WP (`.copilot/wp/5.md`): reuses RenderState/typed-DTO IPC,
the `cli::path::resolve()` dev-mockable seam + `mock-cc` fixture corpus, `render::derive` (the one place
a Healthy verdict is parsed), `settings::managed` (forced-domain detection), `settings::authoring`
(layer-manifest write), the config-pointer/never-destroy write seam, the Settings window pattern, and
the fitness-function discipline.

Maps to PRD **WS-C** (C1–C5), phase-gate **P1**.

## 0. THE CRITICAL CONTRACT QUESTION — the sign-in verb (investigated, flagged like M1/M2)

**The wizard's sign-in step provisions credentials into the OS keychain via device-flow/OAuth. Which
`cc` verb does this, and does it exist?** Investigated the app's docs/schemas AND the real CLI
(`claude-copilot/tools/cc`, branch `ws-a-doctor-slice`). The contract splits into a FROZEN render half
and an UNDEFINED provisioning half.

### FROZEN — the app can render "needs sign-in" today
- **`doctor --json` already carries the read/render contract for signed-out.** `doctor.py` emits an
  `auth[]` array (`build_doctor_report()`: `"auth": []`; rendered at `render_doctor_report_rich` as
  `{identity, scope, state}`), and `signed-out` is a first-class `status` value (the Rich renderer's
  status-color map lists it). UX state-matrix **row 2 (Signed-out)** parses `auth[].state ∈
  {expired,revoked}` for a required layer → solid + **key** badge → "Sign in…". So the app can render
  the honest holding state against the *doctor* schema today.
- **CAVEAT (a sub-gap):** `auth[]` is currently **hardcoded empty** — no checker populates it yet. The
  render *shape* exists in the doctor schema; no real auth data flows until a checker (WS-A) fills it.

### UNDEFINED GAP — the provisioning verb does not exist (D-3-M3)
- **No `auth`/`login` verb** in the real CLI. `main.py` registers: `env, resolve, doctor, freshness,
  update, repair, deprovision, version` + subgroups (`memory, skill, config, mcp, docs, usage, eval`).
  There is no device-flow provisioning verb.
- **No auth schema** in `docs/01-architecture/schemas/` (confirmed absent).
- **The intended verb is *named* but unbuilt:** `credentials-and-boundary.md §3` — "headless `copilot
  auth <integration>` works with no GUI"; §6.2 — `copilot auth rotate-key --tier work`. §3's
  where-each-piece-lives table is explicit: **the CLI owns** OAuth/device-flow execution + keychain
  write; **Control Tower renders the GUI wrapper (browser + code) and holds no secret itself.**
- **A design inconsistency to reconcile:** the *wizard host sign-in* step is described as "poll `gh auth
  status`" (architecture.md §4; UX Flow 2 step 3). Screen-scraping `gh`'s human output is itself a
  **Case Law OUT** ("Screen-scraping human CLI output instead of --json"). Two distinct sign-ins are
  both un-frozen: (1) **host/GitHub identity** (wizard Q2, to pull repos), (2) **per-integration
  secret** (`cc auth <integration>`, post-setup, surfaced via doctor `signed-out`).

### Verdict: **GAP** — same shape as M1 D-1 and M2 D-1.

### Recommended pattern (matches the M1/M2 precedents; keeps invariant #6 intact)
The app **renders the device-flow wrapper** and **passes through** a frozen `cc auth <integration>
--json` verb that the CLI owns end-to-end:
- The verb emits, as JSON, the device-flow ceremony — `{user_code, verification_uri, expires_in,
  interval}` — then a **terminal** `{state: authorized|denied|expired|timeout}` (streamed NDJSON or a
  poll-until-terminal one-shot; freeze which in WS-A).
- The CLI performs the OAuth poll **and the keychain write** (`Security.framework`). **The app never
  sees, relays, or stores the token** — it renders `user_code`, opens `verification_uri`, and polls the
  verb until terminal.
- On a miss/failure the app renders the **existing** `signed-out` holding state (reuse doctor's badge +
  "Sign in…"), never a raw OAuth/error string (Git-Error-To-A-Non-Technical-Person discipline applied
  to auth).

### Fallback so M3 builds NOW (the dev-mockable seam)
A `mock-cc auth` fixture emits the ceremony JSON + a terminal state (authorized/denied/expired/timeout).
The whole sign-in UX + the Rust seam build and headless-test against the **frozen SHAPE** today; the
real verb is batched into WS-A. Mirrors M2-S4's DECISION-GATED pattern and M1's D-1 mock-first approach.

### D-3-M3 — decisions to batch for the owner / WS-A
1. **Freeze the `cc auth <integration> --json` schema** (ceremony fields, terminal states, exit codes)
   in `docs/01-architecture/schemas/auth.schema.json`; build the verb in WS-A (`claude-copilot`). This
   is the same queued cross-repo push family as the WS-A binary/contract work.
2. **Reconcile the host sign-in step:** replace "poll `gh auth status`" (screen-scrape, Case Law OUT)
   with `cc auth login --json` (GitHub identity treated as one integration the CLI drives a device flow
   for — the doc already anticipates this in §6.2's "GitHub becomes one more integration the CLI can
   drive a device flow for"). *Recommended.* Alternative to explicitly ratify: wrap `gh auth login
   --web` but parse only its **exit code**, never stdout prose.
3. **Confirm the doctor `auth[]` shape** is the frozen render contract for signed-out, and schedule the
   checker that populates it (today it is always `[]`).
4. **Machine-credential / kiosk sign-in** (managed silent path): confirm the `AuthMode=gh-app`
   bootstrap-exchange shape (credentials-and-boundary §1.5) the managed wizard's non-interactive sign-in
   relies on — still open per arch §11 item 3.

### S1 — Wizard state machine + phase model (Rust) · me · foundation · **High** · dep: S0
Typed `WizardState` / `WizardPhase` enums: `Welcome → Detect → [Question]* → Materialize(phase) →
Verify → Teach → Done`, with holding terminals `Holding(ItConfigIncomplete{key} | WaitingForNetwork)`.
Managed vs unmanaged branch via `settings::managed::is_managed()`. **Parse-never-compute:** phases are
named states rendered from CLI-verb events; the wizard computes **no** health verdict; the terminal
`Done/Healthy` is gated on a fresh `doctor status:healthy` through the M1 `render::derive` path (the
only Healthy source). **Acceptance:** every transition unit-tested; managed→silent asks 0 questions; a
verify-fail routes to a holding terminal, **never** to Done/Healthy (no false-complete). **Tests:**
Unit — transition table, 0-question managed path, fail-closed-to-holding.

### S2 — First-run completion persistence + resumability (Rust) · me · foundation · Medium · dep: S1
Where "first-run complete" + the mid-setup checkpoint live: **config, not a secret** — written via the
**M2 config-pointer seam** (`cc config set wizard.completed` / `wizard.checkpoint`; single writer is
`cc`, never a Rust JSON read-modify-write). Checkpoint persisted **at the FIRST phase** (WS-C C1:
login-item + watchdog + checkpoint at phase 1) so a mid-setup quit **resumes headlessly** and never
re-runs the wizard nor clobbers a partial setup (**never-destroy**). **Acceptance:** completion gate
blocks re-run; an interrupted run resumes from last checkpoint; no clobber of a partial setup; the
completion flag is not a secret and carries none. **Tests:** Unit — completion gate, resume-from-
checkpoint, never-destroy-on-partial. Honest degrade when `cc` unavailable (reuse M2
`ConfigPointerError::CliUnavailable` — never a false "saved").

### S3 — Sign-in device-flow seam (Rust) · sec · foundation · **High** · **DECISION-GATED on D-3-M3** · dep: S1

## 3. ADRs

### ADR-M3-001 — Sign-in builds against a dev-mockable `cc auth` seam (mock-first), not the real verb
**Status:** Accepted. **Context:** the provisioning verb doesn't exist and has no schema (§0); the app
must not block M3 on a cross-repo WS-A verb, nor invent auth logic (invariant #1). **Decision:** freeze
the `cc auth --json` **SHAPE** (ceremony + terminal states), build the Rust seam + UI against a mock-cc
`auth` fixture; batch the real verb into WS-A (D-3-M3). **Consequences:** M3 ships and headless-tests
now; a real end-to-end sign-in awaits the WS-A verb (owner-batched). **Alternatives rejected:** (a)
screen-scrape `gh auth status` — Case Law OUT (misread green-over-red); (b) the app drives OAuth + writes
the keychain itself — violates invariants #1 and #6 (the app would hold a secret).

### ADR-M3-002 — Terminal Healthy is parsed from `doctor`, never asserted by the wizard
**Status:** Accepted. **Context:** a wizard that declares its own success is a false-Healthy vector (the
worst outcome). **Decision:** the wizard's `Done` transition is gated on a fresh `doctor status:healthy`
via the M1 `render::derive` path; on anything else it holds. **Consequences:** the icon cannot lie even
during setup; "setup finished" and "actually Healthy" can never diverge. **Alternatives rejected:** a
wizard-computed "setup complete → green" — fabricates the exact false-Healthy the holding states exist
to prevent (SOUL Case Law OUT).

### ADR-M3-003 — Progress is rendered by phase NAME, never a time estimate
**Status:** Accepted (ratifies SOUL Case Law OUT). **Context:** an ETA is a computed promise the app
can't keep honestly. **Decision:** stream the CLI phase name ("Setting up Claude…"); a fitness test
forbids any ETA/countdown string in the wizard. **Consequences:** honest, if less "reassuring", progress.
**Alternatives rejected:** "~2 minutes left" — Case Law OUT.

### ADR-M3-004 — First-run state is config (via `cc`), resumable, never-destroy
**Status:** Accepted. **Context:** the wizard must not re-run, must resume if interrupted, and must not
clobber a partial setup. **Decision:** persist completion + checkpoint through the M2 config-pointer
seam (single writer `cc`); checkpoint at phase 1; resume from last checkpoint. **Consequences:** a quit
mid-setup resumes headlessly; no partial-setup clobber. **Alternatives rejected:** a Rust-written state
file (re-implements `cc config` write, risks clobbering sibling keys — M2 already rejected this) and a
"restart from scratch" (would re-ask / re-clone, violating never-destroy of partial work).

### ADR-M3-005 — The host step is product-first (HANDOFF fix)
**Status:** Accepted. **Context:** the "Claude/Codex/Both" step is host-framed — a drift from the
ratified product-first model (Knowledge/CLI/Claude/Codex). **Decision:** render products, config-driven,
narrow-not-widen. **Consequences:** consistent with the M1 dropdown and the owner's model.
**Alternatives rejected:** keep host-framing — contradicts the ratified model and the HANDOFF directive.

## 4. Fitness functions (automated, CI-gated — extend M1/M2's set)
1. **no-ETA-in-wizard** — grep-deny any countdown/ETA/"minutes"/"seconds left" string in wizard code+UI.
2. **no-secret-on-wizard-DTO** — the `WizardState` DTO (Rust + TS) has no token/secret/credential field;
   the sign-in seam surfaces only `user_code`/`verification_uri`/terminal-state, never a token.
3. **no-bare-cli-name** (reuse) — the auth/phase spawns go through `cli::path::resolve()`, never bare.
4. **no-fabricated-complete** (extend no-fabricated-Healthy) — no code path sets `Done`/Healthy without a
   parsed fresh `doctor status:healthy`.
5. **parse-never-compute** — the wizard module contains no health/resolution/signature/keychain logic;
   all such work is a CLI passthrough (code-review + grep gate).
6. **capability-scope** — `capabilities/wizard.json` grants only the wizard commands to only the wizard
   window (no widening of the default/settings grants).

## 5. Invariant checks (per the task brief)
- **#1 parse-never-compute:** ADR-002/003, fitness 4/5 — the wizard renders CLI-computed phases and the
  doctor verdict; the icon can't lie during setup. ✅
- **#4 security never weakened:** S3 forbids `--skip-verify`/`--force`; managed profile schema-validated
  before silent mode; no lower-bar "skip validation". ✅
- **#6 secrets stay in the keychain via the CLI flow, app holds nothing:** S3 + fitness 2; the CLI owns
  OAuth + keychain write (credentials-and-boundary §3). ✅
- **route-by-competence:** the wizard asks Bob only about his own data (host/product choice, his sign-in,
  his company/dept) — never a decision he can't judge; managed path asks nothing. ✅
- **never-destroy:** ADR-004 — resumable, no clobber of partial setup. ✅
- **Flagged risk to watch:** the doctor `auth[]` array is empty today (§0 caveat) — S3/S4 must render
  `signed-out` from the SHAPE and not assume populated data until the WS-A checker lands.
