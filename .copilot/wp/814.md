Assets, actors, and boundaries
- Assets: Developer ID Application and Installer authority, notary authority, approved public ref/commit/tree, signed payload and approval receipt, protected installed anchor, and candidate-release authority.
- Adversary: mutable repository code or another process under the logged-in publisher account, including code able to replace user-owned files between review steps. Root or Apple PKI compromise is out of scope.

Blocking finding 1 — authenticated Git bytes never become the authority-bearing provisioner (CWE-494/CWE-829; high likelihood, critical impact)
`scripts/provision-publisher-bootstrap.sh` is launched from the mutable repository checkout. It correctly uses a clean environment, checks the advertised ref, fetches a bare store, verifies commit/tree, materializes only regular authenticated blobs, and invokes the materialized `scripts/build-publisher-bootstrap.sh` to compile the app. However, control then returns to the original repository-checkout shell. That original shell resolves and sources `.env.release.local` and itself drives `codesign`, `notarytool`, `productsign`, final copying, and evidence generation. It never `exec`s or streams an authenticated provisioner implementation and never authenticates its own executing bytes against the fetched Git object.

Concrete exploit: same-user code changes the checkout provisioner after human review (or invokes a substituted copy). The substituted outer shell can preserve or fake all pre-authority fetch/materialization output, then source the authority file and sign/notarize attacker-selected app/package bytes. Authentication of a separate build script does not authenticate the shell controlling all later authority-bearing decisions. This violates WP-808 step 1 and the runbook claim that exact authenticated source precedes release authority.

Required mitigation: make the checkout entry stage permanently credential-free. After fetching/verifying the exact tree, transfer control to an independently authenticated implementation without returning to checkout bytes—for example a narrowly designed streamed/FD-backed stage with an unforgeable challenge, or another architecture approved by `$ta`. The authority-bearing stage must re-bind all source/ref/commit/tree inputs, create and sign the payload, and never trust a path that same-user code can replace between verification and execution. Add an attack that mutates the checkout outer script while preserving the authenticated tree and proves authority remains unreachable.

Blocking finding 2 — verified package identity is not bound across the Installer handoff or after install (CWE-367/CWE-345; medium likelihood, high impact)
The package verifier correctly validates its current path's signature/team, Gatekeeper/staple, exact top-level members, absence of Scripts, exact extracted payload, root:wheel BOM, app identity/digest, and exact schema-2 source receipt. But the verified package and `package-evidence.json` live in a user-owned output directory. Mode 0444 does not stop the owner from replacing the directory entry after verification. The runbook later supplies only the pathname to Installer. Apple verifies that the package it opens is validly signed; it does not know the earlier expected SHA/ref/commit/tree.

After installation, `verify-publisher-bootstrap.sh` accepts no expected package digest/ref/commit/tree and checks no actual Installer receipt/version. It only proves that the installed app and adjacent root-owned approval are self-consistent and signed by the approved team. A previously valid same-team package with the same fixed package identifier/version (`1.0.0`) can therefore be substituted at the path and become the accepted installed truth, rolling the anchor/source approval backward. This is source/receipt confusion: the payload receipt is signed by whichever package was consumed, but the verifier never compares it with the operator's preverified intended package.

Required mitigation: design a single attended transaction that binds the exact verified package digest and expected source identity through Installer consumption and the immediate installed-state verification. At minimum, installed verification must require the independently recorded expected ref/commit/tree and app digest/CDHash and reject rollback/substitution; package versioning must be monotonic and receipt state must be validated where it contributes to the claim. The architecture must explicitly resolve pathname TOCTOU instead of treating chmod 0444 as immutable. Add A/B tests where package B is validly signed by the same team and replaces package A after preverification; B must not become an approved installed anchor.

Controls that passed
- Package creation is non-root and supplies no preinstall/postinstall scripts; source gates forbid repository root shell and direct Installer execution.
- Local unsigned seam produced exactly PackageInfo/Bom/Payload and no Scripts; payload path/type/mode/ACL and BOM root:wheel checks are materially strong.
- Receipt schema 2 binds package identifier, app path, bundle identifier, team, CDHash, bundle digest, and Git remote/ref/commit/tree; malformed/missing/unknown schema tests fail closed.
- Actual ad-hoc candidate-B mutation, payload/receipt change, extra path, symlink, ACL, writable mode, wrong bundle, wrong expected source, and moved ref reject in the hermetic package path.
- Installed ancestry verifier checks the common root and all app/approval ancestors for exact type, owner, mode, ACL, and symlink conditions in its production functions.
- Builder/verifier do not consume, migrate, restore, or delete the rejected `/Applications` bundle. Runbook removal is separate and ordered after installed verification and fresh approval.
- Scratch roots are fixed under `/private/var/tmp`, mode 0700, caller TMPDIR/Python/shell startup authority is excluded, and generated package contains no secret values.
- `git diff --check` passed; review did not edit the tree.

Unproven real-world boundary
No Developer ID Installer identity or real Installer-signed package was available. Therefore package signer-chain parsing, actual package identity facts, notarization/staple behavior, macOS Installer replacement/failure semantics, root:wheel installed result, package receipt state, and attended post-install ordering remain unproven. WP-813 correctly limits itself to hermetic source approval; it cannot authorize a candidate. A fresh review of exact immutable integrated source plus attended real signed/install evidence remains mandatory after the two source blockers are corrected.

Residual risk
Even after these fixes, compromise of the logged-in publisher account may reach user-held credentials subject to Keychain policy; this anchor reduces mutable-repository authority and package substitution, not full publisher-account compromise. Same-team certificate rotation may be a deliberate trust policy, but it must be stated; textual `pkgutil` matching alone has not yet been validated against a real Installer identity. Apple Installer and root compromise remain external trust roots.

VERDICT: REJECTED
WP-812 does not yet establish independent first trust. TASK-287 candidate work must remain blocked. Route to `$ta` for the provisioner transition and exact-package Installer transaction, then `$me`, fresh `$qa`, and fresh `$sec` before any real signing/install/candidate ceremony.
