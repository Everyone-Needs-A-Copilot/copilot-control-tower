Non-negotiable invariant
No executable or script obtained from the mutable checkout may receive or retrieve GitHub, signing, notarization, Keychain, or release authority before an independent trust anchor proves the exact executable/program bytes. An adjacent hash manifest, ad-hoc signature, caller flag, pipe challenge, local Git config, or self-recompile cannot be that anchor.

Option A — make the source repository public (recommended if public launch is intended now)
- Owner changes repository visibility only after a dedicated public-readiness/security review. This is an external state change and is not authorized by TASK-287 alone.
- A minimal compiled bootstrap performs unauthenticated HTTPS-only ref resolution/fetch from the exact canonical public endpoint. It rejects all credential/sign/notary environment and does not access Keychain or .env.release.local.
- It creates a private mode-0700 temporary bare Git store from a fresh non-repository cwd under env -i. Global/system config are /dev/null; credential helpers, redirects, unsafe protocols, includes, proxies, SSH/askpass, filters, fsmonitor, textconv, external diff, and hooks are disabled. The bare store and its config are bootstrap-created and never derived from the caller checkout.
- It fetches only the selected advertised ref, resolves annotated tags, pins commit/tree, materializes the tree into a separate no-.git source directory, and validates launcher/source/program/manifest/verifier objects and modes from the trusted bare store.
- The immutable launcher/program then independently re-resolve the public ref through a second fresh config-null bare store before loading local publisher authority. Public resolution requires no pre-trust secret.
- All build and release inputs come from the materialized no-.git tree. The mutable invoking checkout is used only to locate the mode-0600 authority file after immutable verification.
- Before Developer ID signing and before metadata, compare every tracked source path/mode/symlink target against the trusted tree manifest; reject unexpected files in build-input directories. Re-resolve the public ref. Do not call repository-aware Git in the authority-bearing program.

Public-visibility prerequisites
- Owner explicitly accepts disclosure of the full reachable Git history, source, assets, branches/tags exposed by policy, and repository metadata consequences.
- Run history-wide secret/key/token/private-data scanning, license and third-party asset review, public README/support/security/contact review, branch protection and Actions permission review, and confirm no private submodule/dependency URLs become a disclosure or build failure.
- Record the visibility decision and rollback posture. Changing back to private does not retract already cloned history.

Option B — retain private source and install a separate pinned release bootstrap
- Produce a minimal launcher as a separately reviewed, Developer-ID-signed and notarized artifact. Install it outside the repository under a protected canonical path with root/platform ownership, non-symlink and non-writable ancestry, exact Team ID/designated requirement, and a version/hash policy stored outside the mutable checkout.
- The repository copy is never a release entry and cannot update or bless the installed launcher. Bootstrap install/update requires explicit owner/admin action and a separately verified signed artifact.
- Only this preinstalled trust anchor may access the fixed private-repository credential channel. It performs canonical config-null fetch into its own mode-0700 bare store, verifies the advertised commit/tree and exact inner objects, materializes a no-.git tree, then launches immutable release code.
- Prefer the installed bootstrap to broker authority after verification rather than hand long-lived secrets to repository code. Notary should use the fixed Keychain profile; Git credentials should remain inside the trusted fetch subprocess.
- This option needs an initial trust ceremony because fd1694f does not already ship such a pinned launcher. The ceremony/build/sign/notarize/install authority is a separate security-reviewed operation; TASK-287 cannot self-bootstrap it from the mutable checkout.

Private pinned-bootstrap prerequisites
- Owner approves a new installed privileged trust component and its canonical install path/update policy.
- Architecture/security review covers installer privilege, designated requirement, rollback, revocation, credential ACL/channel, update custody, and recovery when the bootstrap expires or the private repo credential is revoked.
- Independent QA/security verify copied/ad-hoc/recompiled/symlink/path substitution, downgrade, wrong Team ID, mutable parent, injected config/helper/proxy/hook/filter, stale/moved ref, dirty tree, credential leakage, and uninstall/rollback.

Inner Git redesign required for either option
- Eliminate every plain `git` and `/usr/bin/git -C <release checkout>` invocation from package-user-release.program and release_verify_checkout in authority-bearing context.
- Do not attempt to null arbitrary checkout-local configuration piecemeal. The inner must never read the checkout's .git/config.
- Centralize Git in one trusted wrapper operating only on a bootstrap-created mode-0700 bare Git directory from a fresh non-repository cwd under env -i.
- Fixed controls: absolute /usr/bin/git; system/global config /dev/null; HOME an empty mode-0700 directory; no caller Git variables; helpers empty unless Option B's installed trust anchor supplies its fixed channel; HTTPS only; file/ext/ssh/git/http disabled; redirects disabled; hooksPath=/dev/null; fsmonitor=false; attributes file /dev/null; no external diff/textconv/filters; exact canonical URL/ref.
- Materialize build source without .git. Verify source with a complete Git-tree-derived manifest (path, object ID/hash, mode, symlink target) and filesystem walk, not status/diff commands against a mutable repository.
- All post-build/pre-sign/pre-metadata checks use that manifest plus fresh remote ref resolution through the trusted store/wrapper. No repository-aware Git command executes after authority becomes available.

Rejected approaches
- WP-739 Keychain helper in the mutable launcher: rejected because it retrieves a private-repo secret before immutable trust.
- Mutable gh/osxkeychain helper path, caller GH token, exported extraheader, askpass, SSH agent, or ambient Git config: rejected as caller/machine authority and secret exposure.
- Self-signed/ad-hoc compiled launcher plus adjacent manifest: rejected as circular trust.
- Allowing current fd1694f inner to authenticate after receiving authority: rejected because it still reads checkout-local Git config and hooks.
- Directly invoking verified-source/internal flags or manually copying a clone: rejected as forgeable/bypassable.

Recommendation and blocker
- If Control Tower is ready for its stated open-source public launch, choose Option A. It is the smaller system, removes private-source authentication from the release bootstrap, and avoids adding a permanent installed trust component.
- If repository confidentiality must continue, Option B is the only acceptable route. It is intentionally more operationally expensive because private authentication itself requires a pre-existing trust anchor.
- TASK-287 cannot proceed to implementation/candidate until the owner explicitly chooses public visibility or a pinned installed bootstrap. Do not change visibility, install a bootstrap, access release authority, or publish under this architecture WP.
