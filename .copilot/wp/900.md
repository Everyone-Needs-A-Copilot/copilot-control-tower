Chosen design: use a short, owner-PID-bound `GlobalJourneyTransaction` around the validated `/private/tmp` directory descriptor and tc persistence only. Produce an immutable authority intent under one transaction, run verifier/resolver/capability callbacks after releasing it, then reacquire, rebuild state, and require the intent to match exactly before any store. All authoritative stores go through the transaction's single append primitive, which performs directory identity and PID checks immediately before and after the store. # Existing call graph and trust boundaries

The exact WP-894 code already invokes capability and begin security before the begin claim, but `prepare_run` and `verify_dispatch` invoke security and Knowledge resolver callbacks while holding the global flock. `bind_prompt`, `pause_run`, `_store_final`, and tc append do not need external callbacks. `TcJourneyLedger.append` currently has no access to the claimed descriptor, so it cannot perform pre/post-store checks. `_state` currently sorts dispatch payloads by `stage_index`, then checks only prepare-before-bind-before-dispatch within each stage.

Trust boundaries:

- Untrusted-to-fork callbacks: capability adapter, mandatory-security verifier, Knowledge resolver, and any provider/injected hook. They may fail, block, spawn, fork, or observe stale state; they must never execute while the global descriptor is open/locked.
- Trusted persistence adapter: tc list/get/store. These must execute under the transaction because they are the authority store. Production must bind this adapter to the supported `tc.api`; arbitrary injected stores remain test-only and are not an authorization boundary.
- Authoritative state: exact guarded tc rows, their positive unique row IDs, closed payloads, and the immutable callback receipts bound to an intent.
- Cooperative-local lock: advisory directory flock coordinates framework writers; complete tc database rewrite, root compromise, and noncooperating writers remain documented residual trust.

# Minimal implementation shape

## 1. Owner-bound transaction

`claim()` should yield a transaction object rather than ambient permission. The object owns only: exact directory FD, acquisition PID, active flag, and ledger adapter. It is non-reentrant and cannot be reused after exit. `ledger.append` must either become private or require this transaction token; every begin, prepare, bind, dispatch, pause, and final write must use `transaction.append`.

Acquisition retains WP-894's literal `/private/tmp`, read-only/directory/no-follow/close-on-exec flags, root owner, directory type, sticky bit, lstat/fstat device+inode equality, bounded monotonic `LOCK_EX|LOCK_NB`, and post-acquire validation.

`transaction.append` ordering is normative:

1. assert active and `os.getpid() == owner_pid`;
2. validate literal-path lstat against FD fstat, including root/type/sticky/device/inode;
3. call the trusted tc store exactly once;
4. in a finally path, assert owner PID and repeat FD/path identity validation even when store raises;
5. verify exact returned task/type/title/content/agent and clean guard;
6. repeat owner-PID and FD/path identity validation after returned-row verification;
7. return the stored row.

The owner process alone may issue `LOCK_UN`. A forked child that unwinds the inherited context must close its inherited descriptor without unlocking the parent's open-file description. Register an after-fork child handler for active transaction FDs: mark transactions invalid in the child and close the child's descriptor copy. Every state-read and append method on the transaction asserts owner PID. At owner exit, validate once more, unlock, close, and mark inactive.

If post-store identity validation fails, surface a value-suppressing terminal integrity error and do not retry the store automatically; the row may already exist. The next invocation must reconstruct guarded tc state under a new transaction and act idempotently. Never implement compensating deletion.

## 2. Global row chronology

Build a map from each validated payload object to its real positive tc row ID. Sort dispatch records by row ID, then require their stage indices to be exactly `0..n-1` and their specialists to equal the route prefix. Do not sort by stage to manufacture the prefix.

For each stage N:

- `begin.id < prepare[N].id < bind[N].id < dispatch[N].id` when dispatched;
- for N > 0, `dispatch[N-1].id < prepare[N].id`;
- dispatch IDs therefore strictly increase with stage;
- an undispatched current stage may have exactly one prepare and optional later binding, both after the previous dispatch;
- no stage beyond the current stage may have any row.

For a pause row P with generation G, derive G from the valid dispatch prefix whose row IDs are less than `P.id`; do not trust the capsule's G. Before P, stages `0..G-1` must be completely dispatched in the total order above. Stage G may be absent, prepared, or prompt-bound exactly as captured by the capsule, but cannot be dispatched; no stage greater than G and no final row may precede P. Pause generations and IDs strictly increase, and every historical capsule is rebuilt only from rows below its own cutoff. Final evidence must follow the last dispatch and every pause.

## 3. Safe callback and store ordering

Use a three-phase optimistic transaction for operations that require callbacks:

A. Snapshot: acquire, rebuild and fully validate state, then emit a closed immutable `AuthorityIntent` containing task/run, begin row ID+canonical digest, route/security identity, next stage/specialist, relevant prepare/binding row IDs+digests, session/prompt/marker/Knowledge digest expectations, and observed ledger head ID. Release.

B. Resolve: run security verifier first and require allowed; then run Knowledge resolver/capability as applicable. Validate and freeze their public receipts and content/source digests. No global lock descriptor is open in this phase. Errors disclose no values.

C. Commit: reacquire, rebuild state, recompute the intent, and require exact equality. Bind the callback receipts to that intent. If anything changed, return a stale-intent denial and do not silently rerun callbacks. Otherwise append through the transaction and verify the exact stored row. Dispatch plus optional final row remain in this single commit transaction.

Operation mapping:

- begin: build route, security receipt, and optional capability receipt outside; transaction checks session uniqueness and stores begin.
- prepare: snapshot exact next-stage intent; security then Knowledge resolve outside; commit exact-intent match and store or idempotently return the already-identical preparation.
- bind: no external callback; one transaction rebuilds state and appends/returns the exact binding.
- verify dispatch: marker lookup may nominate a candidate outside, but snapshot transaction must bind the exact task/run/preparation/binding/session/prompt/Knowledge intent; security and Knowledge re-resolution occur outside; commit transaction revalidates the intent, stores one dispatch, and stores final when applicable.
- pause: use the prepare pipeline first if current-stage preparation is absent, then a separate transaction rebuilds state and appends/returns the exact capsule.
- resume: validate and snapshot continuation under a transaction; run security outside; reacquire and require exact continuation intent before returning state or entering the prepare pipeline.
- inspect: read-only inspection may remain callback-free, but any result used to authorize a mutation must be rebuilt inside that mutation's transaction.

This accepts callback-window contention deliberately: a concurrent writer can make the intent stale, but cannot make it authorize against different state. Callers retry explicitly from a new snapshot. It rejects holding the global lock through resolver/provider work and rejects automatic callback replay.

# Minimal acceptance probes

## A. Cross-stage chronology — four probes

A1-A3, parameterized on a valid three-stage ledger: reassign only real-looking positive unique row IDs so, while preserving each moved stage's internal order, (a) stage-1 prepare, (b) stage-1 prepare+bind, or (c) stage-1 prepare+bind+dispatch occurs before stage-0 dispatch. For every variant, `inspect_run` must deny chronology and `pause_run` must append zero rows. Variant C is the exact WP-898 exploit.

A4: run the variant-C reorder in an isolated real tc SQLite database by changing IDs through a test-only database transaction while keeping summary/full identity consistent. Public tc reads must expose the forged order and runtime inspection must deny. This proves the decision uses tc IDs rather than fixture list order.

Positive control: valid generation-1 pause, resume, stage-1 dispatch, generation-2 pause, resume, terminal dispatch remains accepted; every prepare/bind/dispatch boundary and pause/final cutoff is asserted by row ID.

## B. Every-store identity — three probes

B1: instrument one complete three-stage journey and record transaction-validator/store events. For every stored title—begin, each prepare/bind/dispatch, each pause, and final—the sequence must contain the same FD and owner PID with `validate-pre`, one store, `validate-post`, exact-row/guard verification, and `validate-post-verify`. No store may occur outside an active transaction.

B2: inject a pathname/FD identity mismatch on the pre-store validation for each record type via a parameterized validator seam. The store spy count must remain zero for that operation, the error must be value-suppressing, and prior rows remain unchanged.

B3: inject mismatch after the store returns. The call must deny without a second store; reconstructing with identity restored must observe at most the one guarded row and make retry idempotent. Repeat at least for dispatch and final because they share one transaction and exactly-once is material.

## C. PID/fork lifecycle — three probes

C1: while an owner holds a transaction, raw-fork a child. The child must see the transaction invalid/owner-PID mismatch, be unable to read state or append, close its inherited FD without `LOCK_UN`, and exit. An independent third process must remain blocked until the owner releases, then acquire.

C2: fork a child that unwinds the inherited context and remains alive briefly. The parent's lock must remain held; child lifetime must not prolong the lock after parent release because the after-fork handler closed the child copy.

C3: use resolver and verifier callbacks that spawn/fork and wait. Instrument descriptor opens: callbacks must run while no journey lock FD/transaction is active. After their immutable receipts return, commit succeeds only if the recomputed intent matches; concurrently append one legitimate progress row during the callback and prove commit denies stale intent with zero additional authority rows.

# Rejected alternatives

- Stage-sorting plus local checks: rejected because it recreates a route prefix from forged payload fields and is the WP-898 bypass.
- Holding flock while callbacks run: rejected because raw fork shares the open-file description and long resolver/provider work expands global DoS and contention.
- Lock-free callback result followed by store without intent replay: rejected as a stale-authority TOCTOU.
- Making arbitrary store callbacks safe: rejected; tc persistence is a trusted adapter and an arbitrary malicious callback can fork or write before any wrapper regains control. Production must use the supported adapter, with injectable stores confined to tests.
- Per-run child lock files: rejected because earlier rename/unlink/recreate reviews demonstrated split-inode claims.
- Automatic rollback/delete after a post-store check failure: rejected because it weakens append-only evidence and can delete an authority row another reader has observed.

# Residual risk and routing

Any local user can still hold `/private/tmp` flock and cause bounded fail-closed denial of service. Flock remains advisory, and root or a complete tc-store attacker can bypass/rewrite authority. The global vnode intentionally serializes all projects, so short transactions and callbacks outside the lock are mandatory for availability.
