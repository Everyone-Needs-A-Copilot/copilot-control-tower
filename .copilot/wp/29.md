## 4. Promote/rollback semantics (the safety mechanism)

Live-wired proof, not just the pure state machine (all passing, part of §1):

- **Promote:** `confirm_staged_bundle_boots_promotes_on_a_real_self_test_ok_
  heartbeat` — injected fake launcher + temp `StagedLayout` + the REAL
  `heartbeat::FileHeartbeatSource` (not a fake heartbeat reader) → `Ready`,
  `staged/` consumed, `current/VERSION` updated, no rollback marker set.
- **No heartbeat ⇒ rollback+poison:** `confirm_staged_bundle_boots_rolls_
  back_and_poisons_when_no_heartbeat_ever_appears` → `RolledBack`, message
  exactly `"Kept your working version."`, `current/` untouched, staged
  version poisoned, rollback marker set to the poisoned version.
- **Malformed heartbeat ⇒ rollback:** `..._rolls_back_on_a_malformed_
  heartbeat` — a launcher that writes garbage JSON instead of a valid
  heartbeat → `RolledBack`, poisoned. Confirmed via `heartbeat.rs`'s own
  `observe_reports_malformed_immediately_without_waiting_out_the_full_
  timeout` that a confirmed-malformed heartbeat short-circuits rather than
  waiting out the timeout.
- **Launcher failure itself (missing/unexecutable staged binary) ⇒
  rollback**, never a distinct "error" branch —
  `..._rolls_back_when_the_launcher_itself_fails_fitness_ff_m4_6` — degrades
  to the SAME fail-closed outcome a genuine crash/hang produces.
- **Stale heartbeat from a previous attempt is discarded, never mistaken for
  fresh proof** — `..._ignores_a_stale_heartbeat_from_a_previous_attempt`
  AND `heartbeat.rs`'s own `observe_never_promotes_on_a_stale_heartbeat_for_
  a_different_app_version`.
- **The shown-once rollback marker:** `check_for_update_at_surfaces_a_
  pending_rollback_marker_exactly_once` — first `check_for_update_at` call
  after a real rollback returns `UpdateStatus::RolledBack` with the exact
  message; the SECOND call (no re-call to `record_rollback`) does not.
  `rollback_marker.rs`'s own 6 unit tests independently confirm: shown-once,
  absence-is-not-an-error, a corrupt marker file is treated as absent
  (fail-closed), recording twice overwrites (not appends), no temp file is
  left behind, and a read of an absent marker never creates one.
- **Interrupted-update reconciliation (a prior launch crashed mid-self-test,
  leaving `staged/` in limbo):** `updater::startup`'s
  `a_leftover_staged_bundle_is_discarded_poisoned_and_marked_for_the_next_
  launch` — routes through the SAME `watchdog::run_self_test` (a
  `NeverAliveSource` that always reports `Timeout`, never a hand-rolled
  discard), `current/` untouched, marker set. `calling_it_twice_in_a_row_is_
  safe_idempotent` and `a_staged_bundle_with_no_readable_version_file_is_
  still_discarded_and_poisoned_as_unknown` (poisons `"unknown"` rather than
  panicking or silently trusting an un-versioned leftover) both pass.
- **`--self-test` runs the self-test path and exits WITHOUT starting the
  tray:** confirmed structurally via `main.rs` (§2's new
  `main_rs_exits_on_self_test_before_ever_reaching_the_resident_app_fitness_
  ff_m4_7` test) — `std::process::exit(...)` on the self-test branch appears
  textually BEFORE the fall-through `copilot_control_tower_lib::run()`
  call, so a `--self-test` invocation can never also become the resident

- **Anti-orphan fitness test genuinely fails if the wiring is removed:**
  spot-checked via mutation (§2) — confirmed.

## Defects found

**D1 (Medium, REPORTED, not fixed — routing to @agent-ta then @agent-me) —
the app-level launch-failure circuit breaker ADR-M4-001 ratifies is entirely
unimplemented.** `architecture.md` §3, `threat-model.md`, `redteam-
platform.md`, `windows-parity.md`, `prd.md`, and 4 more `docs/product-design/`
files all describe the SAME two-layer design: `ThrottleInterval` (the
"dumb," OS-level backoff, which IS implemented — `packaging/launchd/*.plist`
has `ThrottleInterval=10`) PLUS "an app-level launch-failure circuit breaker
(N non-zero exits in a window → stop relaunching, surface 'reinstall')" (the
"smart," in-process counterpart). The plist's OWN checked-in comment says
this second layer "lives in app code, not here" — but grepping the whole
crate for `circuit.breaker`/`crash.count`/`exit_count`/`non_zero_exit` (and
`reinstall`, which only appears in the UNRELATED "I couldn't start the
engine" CLI-spawn-failure copy from M1) turns up **zero** matches. This is
not flagged anywhere as an owner-gated/deferred item (`.copilot/wp/24.md`'s
own "Gaps" section lists only D-4-M4/D-3/minisign-custody/heartbeat-contract
— none of which is this) — it appears to have been silently dropped between
ADR ratification and implementation, unlike the wizard's D2/D3 gaps M3 QA
found (which at least had partial scaffolding). **Practical effect:** if the
CURRENTLY-running (`current/`) binary itself starts crash-looping for a
reason unrelated to a self-update (corrupted install, a bad non-update code
path, disk full, …), `launchd`'s `ThrottleInterval=10` will relaunch it
forever at a fixed 10s cadence with no escalation — there is no "stop
relaunching, tell Bob to reinstall" terminal state today. This does NOT
compromise the self-update rollback mechanism itself (§4's whole promote/
rollback chain is independently sound and doesn't depend on this breaker),
and it does not violate `KeepAlive`'s own invariant (relaunch-on-crash is
still correctly gated to non-zero exits, never a clean Quit) — so this is a
**hardening gap, not a security/trust violation**, but it IS a real,
documented-everywhere design commitment that was never built. Implementing
it is real design+code work (where does the exit-count state persist across
relaunches — a small file alongside the heartbeat/rollback-marker files is
the natural fit — and what UI surfaces "reinstall"), not a "small/safe" QA
patch. **Route to @agent-ta** (confirm the persisted-counter design, ideally
reusing the SAME `updater`-directory layout root `heartbeat.rs`/
`rollback_marker.rs` already establish) then **@agent-me** to implement +
test.
