## 2. Parse-never-compute / authoring policy (S4, D-1-M2 fallback)

`author_manifest` (`settings/authoring.rs`) assigns `rank` from the
published, hard-coded `tier_rank_base` table (personal=10 < department=20 <

## 3. The Leak wall (invariant #6) — adversarial, 2 defects found + fixed

Drove every `secret-*.yml` fixture plus hand-crafted adversarial YAML through
`guard::scan_for_secrets` directly and through the full
`authoring::author_manifest`/`commands::save_settings_at` pipeline. All
documented shapes (PEM block, GitHub/Slack token prefixes, AWS access key,
bearer token, JWT, `user:pass@` URL, inline `password=`/`api_key=` assignment,
mixed-case high-entropy blob, hex blob) were correctly refused before any
byte reached disk, and every `GuardError` was confirmed (via
`assert_secret_value_never_leaks`, which checks `Display`, `Debug`, *and*
`.message`) to never echo the offending secret text.

**Then I went looking for the shapes the fixture corpus didn't cover.** Two
real gaps found, both exploitable to smuggle a genuine credential into
`copilot.layers.yml` past the fail-closed guard:

- **A purely single-character-class high-entropy token was not scanned at
  all.** `is_high_entropy_token`'s original gate was `if class_count < 2 {
  return false; }` — so ANY string using only one character class (e.g. all
  lowercase) returned `false` unconditionally, *regardless of entropy*. A
  40-character random lowercase-only token (`auth:
  qwoeiruzmxnbvcpaslkjfghdtyuiqpwoeirutyfgh` — the shape of a lowercase-
  alphabet vendor token or a base32-lowercase credential) sailed straight
  through `scan_for_secrets` → `Ok(())`, in both `auth` and a `source.repo`
  query string. **Fixed**: added a second, higher-bar entropy tier
  (`>= 4.5` bits/char, vs. `>= 4.0` for the mixed-class case) for
  single-class tokens — measured against real English/snake_case-phrase
  entropy (`SOME_LONG_CONSTANT_NAME_HERE_FOR_TESTING` ≈ 3.63,
  `personal_department_organization_layer` ≈ 3.78, even a pangram-shaped
  `the_quick_brown_fox_jumps_over_lazy_dog` ≈ 4.42) to keep comfortable
  headroom below the adversarial probe's 4.59, so ordinary long identifiers/
  branch names are never falsely flagged. 3 regression tests added
  (`a_lowercase_only_high_entropy_token_is_refused`, the same via a repo-URL
  query string, and `ordinary_long_single_case_phrases_are_never_flagged`).
- **`scan_mapping_for_secrets` only ever scanned the map VALUE, never the
  KEY.** A secret embedded as the literal field NAME of an unmodeled `extra`
  entry (e.g. `ghp_1234567890ABCDEFabcdef1234567890AB: "innocuous value"`)
  bypassed the scanner entirely — `Ok(())`. **Fixed**: the key string is now
  run through the same `secret_reason_in` heuristics. Critical follow-on I
  caught in my own fix before shipping it: when the KEY is what matched, the
  field label must **not** echo the raw key text into `GuardError.field` —
  doing so would put the secret itself into the one place the module's own
  doc promises it never appears ("never echoes a secret" — field names the
  *location*, never the value). Used a fixed `"<redacted field name>"` label
  for this one case instead. 1 regression test added
  (`a_secret_hidden_as_an_extra_field_key_rather_than_its_value_is_refused`),
  which also asserts via `assert_secret_value_never_leaks` that the redacted
  label doesn't leak the secret either.

Both fixes are narrowly scoped to `guard.rs`'s two heuristic functions, add
no new dependency, don't touch `validate.rs`/`writer.rs`/`authoring.rs`'s
public contracts, and are covered by 4 new passing regression tests (149 lib
tests total, up from 145). Re-ran the full green suite (§1) after both
fixes — all still clean.

Nothing else escaped the scan in this pass: I also checked for
homoglyph/spacing evasion of the fixed-prefix checks (`ghp_ 1234...` with an
inserted space defeats the literal `contains(prefix)` check, but then the
token also no longer looks like a real vendor token to any consumer either —
same trade-off the module's own doc already accepts for the fixed-prefix
family) and confirmed the AWS-key/JWT/PEM detectors operate on raw bytes/
fixed anchors that don't have an analogous class-count blind spot.

## Defects found

**D1 (Medium, FOUND + FIXED) — `guard::scan_for_secrets`'s entropy heuristic
had a class-count blind spot.** A purely single-character-class (e.g.
all-lowercase) high-entropy token — a plausible real-world credential shape
— was never scanned at all, regardless of how random it was. Fixed with a
tuned second entropy tier (§3). 3 regression tests added.

**D2 (Medium, FOUND + FIXED) — `scan_mapping_for_secrets` never scanned map
KEYS, only values.** A secret embedded as a literal `extra` field NAME
bypassed the scanner entirely. Fixed, with the important follow-on fix (also
caught and corrected in this same session) that the redacted-key case must
never echo the offending key text into `GuardError.field` — a naive fix
would have introduced a NEW secret-leak path while closing the original one.
1 regression test added.

**D3 (informational, not blocking) — the WP's named fitness-test file layout
(`tests/fitness_manifest_never_destroy.rs`, `fitness_secret_lockout.rs`,
`fitness_managed_gate.rs`, `manifest_corpus.rs`) doesn't exist as separate
top-level files.** Every one of the named fitness PROPERTIES (preserve-
untouched, atomic-write, no-secret-persisted, security-key-lockout,
no-network-in-authoring, managed-gate, plain-language-errors, thin-skin) is
genuinely tested and passing — just organized as inline `#[cfg(test)]`
modules inside each owning file (`writer.rs`, `guard.rs`, `managed.rs`,
`authoring.rs`) rather than as separate `tests/` integration files. This is
a structural/organizational deviation from the WP's task brief, not a
coverage gap — I verified every named property has real, passing test
coverage before treating this as non-blocking. Worth a follow-up refactor
into the WP's intended file layout for discoverability, not release-blocking.

**D4 (informational, not blocking) — no literal crash-injection test for the
atomic write.** `atomic_write`'s crash-safety (temp file leaves the original
intact if killed before `rename`) is a structural guarantee of the
temp-in-same-dir+fsync+rename design, verified by code review and by the
"no temp residue after a successful/refused write" tests, but there is no
test that actually kills the process mid-write. Standard practice, not a
gap I'd block on.

## Verdict

**M2 = ACCEPT-WITH-FOLLOWUPS.**

The core M2 promise — a user can safely paste org/dept/personal repo URLs
without the app ever computing resolution, ever writing a security-sensitive
key, or ever losing/leaking anything — held under adversarial pressure, but
only after I found and closed two real credential-leak paths in the S3
guard's entropy heuristic and its map-key blind spot (D1/D2). Both are now
fixed, tested, and re-verified against the full green build/test/lint suite.
Every other invariant (parse-never-compute, the write allowlist, the
managed-domain-only gate, never-destroy, plain-language errors) held without
needing a fix. The headless UI sweep (built fresh this session, no
pre-existing Settings harness) confirms all 6 `SettingsState` shapes render
correctly with zero console/CSP violations and no false "saved!" state. D3/D4
are informational, not release-blocking.
