# TASK-287 candidate-versus-publisher-anchor architecture audit

## Verdict

No dependency-safe route currently exists to produce the TASK-287 **verified Control Tower candidate** using only the installed Developer ID Application identity and the working `ct-notary` profile. A Developer ID Installer identity is not cryptographically required to sign/notarize the User `.app` or its drag-install DMG, but the approved TASK-287/WP-815 threat model requires release credentials to become reachable only through an independently established publisher first-trust anchor. That anchor is absent. Directly invoking the app release implementation from this user session would produce, at best, a developer-signed/notarized artifact; it would not be the verified candidate required by TASK-287, PRD-23 AC-18/AC-20, WP-815, QA WP-824, or security WP-826.

This audit therefore rejects the apparent shortcut. No signing, notarization submission, installation, push, Actions enablement, candidate creation, release publication, repository edit, or system mutation was performed.

## Artifact boundary: two distinct things

### 1. Control Tower User app candidate

The shipping user artifact is `Copilot Control Tower.app` plus a drag-install DMG. The reviewed public release program:

1. builds the native User app from exact materialized source;
2. embeds and verifies the pinned `cc` helper;
3. runs headless Detect/setup and native watchdog proofs;
4. signs the app with `Developer ID Application`;
5. notarizes and staples the app;
6. creates and signs the DMG with the same Application identity;
7. notarizes/staples the DMG;
8. Gatekeeper-assesses both and runs `verify-user-install-artifact.sh` after copying the app off the mounted image.

The User app itself uses a per-user LaunchAgent and requires no root package. Its embedded supervision plist has `KeepAlive = { SuccessfulExit = false }` and `RunAtLoad = false`; installation of that watchdog is userland-only.

Therefore a Developer ID Installer certificate is **not an Apple-format dependency** for signing/notarizing the User app or DMG.

### 2. Publisher first-trust helper/package

The publisher bootstrap is a different artifact. It is a root-owned helper at `/Library/PrivilegedHelperTools/...publisher-bootstrap.app` plus a protected approval/anti-rollback record, installed from a zero-script flat package. Its purpose is not to ship to end users. Its purpose is to make release authority unreachable from mutable checkout/session code until exact public Git bytes and the approved source tuple are established.

That package requires a Developer ID Installer signature because Apple `productsign` will not accept a Developer ID Application identity for a flat Installer package. More importantly, WP-815 also requires an independently controlled signing/execution context, an out-of-band completed exact tuple/final package digest, root-owned staging, same-object Installer consumption, installed receipt verification, and atomic advancement of a separate root-owned version floor. Merely obtaining an Installer certificate without those controls would not close first trust.

## Why the direct app/DMG route is not a verified candidate

The current public entry `scripts/package-user-release` is deliberately a credential-free adapter. Its compiled launcher requires the canonical root-owned publisher bootstrap and preflights its ancestry and Developer ID identity before executing it. The anchor does not exist, so the supported route fails closed.

The inner `package-user-release.program` contains the app/DMG build, Application signing, notarization, stapling, Gatekeeper, and install-artifact verification logic. Running it directly, copying its logic, sourcing `.env.release.local`, or weakening the launcher would move release authority back into the exact mutable same-user checkout/session boundary that WP-815 treats as hostile. A process in that boundary can replace build inputs, signing targets, output paths, or the invoking program while preserving plausible logs. Apple signatures and notarization would then prove only that Team `3SYGVX2HB8` signed Apple-accepted bytes—not that the bytes came from the owner-approved ref/commit/tree.

Manual comparison of hashes displayed by the same session is not independent. Administrator authorization does not authenticate the requesting bytes. A read-only DMG or mode `0444` does not prevent selecting/replacing a different valid artifact through a user-owned parent. The legacy `/Applications` helper cannot be reused because the directory entry remains replaceable. The root-owned schema-1 receipt cannot authorize the candidate because it lacks the exact current app CDHash/bundle digest, final artifact digest, package/version identity, and independently approved freshness decision.

Thus this route can create an Apple-valid artifact but cannot satisfy these current requirements:

- TASK-287: candidate from immutable pushed source with packaged behavior verified.
- PRD-23 AC-18: signed artifact suitable for the clean-machine journey with rollback evidence.
- PRD-23 AC-20: durable commit/WP/QA/security/release provenance.
- WP-815: `No app candidate may be created from source-only evidence.`
- WP-824/WP-826: both approvals explicitly stop before candidate authority and require external first trust.

Calling that output a candidate would violate SOUL’s “say only what you can prove” rule and weaken the security posture.

## Alternatives evaluated

1. **Use Developer ID Application for the User app/DMG directly.** Technically produces Apple-signed/notarized bytes; rejected as a TASK-287 verified candidate because the invoking executor and inputs remain in the adversary boundary.
2. **Use Developer ID Application to sign the flat publisher package.** Impossible: `productsign` requires an Installer identity, as WP-828 proved with a real lookup.
3. **Use the existing `/Applications` publisher helper.** Rejected by WP-791/WP-815; same-user replacement exists before execution.
4. **Treat the root-owned schema-1 receipt as the independent anchor.** Insufficient: no protected executable exists and the receipt lacks candidate/package digest, signed-app identity, monotonic version, and freshness policy.
5. **Treat notarization as source authorization.** Rejected: notarization is Apple malware/distribution acceptance, not owner intent, exact Git provenance, or anti-rollback.
6. **Use GitHub Actions as the independent signer.** Unavailable and outside current architecture: Actions is disabled, the public repository has no secret-bearing release workflow, no reviewed OIDC/HSM/secret custody path exists, and enabling it was prohibited in this audit.
7. **Use an independently anchored manual/system-tools-only ceremony now.** No such executor, protected staging mechanism, independently delivered exact tuple, or protected policy ledger is presently provisioned. The same Terminal/user session is not independent under WP-815.
8. **Reuse a prior accepted 0.6.9 app/DMG submission.** Rejected: Apple acceptance history does not bind that prior artifact to commit `6d211617...`, tree `7625c7a...`, the current QA/security WPs, or current candidate metadata.

## Dependency-safe unblock paths

A verified app candidate becomes possible only after one of these preconditions is independently established:

### Chosen current architecture: publisher package first trust

1. Supply an independently controlled Developer ID Installer identity for Team `3SYGVX2HB8` in addition to the existing Application identity.
2. In an independently authenticated executor, re-fetch/materialize the exact approved public ref/commit/tree and build/verify the zero-script publisher package.
3. Sign the contained publisher app with Developer ID Application and the flat package with Developer ID Installer; notarize and staple both.
4. Complete an immutable owner-approved manifest binding canonical remote/ref, exact commit/tree, package identifier and monotonic version, app bundle ID/Team/CDHash/bundle digest, final signed-package SHA-256, prior version/version floor, and owner approval ID/time.
5. Deliver the manifest SHA-256 and tuple through a channel independent of the hostile user session.
6. In one attended trusted transaction, copy package and manifest into a newly created root-owned, non-group/world-writable staging directory; recompute and compare digests there; verify Installer signer/team/package identity, Gatekeeper/staple, closed BOM/no Scripts, payload/source tuple, and monotonic version.
7. Invoke `/usr/sbin/installer` on that same protected package pathname without returning to same-user code.
8. Immediately verify package receipt version and installed app/approval against the independently supplied tuple, including root-owned/no-ACL/non-writable ancestry, designated requirement, Team ID, CDHash, bundle digest, source ref/commit/tree, and notary/staple.
9. Only after success, atomically create/advance a separate root-owned authorization/version-floor ledger. Preserve prior anchor/ledger on failure.
10. Fresh independent QA and security must approve the real package/staging/install/rollback evidence.
11. Only then invoke the protected publisher bootstrap to produce the User app/DMG candidate from the exact immutable public ref. Stop after packaged artifact verification; TASK-298 alone owns publication.

Mandatory negatives: same-team package B substitution, version downgrade, user-owned pathname race, wrong source tuple, altered app/payload/receipt, package scripts/extra members, unsafe type/mode/ACL/ownership, Installer failure preservation, wrong installed receipt, and unauthorized rollback must all reject.

### Equivalent alternatives

- Install a separately provisioned and independently verified trusted bootstrap/helper that enforces the same immutable-source, credential isolation, exact-tuple, protected-output, and anti-rollback controls; or
- use an independently controlled build/sign service with equivalent identity custody and signed provenance, followed by independent artifact verification. This would be a new architecture and requires owner approval, implementation, QA, and security before use.

Neither equivalent exists today.

## Task disposition

TASK-287 must remain `in_progress` and candidate-blocked. The correct blocker is not “the app needs an Installer certificate.” The correct blocker is: **the verified candidate requires an independently established release-authority executor; the selected executor is the root-owned publisher bootstrap, whose first-trust package currently lacks both Developer ID Installer authority and the attended independent installation ceremony.**

The existing Application identity and working `ct-notary` profile are valid and sufficient once that executor exists. Do not recreate either credential. Do not produce or label a direct local app/DMG build as the verified candidate.
