# Milestone 2 Architecture — Settings (unmanaged/solo layer-manifest authoring)

Thin-skin (parse-never-compute) Settings surface: the user wires their own org/dept/personal repo
URLs, which are written into the layer manifest the engine (`cc`) reads. This document is the
buildable design: the contract Settings writes against, the never-destroy write boundary, the
invariant guards, the task/stream breakdown, ADRs, fitness functions, and the owner decisions.

Builds on the M1 WP (`.copilot/wp/1.md`): reuses RenderState/typed-DTO IPC, the mock-CLI fixture
strategy, the single-process/Accessory shell, the doctor timer, and the fitness-function discipline.

---

## 0. The critical contract question — WHERE is the manifest format defined? (investigated)

**Settings WRITES a layer-manifest file that `cc` CONSUMES.** The contract splits cleanly into a
FROZEN half (the app can build against it today) and an UNDEFINED-GAP half (needs a WS-A owner
decision — the M2 analogue of M1's per-layer-status D-1 gap).

### FROZEN — the app can build against these today

1. **Manifest READ/VALIDATE shape — `copilot.layers.yml`.** Authoritatively documented in this repo at
   `docs/reference/four-tier-topology.md §4`, and ENFORCED by the real consumer
   `claude-copilot/tools/cc/src/cc/core/ecosystem/manifest.py` (`REQUIRED_LAYER_FIELDS`,
   `load_layers`, `validate_layers`). Shape:
   ```yaml
   version: 1
   layers:                      # highest precedence FIRST; list order MUST agree with ascending rank
     - id: personal-pablo       # required, non-empty (label)
       role: personal           # required; OPEN vocabulary string (not a closed enum)
       product: claude          # required, non-empty; config-driven (knowledge|cli|claude|codex + more)
       rank: 10                 # required INT; UNIQUE; lower = higher precedence; list order agrees
       source:                  # required object
         repo: git@github-personal:me/claude-copilot-private.git   # required (>= a `repo` key)
         ref: main              # optional
         path: sub/dir          # optional (one repo can serve multiple layers)
       auth: ssh-personal       # required, non-empty (REFERENCE: alias name | anon | gh-device)
       activation: always       # required (always | includeIf:<glob>)
       unit: engineering        # optional; only meaningful for role=department (selection key)
   ```
   Required per layer (validated, hard-error with PLAIN-LANGUAGE messages, never a stack trace):
   `id, role, rank, product, source(.repo), auth, activation`. Ranks unique + integer + ascending +
   list-order-agrees (Nix-style error-on-equal-priority). `product` is carried metadata + grouping
   axis; it does NOT change resolution semantics (resolver still folds per-dimension).

2. **The config POINTER mechanism.** The engine finds the manifest via config key `layers.manifest`
   (`config.py` default `None  # path to copilot.layers.yml`), read by `resolve.py`/`update.py`/
   `freshness.py` via `resolve_key("layers.manifest")`. Stored in the MACHINE config
   `~/.claude/cc/config.json` (`config_paths.machine_config_path()`), written by `write_config()` as
   indent-2 JSON via a **dotted-set that PRESERVES all sibling keys**. Settable today via
   `cc config set layers.manifest <path>`. Related keys (do NOT touch from Settings): `layers.department`,
   `layers.lock_source`, `layers.lock_ref`.

### UNDEFINED CONTRACT GAP — needs a WS-A owner decision (D-1-M2, headline/blocking)

**No `cc` verb AUTHORS the manifest from user input.** Confirmed by inspecting the engine:
`load_layers`/`validate_layers` only READ + validate; `cc derive` builds the manifest from
`ecosystem.yml` (the MANAGED path — "nobody types a URL", ecosystem-architecture §4.1/§4.2);
`write_config` writes only the POINTER, not the manifest content. There is **no** `cc layers add`,
no `cc config set-layer --json`, nothing that takes `(tier, product, repo-url, ref)` and produces a
valid, correctly-RANKED layer entry. No `yaml.dump` of layers exists anywhere in the engine.

So if the app writes `copilot.layers.yml` itself, it must assign fields the user's pasted URL does
NOT carry:
- **`rank`** — precedence-of-record = *which layer wins in resolution*. (A fixed tier→rank table
  personal=10/dept=20/org=30/foundation=40 is a *published constant* — arguably render-not-compute —
  but the app owning it means the app owns resolution-ordering encoding.)
- **`product`** — a single URL box doesn't say which product; the 4×4 model fans org/dept/personal
  across 4 products.
- **`auth`** — SSH alias vs `anon` vs `gh-device`; depends on URL scheme + whether the repo is
  private, which the app must NOT probe (a network probe = compute).
- **`activation`/`id`/`unit`** — defaults (`always`/derived label/department-only).

**This is the exact M1 D-1 pattern** (CLI owns the computed thing; the app must not synthesize it).
The clean resolution is a thin CLI write-verb — the app renders the form and passes the choice back,
exactly like the CLI-computed merge-conflict chooser (invariant #1). **Until that verb exists, M2 can
build the reader/validator (S1), the never-destroy writer (S2), the pointer writer (S2), the guards
(S3), and the form UI (S7) against frozen contracts — but the manifest-WRITE-FROM-URLS assembly step
(S4) is decision-gated on D-1-M2.**

## 1. Invariant checks (all pass — with load-bearing guards)

- **#1 Parse-never-compute.** Writing user-entered URLs into `source.repo` is configuration INPUT,
  not computing ecosystem state. The resolver (`cc resolve`/`cc update`) still computes resolution
  FROM the manifest; Settings supplies inputs only and adds ZERO resolution/sync/merge/signature
  logic. **Confirmed.** The ONE gray area is `rank` assignment (resolution-precedence-adjacent) →
  resolved by D-1-M2 (push to a CLI write-verb) or the fixed published-constant table under sign-off.
- **#3 Never-destroy.** The manifest is a user-authored personal working file → read-modify-write,
  MERGE by layer `id`, PRESERVE every layer/field the UI didn't touch, atomic temp+fsync+rename,
  keep a backup, never truncate. The config.json pointer write reuses the dotted-set merge (preserve
  all sibling keys — e.g. `paths.*`). (S2, fitness fn "preserve-untouched".)
- **#6 Secrets never in config/git.** Repo URLs are NOT secrets. `auth` holds only a REFERENCE
  (alias name / `anon` / `gh-device`); credentials stay in ssh-agent/keychain/gh. A fail-closed
  pre-write scanner (S3) refuses any value matching a secret pattern (PEM header, `ghp_`/`gho_`/
  `github_pat_`, `AKIA`, `xox[bp]`, a `://user:pass@` URL) and strips embedded creds from pasted
  URLs. Nothing Settings writes ever reaches git (the manifest is machine-local, never committed —
  ecosystem-architecture §3.3). **Confirmed by construction + backstop scan.**
- **#4 Security posture never weakened / Convenience Backdoor (SOUL).** HARD RISK: "a settings panel
  that re-points the update feed" is the NAMED Convenience-Backdoor anti-pattern (SOUL §4, 50-ux P5,
  60-ui §74). Mitigation is load-bearing: S3 enforces a WRITE ALLOWLIST — the ONLY writable surface
  is `{a layer's source.repo/ref/path, product, role, unit, activation, id, rank, and the
  layers.manifest pointer}`. Settings physically CANNOT set `UpdateFeedURL, FoundationMirror,
  EcosystemSeedURL, HTTPSProxy, GitHubHost, AuthMode, AllowSelfUpdate, Deprovisioned, AdminContact,
  root_key/key_set/policy_signers, layers.lock_source/lock_ref` (forced/managed-domain-only or
  compiled-in trust roots, architecture §8.3). No update-feed field exists, ever.

### Managed vs unmanaged — the critical framing
On a MANAGED machine the manifest is produced by `cc derive` from the MDM-delivered `ecosystem.yml`;
Settings must NOT fight or overwrite it. **Settings-writes-repo-URLs is the UNMANAGED / solo /
early-adopter-author path** (at most the personal-tier row on a managed machine). A hard gate (S5):
if a forced-domain ecosystem is present (`CFPreferencesAppValueIsForced`), org/dept fields are
locked/hidden ("managed by your organization") and only the personal layer is editable if policy
allows. This honors Bob-first (Bob on a managed fleet touches nothing) AND the design's rejection of
"a settings-heavy tab-rich consumer chrome for Bob" (60-ui §74) — Bob's Preferences (50-ux §84:
schedule/notifications/MDM-status/launch-at-login) is a SEPARATE, read-mostly surface; repo-URL
Settings is the unmanaged/solo/author surface reached behind it.

### SOUL Feature-Filter verdict
Gate 1 (parse-not-compute): PASS (config input; rank gray-area pushed to CLI via D-1-M2). Gate 2
(essential job): PASS — an unmanaged/solo user or early-adopter author cannot wire their own layers
any other way without the terminal. Gate 3 (right-actor): PASS — no new Bob notification; honest
inline validation only. Gate 4 (trust-surface): PASS with the S3 allowlist guarding the Convenience
Backdoor; The Leak is impossible (local-only, no push, secret-scan); The Git Error To Bob is
answered (all errors plain-language via S1 messages + S6 DTO, never raw yaml/git).

## 5. ADRs

### ADR-M2-001: The manifest-authoring step belongs in the CLI (D-1-M2)
**Status:** Proposed (blocks S4). **Context:** No `cc` verb authors `copilot.layers.yml` from user
input; assembling it app-side forces the app to own `rank` (resolution precedence), `product`, and
`auth` — resolution-adjacent + guess-prone. **Decision:** Prefer a thin CLI write-verb
(`cc config set-layer`/`cc layers add --json`) that takes `(tier, product, repo, ref)`, CLI-side
produces the validated correctly-ranked layer, and echoes it back; the app renders the form and
passes the choice back (invariant #1 clean). Fallback (owner-gated): app assembles from a fixed
PUBLISHED tier→rank constant table + user product selection, with the CLI `validate_layers` as the
write gate. **Consequences:** Verb path keeps the app a pure skin; fallback ships without a CLI change
but puts rank/role encoding in the app. Reversible? Yes (a mapping/verb swap). **Alternatives
rejected:** App freely computes rank/product/auth incl. probing the repo — rejected (network probe =
compute; rank = resolution semantics; invariant #1).

### ADR-M2-002: Never-destroy manifest write — merge-by-id, atomic, preserve-untouched
**Status:** Accepted. **Context:** invariant #3; the manifest may be hand-authored and carry layers/
fields the UI never showed. **Decision:** read-modify-write, upsert edited layers by `id`, preserve
all other layers/fields byte-for-byte, temp+fsync+atomic-rename, keep a `.bak`; the config.json
pointer uses dotted-set preserving siblings (prefer shelling `cc config set`). **Consequences:**
Easier — a hand-authored manifest survives an app edit; a crash mid-write leaves the original intact.
Harder — no whole-file rewrite convenience. Reversible? Yes. **Alternatives rejected:** Serialize the
DTO back to a fresh file — rejected (clobbers untouched content + comments, violates never-destroy).

### ADR-M2-003: Write allowlist guards the Convenience Backdoor
**Status:** Accepted. **Context:** SOUL's named Convenience-Backdoor anti-pattern = a settings panel
that re-points the update feed/mirror/trust root. **Decision:** the writer accepts ONLY an allowlist
of layer source/product/role/unit/activation/id/rank + the `layers.manifest` pointer; every security-
sensitive key is a refused path; a fail-closed secret scan refuses/strips credentials. **Consequences:**
The one supply-chain-RCE surface is closed by construction, not discipline. Reversible? Yes.
**Alternatives rejected:** A generic key/value config editor — rejected (exactly the backdoor).

### ADR-M2-004: Settings is the unmanaged/solo/author surface, gated off managed fleets
**Status:** Proposed (D-2-M2). **Context:** managed manifests come from `cc derive`; Bob-first says
Bob touches nothing. **Decision:** forced-domain ecosystem present → org/dept locked, only personal
editable if policy allows; unmanaged → full editing. **Consequences:** Bob on a fleet is untouched;
solo/author users self-serve. Reversible? Yes.

## 6. Fitness functions (define now, enforce in CI)
- **preserve-untouched:** writing one layer never mutates another byte of the manifest, nor a sibling
  key of config.json (golden round-trip).
- **atomic-write:** an interrupted write (temp exists, no rename) leaves the original manifest intact.
- **no-secret-persisted:** every secret-bearing fixture is refused/stripped; no PEM/token/`user:pass@`
  ever lands in the manifest or config.
- **security-key-lockout:** the deny-list (UpdateFeedURL/…/policy_signers/lock_source/lock_ref) is
  exhaustive; a write attempt to any of them is refused; the allowlist is the only writable surface.
- **no-network-in-authoring:** the authoring path performs no network I/O (no repo probe).
- **managed-gate:** a forced-domain fixture refuses org/dept edits with a plain-language message.
- **plain-language-errors:** no validation path emits raw yaml/git/io text to the DTO (grep + tests).
- **thin-skin:** `src/settings/*` pulls no framework; no `cc resolve`/merge/sync logic in Rust config/.

## 7. Owner decisions (need sign-off)
- **D-1-M2 (BLOCKING, headline):** the manifest-authoring contract gap — add a `cc config set-layer
  --json`/`cc layers add` write-verb (A, recommended), or app-assembles-from-fixed-table + CLI-
  validates (B). S4 is blocked until chosen.
- **D-2-M2:** managed-machine scope — is Settings hidden entirely when managed (manifest owned by
  `cc derive`), or is the personal layer editable even when managed?
- **D-3-M2:** where `copilot.layers.yml` lives for a solo/unmanaged user, and whether M2 creates it if
  absent + sets `layers.manifest`. Proposed: `~/.copilot/copilot.layers.yml` (alongside
  `~/.copilot/manifest.local.yml`, ecosystem-architecture §3.3), pointer in `~/.claude/cc/config.json`.
- **D-4-M2:** `auth` provisioning seam — Settings records only the auth REFERENCE (`anon`/alias/
  `gh-device`); it does NOT provision the ssh key / device-flow token (that is wizard/M3). A private
  repo with no credential surfaces an honest "needs sign-in", never a raw git auth error. Confirm.
- **D-5-M2:** pointer write — shell `cc config set --json` (single writer, preferred) vs replicate the
  dotted-set JSON write in Rust.
