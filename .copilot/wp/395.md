# Bob-in-accounting connects to the org secret store — the actual end-to-end experience (read-only trace, 2026-08-02)

Persona: non-technical department member, fresh Mac, not the owner/admin. Control Tower 0.4.0, cc 2.2.0, cli-copilot v0.3.2. Every claim below is from code, live command output, or a doc — nothing inferred.

## Headline

**There is no "connect" path for Bob. There is no Connect button anywhere in the product, no `copilot`/`cc` verb that writes the credential the ladder reads, no admin tool that mints per-user store credentials, and no runbook that tells anyone how to hand Bob the two values. The needs-connect row is a sentence, and the sentence names two credentials with no destination, no source, and no action.** On top of that, the one row Bob would see named is the one row that is structurally unresolvable — verified live on the owner's own fully-working machine, which reports `needs-connect` for `infisical` while everything works.

---

## (a) The truthful walkthrough, in Bob's shoes

### Step 0 — install
Bob installs Control Tower.app (drag-install DMG). The app vendors **only** `cc` at `Contents/Resources/cc` (`scripts/verify-vendored-cc.sh:19,49`). The `copilot` service CLI is **not vendored and not installed by any onboarding stage** — `cc onboard`'s stage list has no CLI-install stage (`onboard.py` has no pip/install of `cli-copilot`; the only installer is the dev script `scripts/install-test-clis.sh`, described in `docs/40-initiatives/02-enac-self-onboarding/phases/phase-6-ecosystem-install-and-onboarding-proof.md` §5.2 as "install the two CLIs from source or a development checkout").

### Steps 1–5 — Welcome, Connect GitHub, Detect, What you're getting, Departments
These work. `cc auth` (GitHub device flow) and `cc layers` do not shell out to `copilot` (`commands/doctor.py`, `commands/layers.py` — no `resolve_executable("copilot")`). Bob signs in with a device code and picks his department. No mention of a secret store anywhere.

### Step 6 — "Your connections" (`wizard.swift:4574`)
The screen's intro promises, verbatim (`wizard.swift:4578`):

> "These are the connections Control Tower can prove are ready for you. **If your organization makes another connection available, it will appear here with a working Connect button.**"

`continueFromDepartments()` fires `loadConnections()` → `cc connections --json` (`wizard.swift:2482-2498`).

**What Bob actually sees depends on how far his machine got, and all three branches dead-end:**

- **Fresh Mac, no `copilot` binary** (the realistic day-one case): `_copilot_layers` fails → `result: "copilot-unavailable"`, `connections: []` (`connections.py:319-332`). The app renders `ConnectionsRender.unavailableDetail(report)` — the CLI's own detail, e.g. "The installed `copilot` reader rejected the request: …" (`connections.py:160`) — under a card headed **"Available to connect"** (`wizard.swift:4715-4719`). No button, no next step.
- **`copilot` present but org config not yet materialized** (step 6 runs *before* the Set up step that writes `ecosystem.yml`): `result: "org-config-unavailable"`, every store-checked row `no-store`, detail = "The organization's inherited configuration (ecosystem.yml) was not found on this Mac." (`connections.py:336-350`). Rendered verbatim by `connectionsNoStoreGroup` (`wizard.swift:4683-4696`) with a grey list of capitalized service names beneath it. No button.
- **Store configured but Bob has no credentials** (the case the design is *about*): `cc connections` runs `copilot infisical --json secret list …`, which exits 1, and the app renders the **raw CLI stderr verbatim**:

  > "The shared credential store could not be reached: Infisical credentials not configured.
  > Set INFISICAL_CLIENT_ID and INFISICAL_CLIENT_SECRET in your .env."

  Provenance: `connections.py:229-233` (`f"The shared credential store could not be reached: {detail}"` where `detail = result.stderr.strip()`), text from `cli-copilot/copilot_cli/services/infisical/main.py:33-38`, Rich-rendered to exactly that two-line string (verified). It reaches the screen through `store.detail` → `connectionsNoStoreGroup(storeDetail:)` (`wizard.swift:4685`, `user-settings.swift:778`).

**This is the product telling a non-technical accountant to edit a dotfile.** It is a raw developer error surfaced verbatim — the exact "Git Error To A Non-Technical Person" anti-pattern the app's own `cli-client.swift` rule ("never shows a raw error") and the copy deck's Quiet Instrument voice forbid. It is also **wrong advice**: the ratified design says the `.env` rung is not where these live (`credentials-and-boundary.md` §1.6.3; `cli.overlay.yml:182` "OS keychain: INFISICAL_CLIENT_ID/_SECRET (bootstrap, can't live in the store they unlock)"), and Phase 5 deliberately **emptied** the org `.env` (verified: `/Volumes/Dev/Sites/COPILOT/cli-copilot-internal/.env` contains zero `INFISICAL_*` keys).

**And the needs-connect row itself, when it appears** (`connectionNeedsConnectRow`, `wizard.swift:4661-4678`; identical in `user-settings.swift:756-772`): three stacked `Text` views — name, description, and `ConnectionsRender.needsConnectDetail(row)` (`render-state.swift:394-398`) producing "Needs 2 credentials in your organization's secret store: INFISICAL_CLIENT_ID, INFISICAL_CLIENT_SECRET." **There is no Button, no Link, no `NSWorkspace.open`, no pasteboard affordance, no contact, no help URL, no "ask your IT admin" sentence.** Confirmed exhaustively: the only `Button`s in `user-settings.swift` are "Try again", "Finish Copilot Setup", and four project-folder buttons (lines 488, 511, 813, 819, 825, 837, 880, 927). The promised Connect button does not exist anywhere in `native/`.

The schema anticipated it and it was never built — `connections.schema.json:60` describes `name` as "the `copilot <name>` command group — **this row's identity for a Connect action to reference**." Nothing references it.

**The row Bob would see named is a false negative — verified live on the owner's working machine:**

```
infisical   needs-connect  req=[(INFISICAL_CLIENT_ID,'any'),(INFISICAL_CLIENT_SECRET,'any')]  missing=[both]
store: {'type':'infisical','reachable':True,'scope':'prod:/shared','detail':None}
```
(19 other rows all `ready`.) The owner's credentials are correctly in the keychain (verified present under service `copilot-cli`, accounts `INFISICAL_CLIENT_ID`/`INFISICAL_CLIENT_SECRET`; values never read) and the store is reachable — yet the row says needs-connect. Cause: `cli.overlay.yml:157-159` declares the pair as **bare strings** → `from: "any"` → store-checked (`connections.py:_STORE_CHECKED_HINTS = {"store","any"}`, line 107), but `managed_store.py:56-66` `_NEVER_FROM_STORE` makes it **impossible by construction** for the store to ever hold its own bootstrap credentials. Contrast `DISCORD_BOT_TOKEN` at `cli.overlay.yml:200-201`, which carries `from: keychain` and correctly reads `ready`. So the one connection Control Tower will ever tell Bob to "connect" is permanently un-connectable, and permanently mislabelled for everyone who *is* connected.

### Step 7–8 — Projects, Set up
The `secret-store` stage runs, labelled to Bob as **"Connecting your organization's shared store"** (`wizard.swift:420`). `_provision_store` (`onboard.py:2068-2159`) calls `copilot infisical --json identity list`. Its own docstring concedes the design: *"the call itself requires successful org authentication to return anything at all — there is no anonymous/unauthenticated path"* (lines 2083-2086). On Bob's Mac there are no credentials, so the call fails and the stage returns `deferred` with:

> "The shared credential store could not be connected on this Mac. Setup kept this Mac's existing credentials and will continue without shared integrations." (`onboard.py:2120-2128`)

**This is the chicken-and-egg in one function: the stage whose job is to connect the store can only succeed on a machine that is already connected.** Even the theoretical bootstrap branch is a dead end: `identity create` (`cli-copilot/…/infisical/commands/identity.py:68-90` → `api_client.py:366-372`) POSTs `/api/v1/identities` and creates **only an identity object** — no universal-auth method, no client secret, no project membership, no role — and `_provision_store` then explicitly discards the response ("this stage never reads, stores, or forwards ANY field from it", line 2100-2103). Nothing is ever written to Bob's keychain.

`secret-store` is also the **one stage exempted from the completion rule** (`wizard.swift:2007-2010`), so setup declares success.

### Step 9 — "Your copilots are ready"
Bob gets a "Still to do" card containing exactly one sentence (`wizard.swift:5742-5748`):

> "Shared team connections are not available on this Mac yet. Your existing credentials were kept, and you can check again later from Control Tower."

**Terminal state.** "Check again later" is the only instruction, and checking again re-runs the same failing call. Nothing tells Bob who to ask, what to ask for, or what he'd do with an answer. Settings renders the same rows with the same absence of actions (`user-settings.swift:680-789`).

### Can Bob self-serve if someone hands him the two values?
The ladder's keychain rung reads **service `copilot-cli`, account = the secret NAME** (`secrets_ladder.py:47,112`); `managed_store._read_bootstrap_cred` (lines 165-179) tries that rung first, then the layer `.env`. So the mechanically correct action is:

```
security add-generic-password -s copilot-cli -a INFISICAL_CLIENT_ID -w '<value>' -U
security add-generic-password -s copilot-cli -a INFISICAL_CLIENT_SECRET -w '<value>' -U
```

**No shipped surface does this and no document tells Bob (or his admin) that it is the answer.** The only keychain *writer* in the entire ecosystem is `claude-copilot/tools/cc/src/cc/core/keychain.py:52-85`, called exclusively by `cc auth` for the GitHub device-flow token under a **different** service, `com.everyoneneedsacopilot.copilot.github` (`cc/core/config.py:147`). Grep for `add-generic-password` across `cli-copilot`, `cli-copilot-internal`, and `copilot-control-tower` returns **zero** hits. Bob's only path is a Terminal command he will never be given, or Keychain Access.app with hand-typed service/account names — both of which are exactly what the "non-technical user IS the spec" rule prohibits as a user-facing step.

Both are still open, and the shipped copy is worse than "undrafted" — it is raw stderr. | `credentials-and-boundary.md` §5.7, §5.9 |
| D-8 | Is there a documented "new team member joins" flow? | The closest is `ecosystem-use-cases.md` §Use Case 1 ("Rosa, day one"), which is a **shell-script walkthrough** (`./acme-onboard.sh`, `git clone git@github-personal:…`, `cc config add paths.layer`) and **never mentions the secret store at all**. `control-tower-admin-flow.md:31` names "a new hire" as a Govern-mode job story with no store step. **There is no new-team-member store flow, in any repo, at any fidelity.** | `docs/10-reference/ecosystem-use-cases.md:41-63`; `docs/03-design/control-tower-admin-flow.md:31` |
| D-9 | Admin side creates/delivers per-user credentials | `scripts/admin_bootstrap.sh` (2335 lines) only **reads** the brief's non-secret `store:` block into shell variables and does a bounded reachability curl (lines 10, 49-56, 427-441). It creates no identity, mints no credential, and delivers nothing to any user. The Admin app has no credential-delivery surface. | `scripts/admin_bootstrap.sh` |

**What `INFISICAL_CLIENT_ID`/`_SECRET` concretely are, per the code:** an Infisical **Universal Auth machine-identity** pair, POSTed to `/api/v1/auth/universal-auth/login` (`api_client.py:106-118`). Today they are effectively **org-wide** — one pair, held in the owner's keychain, with full read of `prod:/shared`. RD-1 ratifies the opposite ("Use a scoped, revocable per-machine identity; do not distribute the org-wide `ecosystem-admin` credential" — `phase-6-…-proof.md` §7 RD-1), and the only mechanism that could honour it is the verb that does not exist (D-4). **So the only way Bob gets working credentials today is for the admin to hand him the org-wide pair out-of-band — which is precisely what RD-1 forbids.** That is the real dead end: not "hard", but *"the only available action is the prohibited one."*

**Where the design says Bob receives them:** nowhere. `credentials-and-boundary.md` never contemplates a human-delivered bootstrap pair, because in its model rung 1 authenticates via team-gated OIDC (D-1) and there is nothing to deliver. The bootstrap pair is an implementation artifact of the Universal Auth shortcut, and no document assigns anyone the job of provisioning or delivering it.

|---|---|---|---|
| **G-1** | **The `infisical` row is a permanent false negative.** Bootstrap creds are declared `from: any` (store-checked) but are `_NEVER_FROM_STORE`. Fix at the declaration (`from: keychain`, matching `DISCORD_BOT_TOKEN`) **and** defensively in `cc` (exclude `_NEVER_FROM_STORE`-class names from store presence-checking, so no future overlay can reintroduce it). Verified live on the owner's machine. | `cli-copilot-internal` (`cli.overlay.yml:157-159`) + `claude-copilot` (`connections.py`) | **Low** |
| **G-2** | **Raw CLI stderr is rendered verbatim to a non-technical user**, including "Set INFISICAL_CLIENT_ID and INFISICAL_CLIENT_SECRET in your .env." `cc` must author plain-language, actor-routed copy for store-unreachable (invariant #1: the CLI computes the sentence) and never pass through `result.stderr`. | **G-3** | **No Connect affordance exists.** The step-6 intro promises "a working Connect button"; the schema reserves `name` as "this row's identity for a Connect action to reference." ### Sequencing note
G-1, G-2, G-3, G-7 are honesty fixes that stand alone and should not wait on the credential design. G-6 is the fork that governs G-4/G-5/G-12: if OIDC/team-gated auth (option b) is chosen, the bootstrap pair disappears and G-4/G-5 shrink to nothing for this credential class. **Deciding G-6 before building G-4/G-5 avoids building a credential-delivery pipeline the ratified design intends to delete.**
