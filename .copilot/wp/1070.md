# TASK-291 interim integrated framework security review

Scope: independent read-only review of the current uncommitted TASK-285 framework evaluation diff, the released TASK-284/TASK-296 contracts, WP-718, WP-966, WP-1052, WP-1054, reopened TASK-297 WP-1061, and the Initiative 06 framework abuse-case plan. The app is excluded. This is an interim rejection, not the final TASK-291 verdict. Exact released TASK-297 shared-tier inputs, the approved fleet census, final integrated code, and full evidence do not exist yet.

## Assets and boundaries

The reviewed boundaries are exact runtime prompt and tool policy, Claude/Codex credentials, signed layer and composed-content provenance, TASK-296 route/continuity evidence, runtime output and durable artifact identity, private personal evidence, one-attempt evaluation integrity, and the credibility of non-regression/effectiveness claims. The relevant actors are the owner/evaluator, the framework verifier, signed content publishers, Claude/Codex native runtimes, same-UID local processes, and model-generated tool requests.

## Blocking findings

1. P1 — Claude execution is deauthenticated under the adapter environment. The adapter supplies a fresh empty HOME and CLAUDE_CONFIG_DIR. An exact native Claude 2.1.232 `auth status --json` probe under the same four-key environment returned `loggedIn=false`, `authMethod=none`; normal installed status is authenticated. Readiness currently treats an executable digest as runtime readiness. A live Claude call therefore cannot be represented as ready until an auth-only, value-suppressing projection is implemented and the exact isolated environment passes a real auth-status probe.

2. P1 — Completion evidence was replayable across changed execution configuration. Before remediation, one adapter-issued Claude output returned true from `verify_authenticated_completion` for its original cell, for the same cell with a different `runtime_configuration_sha256`, and for the same cell with a different `tool_configuration_sha256`. The receipt bound only the older invocation envelope. Exact full-prompt, runtime-configuration, and tool-configuration identities must be included in issuance and verifier equality checks, with negative replay tests. The live stream accepted this finding and is patching it.

3. P1 — Codex layered attribution is not currently real. TASK-296 replaces the Knowledge resolver with one nearest-winner plugin `SKILL.md` projection for Codex. Organization/accounting plugin bytes for common specialists can be identical, so the path can mint a layered-looking source receipt without consuming attributable organization/accounting Knowledge. Each matrix variant must prove exact tier coverage and compose the signed Codex specialist projection with all applicable signed Knowledge contributions. Missing, substituted, duplicated, wrong-runtime, wrong-tier, and same-byte/wrong-source cases must fail.

4. P1 — The current receipt model cannot represent that real source composition. `ContentReceipt` requires exactly one `LayerContentReceipt` for each tier. It cannot record both a Knowledge repository and a Claude-agent or Codex-plugin repository at the same tier. The model must allow a canonical multi-product set per tier while requiring exact variant tier coverage, and the prepared source receipts must cross-check repository/ref/tree/signer/content against the content receipt instead of matching only a composed-content digest.

5. P1 — Claude specialist projection conflicts with safe-mode semantics. Native Claude 2.1.232 help states that `--safe-mode` disables custom agents. The adapter nevertheless materializes `.claude/agents/<specialist>.md` and invokes `--agent <specialist>`. A supported CLI-explicit or direct system-context projection must be used and proved through a real safe-mode invocation; filesystem presence is not consumption evidence.

6. P1 — Codex tool denial is post-action, not preventive. The native Codex runtime has the stable shell tool enabled, the adapter supplies a readable copied `auth.json`, and `--sandbox read-only` prevents writes but does not remove read-capable runtime tools. The JSONL parser rejects command/tool events only after the action has executed. A tool call could read credentials or other files before the run is rejected. The exact runtime must disable model tools before execution or run inside a boundary that denies child tool execution/read access while retaining only the parent runtime network/auth capability. A post-hoc event rejection is necessary evidence but not a security boundary.

7. P1 — Codex final-message identity is not bound to the precreated file. The adapter creates and closes the output file before launch, but records no initial dev/inode. Its first lstat occurs after the process returns, then it reads by pathname. A same-UID replacement during execution is accepted as the intended file. Retain the original descriptor/inode through execution, read through a no-follow descriptor, bind the final name to that inode, and add deterministic replacement and ABA negatives.

8. P1 — Personal non-leakage is incomplete before persistence. The generic shared-output scanner rejects `PERSONAL_ONLY` but accepts both `career_concern: synthetic concern about role scope...` and the private value without its marker, even though EVAL-07 oracle explicitly prohibits `career_concern` in shared output. Current flow stores output before criterion/hard-rejection judgment. Build a verifier-only, value-suppressing non-leakage projection from the private fixture/oracle and enforce it before runtime-output persistence and run completion.

9. P1 — AC-11 non-regression is not enforced. `compare_criterion_judgments` calculates `regressed` but still emits a VALID comparison. It does not reject a regression in safety/privacy, evidence discipline, user ownership, factual restraint, or applicable specialist craft, and it does not reject a newly violated criterion unless a separate hard-rejection rule happens to be triggered. Add exact protected-criterion and new-violation rejection tests.

10. P1 — One-attempt/cherry-pick authority is not implemented. `attempt_policy_sha256` is opaque, and no persistent matrix coordinator prevents multiple independent attempt-1 COMPLETED runs for one case/variant/runtime cell. Technical retry lineage exists only at record level and completed parents cannot be retried, but independent first attempts can still be selectively retained. Add a preregistered matrix ledger keyed by matrix/cell identity, atomically reserve attempt one, permit only enumerated technical retry reasons with complete lineage, and preserve every attempt.

11. P1 — Readiness is not provenance readiness. `_layer_statuses` checks only a semantic-version-shaped ref and nonempty signer list. It does not verify the tag signature, authorized signer, exact repository/tree/path, entitlement lease, canonical join/materialization, lock/disk identity, or variant-specific contribution. It can report ready for fabricated metadata. Readiness and run authority must consume canonical verifier-issued signed-layer receipts for the exact released TASK-297 identities.

12. P2 — Executable and subprocess lifecycle need stronger closure. `_executable_sha256` checks a path and later executes the path without retained inode identity. Process-group cleanup happens only on timeout, not cancellation, unexpected exceptions, or successful parent exit with surviving descendants. stderr is captured without a size bound. Bind the executed native inode or a private verified copy, verify interpreter-chain closure, terminate/reap the group on every exit path, and bound both stdout and stderr.

13. P2 — Known WP-966 artifact namespace race remains. `_verify_storage_snapshot` still verifies the root-to-type binding before the artifact and does not repeat the root-to-type name/inode check as its final operation. The same final ordering must protect writes and recursive lineage reads.

## Existing controls verified in this pass

The current work does use native Codex binary resolution instead of the Node launcher, a closed Codex terminal-event set with started/completed item pairing, empty inherited runtime environments, private Codex auth-file copying, subprocess sessions with timeout killpg, content-addressed private output storage, exact 28-cell preregistration, private-oracle exclusion from the user packet, criterion span digests, aggregate-score rejection, and output safety scanning. These are useful controls but do not close the blockers above.
