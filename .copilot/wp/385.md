# WP-384 protocol-chain gap closure: fold un-freeze + project-protocol deference (task 220)

## Fix 1 -- fold falls back to the newest verified layer when the winner is blocked

Root cause: `materialize()` (claude-copilot/tools/cc/src/cc/core/ecosystem/materialize.py) applied the policy gate only to the resolver's single OVERRIDE winner (`entry["winning_layer"]`); when that verdict was `block` it emitted a `blocked` op and moved on, never consulting `entry["shadowed"]` (the resolver's own nearest-shadowed-first list). Because the org tier has no wired signer by design (an intentional, untouched OWNER-GATED policy decision), org's `commands/protocol.md` permanently won the fold and permanently blocked, freezing that materialize slot at whatever foundation content had last successfully applied before the org scaffold existed.

Fix: added `_first_verified_shadow()` inside `materialize()` -- when the winner's verdict is `block`, it walks `entry["shadowed"]` in the resolver's own order and evaluates the SAME policy gate against each shadow candidate's own real source content; the first one that verifies is materialized in its place. The blocked winner's own prior lock pin (if any) carries forward untouched via the existing `_carry_forward()` helper -- it was never actually applied, so its recorded sha must not silently change. Every op emitted after a substitution carries a new `blocked_winner` field (the real, blocked winner's layer id) and a `reason` string naming it, so the report is honest: never silently indistinguishable from an ordinary, non-substituted change. If every shadowed layer is also blocked/held/missing, behavior is unchanged from before -- `blocked`, honest, nothing stale silently kept.

Schema: `update.schema.json`'s `changed[]` item shape (additionalProperties: false) gained two additive, nullable fields -- `blocked_winner` and `reason` -- both null on every ordinary change. Edited in both the canonical source (copilot-control-tower/docs/01-architecture/schemas/update.schema.json) and the vendored test fixture (claude-copilot/tools/cc/tests/fixtures/schemas/update.schema.json), kept in sync per that fixture's own "source of truth" comment.

Tests added (all passing): `test_materialize_falls_back_to_verified_shadow_when_winner_blocked`, `test_materialize_all_blocked_stays_blocked_honest_nothing_stale_kept`, `test_materialize_winner_verified_no_fallback_substitution`, `test_materialize_fallback_carries_forward_blocked_winners_own_prior_pin` (tests/test_ecosystem_materialize.py), plus an end-to-end `test_update_json_fold_fallback_reports_blocked_winner_and_validates_against_schema` (tests/test_update_contract.py) that runs the real `build_update_report()` pipeline through the schema validator.

Live proof (`cc update --json` from $HOME, cc 2.1.5): the `commands/protocol` entry in `changed[]` reports `"layer": "claude-foundation"`, `"blocked_winner": "claude-organization"`, `"reason": "winner claude-organization blocked: unverified; materialized verified layer claude-foundation instead"`, and no corresponding entry in `blocked[]`. `~/.claude/commands/protocol.md` is now byte-identical (sha256 `bc1c649e...`) to claude-copilot's current `.claude/commands/protocol.md` checkout, confirmed via diff -- the slot is un-frozen and tracking foundation again, including Fix 2's new clause. `claude-organization`'s lockfile entry has no `commands` pin at all (only `_meta`), confirming org's own content has still never applied, exactly as the fail-closed policy requires.

## Fix 2 -- project-protocol deference clause

Added a new "## Project Protocol Precedence" section at the very top of protocol.md's operating instructions (right after the "Agent-First Protocol is now active" opening line, before "## Command Argument Handling"), in both claude-copilot's foundation copy (`.claude/commands/protocol.md`) and claude-copilot-internal's org scaffold copy (`commands/protocol.md`, body kept byte-identical to foundation's, company-overrides header left untouched). Full clause text:

> ## Project Protocol Precedence
>
> **Before anything else below: check the current project for its own `.claude/commands/protocol.md`.** Claude Code resolves a same-named personal/machine-level command (this file, materialized to `~/.claude/commands/protocol.md`) over a project-level one by filename precedence alone -- so without this check, a project's own protocol would silently lose to this machine copy every time, even on a project that intentionally defines its own.
>
> 1. Read `.claude/commands/protocol.md` relative to the current project's root, if the project has one.
> 2. **If it exists and its content differs from this file:** follow the PROJECT file's instructions in full, in place of everything below this section -- this machine copy is superseded for the rest of this conversation. Declare it: `[Protocol: project]`. This is expected and correct for a non-software project (documents, presentations, image creation, etc.) whose protocol has nothing to do with the software flows below.
> 3. **If it is absent, or identical to this file:** this file governs, unchanged. Declare it: `[Protocol: machine]`.
>
> Do this check once, before any flow detection or agent routing below -- never mid-flow, and never skipped because a flow already seems obvious from the user's first message.

This is content-injection, the same precedent already established by CONSTITUTION.md's loading mechanism elsewhere in this same file (`## Constitution Loading`), deliberately not relying on Claude Code's own same-filename resolution order (verified live: personal/machine wins over project, v2.1.220, confirmed against current docs -- the opposite of the naive assumption). The `[Protocol: project]` / `[Protocol: machine]` declaration tag is a new, separate bracket tag alongside the existing `[PROTOCOL: TYPE | Agent | Action]` primary declaration and `[Constitution: Active/Not Found]` tag, following that same established pattern.
