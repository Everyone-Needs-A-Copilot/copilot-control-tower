# Independent Initiative 06 coverage and executability review

## Verdict

**Directionally aligned, but not yet complete or fully executable as a goal-driven delivery graph.** PRD-23 correctly centers the canonical transaction, truthful conformance, nearest-tier precedence, immutable provenance, evaluation, fleet propagation, security, and observed use. Those are the right structural outcomes for the stated Copilot Solution Ecosystem goal. However, several user-goal capabilities have no producing task or acceptance criterion, the release/security dependency order contradicts the initiative's own gate, and three required outcomes depend on explicit human or physical resources that agents cannot supply autonomously.

This review is evidence-bound to `SOUL.md`, `docs/01-architecture/12-architecture-guiding-principles.md`, Initiative 05 handoff/audit, Initiative 06 README and phase documents, `stream-plan.json`, PRD-23, TASK-278..294, and WPs 627-635. No implementation, task, dependency, or status was changed.

## Material gaps requiring graph/PRD correction

### 1. Security is ordered after the release it is supposed to gate

Initiative 06's integration sequence requires independent security review before fleet fan-out or app release. The live graph does the opposite:

- TASK-287 combines Control Tower implementation, signing, notarization, and publication, but depends only on TASK-286.
- TASK-291 (integrated security review) depends on TASK-287.
- TASK-288 (fleet propagation) does not depend on TASK-291.

This makes the security gate structurally incapable of gating publication or fan-out. Split TASK-287 into release-candidate implementation/package and publication, place TASK-291 between them, and make TASK-288 and the publication task depend on an approved security verdict. Because TASK-291 includes cross-tier entitlement/security evidence, either add a post-fan-out security verification or split security into pre-release and post-fan-out gates.

### 2. GitHub entitlement lifecycle has no producing task or explicit AC

FR-1 and abuse case AB-06 require entitled, unentitled, offline, and revoked behavior across the four product families. TASK-279 addresses canonical transaction, TASK-294 addresses signed Codex materialization, and TASK-291 reviews security, but no task owns implementation and deterministic fixtures for entitlement freshness, revocation, offline policy, or reauthorization. Add an implementation task and an AC requiring those four states with fail-closed/no-cross-tier-leak evidence. A review task cannot create a missing capability.

### 3. Protocol-led solution creation is not covered

The user's goal says protocol should assemble the right specialist workflow, operational capabilities should help people build solutions, and tc should preserve durable execution evidence. FR-7 mentions this, but no producing task or AC proves:

- protocol routes a representative request to the correct specialists;
- organization/department knowledge is actually consumed in that workflow;
- operational capabilities fail open when optional transports are absent;
- tc continuity survives the workflow.

TASK-284/285 evaluate layer contribution; they do not implement or verify protocol/tool/task continuity. Add a bounded protocol-and-capabilities integration task plus acceptance evidence. Without it, the initiative can prove installation and content precedence but not the core people-create-solutions journey.

### 4. "Materialize all four product families" is ambiguous and currently overclaims

The PRD says CLI and Knowledge materialize into a project, while the canonical transaction and definition-of-done focus on Claude/Codex. TASK-294 covers Codex plugins; there is no task that materializes CLI or Knowledge as project artifacts. Clarify the architecture contract: either add the missing materialization/consumption work, or state that CLI/Knowledge are resolved operational/source layers whose relevant outputs are consumed through Claude/Codex. Acceptance must name the actual consumer path; organization-content parity must not be inferred merely from source presence.

### 5. Signed tier-content release and pin update have no explicit owner

WPs 627/628 prove bounded Knowledge content and hashes, not an immutable signed organization/department release consumed by the fleet. TASK-294 can consume signed atomic sources but does not own releasing the Stream-C content repositories. TASK-288 requires an immutable nearer-tier release. Add an explicit task to review, commit, sign/tag/release organization and department content and update manifest pins, with dependencies before evaluation/fleet propagation. Name the signer and immutable reference evidence.

### 6. Normal-cadence propagation is not encoded

AC-13 requires a shared change to reach an eligible repo through normal cadence or Sync Now. TASK-288 can perform fleet fan-out but does not depend on TASK-286/287 and therefore can complete without proving the shipping app/cadence path. Add the cadence/app dependency and require evidence from the actual scheduled/Sync Now consumer path, not only a manual reconciliation invocation.

### 7. Reviewed-exception ownership overlaps and fleet write scope is not executable enough

Stream-B owns conformance code/structured exclusions, while Stream-F is assigned the reviewed exception registry. The registry path and write contract are not named, and TASK-288 metadata still uses placeholder/wildcard eligible-project paths. Assign one owner for the global exception schema/registry; give fleet work only explicit per-repository dispositions. Materialize and approve the exact eligible-repository list from the read-only census before mutation. Broad placeholders are not a safe executable ownership boundary.

### 8. TASK-282 completion is narrower than its title implies

WPs 627/628 explicitly approve a bounded Knowledge extension milestone, not native Codex organization materialization or broad organization execution-content parity. Keep the milestone, but ensure downstream acceptance does not treat TASK-282's completed status as AC-07/AC-09 proof. TASK-294 and the actual consumer-path evidence must close that gap; if Claude organization agents/commands are intended independently of Knowledge extensions, add an explicit producing task or narrow the acceptance language.

### 9. Evaluation claims exceed what the evidence can honestly prove

`SOUL.md` permits claims about process, context, and observable behavior, not blanket claims of better software or solution quality. PRD/Phase 2 language asks whether nearer layers create a "more methodologically sound solution" and discusses changing "solution quality." A small controlled comparison can demonstrate attributable company-specific decisions, methods, traceability, or artifact differences; it cannot establish general solution quality. Rewrite the claim/AC vocabulary accordingly and preserve the prohibition on blanket effectiveness claims.

## External human and physical blockers

These are real prerequisites, not agent-executable tasks:

1. **Owner semantic approval.** The PRD risk mitigation calls for owner review, but the graph has no explicit Pablo approval gate for organization/department guidance. Security/QA cannot ratify company intent. Add an owner-decision artifact before signing/release.
2. **Confidentiality decision.** WP-635 found a P1 tax-identifier exposure. TASK-293 can remediate files/history, but notification, rotation, and containment decisions require the owner. Record the owner decision and do not release dependent content before closure.
3. **Second Mac and ordinary user identity.** TASK-289 requires a second physical machine and normal GitHub identity/access that the agent cannot invent.
4. **Real non-technical participant.** TASK-290 requires recruitment/consent, participant criteria, observer, privacy/data-retention rules, and scheduling. Name the human owner and a stop condition; do not substitute an expert or simulated persona if unavailable.

The initiative should remain active rather than waive these outcomes when resources are unavailable, consistent with its own phase documents.

## Recommended minimal graph amendments

- Add entitlement lifecycle implementation/fixtures task.
- Add protocol + operational-capabilities + tc continuity integration task.
- Add signed organization/department release and manifest-pin task.
- Split Control Tower release candidate from publication; gate publication and fleet fan-out on independent security.
- Add post-fan-out security verification if TASK-291 remains pre-release.
- Make normal-cadence propagation depend on the actual shipping consumer path.
- Add owner semantic approval and confidentiality decision artifacts.
- Make the eligible fleet list and reviewed-exception ownership explicit.
- Narrow evaluation claims to attributable process/context/decision effects.

## Bottom line

PRD-23 is a strong architecture-and-conformance program, but in its current form it can finish with a canonical installer, truthful checks, content, and evaluation while still failing to prove the user's central promise: that an entitled person can start with protocol, receive the right layered help through the real consumer path, use operational capabilities safely, preserve durable task context, and propagate trusted updates without specialist intervention. The amendments above are required before the task graph is a comprehensive route to that goal.
