Threat model and sensitive assets
- Assets: the GitHub credential stored by GitHub CLI, private canonical source, Developer ID identity and Keychain authority, notary profile/API-key authority, immutable source identity, candidate bytes, and provenance.
- Actors: legitimate publisher, caller-controlled checkout/environment/config, another same-user process able to mutate user-writable checkout metadata, and the canonical GitHub service.
- Critical transitions: mutable/ad-hoc working-tree launcher -> Keychain; canonical remote -> detached checkout; untracked .git metadata -> source verifier; verified inner -> authority-bearing Bash program.

Controls that passed
- The caller-supplied GH_TOKEN, GITHUB_TOKEN, signing identity, notary profile/key identifiers/path, and legacy checkout authority are rejected before remote access. All seven authority-key negatives returned the expected generic key-name-only rejection and did not print values.
- /usr/bin/security is currently a root-owned regular non-symlink mode-0755 executable and satisfies codesign strict anchor-Apple verification. The patch uses the absolute path and rejects unsafe ownership/mode/signature.
- The current gh:github.com item is structurally the expected go-keyring-base64 envelope. Without printing or hashing the secret, a bounded probe confirmed strict Base64 decoding, a 40-byte recognized GitHub token, single-line content, and alphanumeric/underscore syntax. The service-only lookup currently selects the same item as service+account pablitoalejo.
- Invalid/trailing Base64 returns nonzero. Ambient caller Git configuration variables are absent from the clean Git environment. The fresh child cwd blocks the ordinary caller-repository test in WP-739, and the hermetic test slice passed startup/direct/foreign-parent/unsigned-helper/launcher identity/local immutable bootstrap controls.
- The helper command does not put the token in launcher argv or environment. Synthetic credential-protocol tests showed fill returns credentials only to Git while approve/reject emitted no helper output to the caller. Resolver/clone/value failures use generic classes/statuses rather than captured Git output.
- Reproducible launcher verification, codesign consistency, git diff --check, and Bash syntax passed. The four-file patch is bounded as WP-739 describes.

Blocking finding 1 — mutable outer regains a pre-verification GitHub credential (high)
- WP-721 required that no GitHub token or other release authority reach mutable repository program bytes before those exact bytes are authenticated by a non-circular trust anchor. WP-729 met that ordering only because outer Git had no credential.
- WP-739 now calls resolveRef -> trustedGit -> the inline shell helper -> `/usr/bin/security find-generic-password -s gh:github.com -w` before clone, Git-object comparison, reproducible launcher proof, or immutable-inner execution. The Keychain value therefore reaches a helper program whose command string is authored by the current working-tree launcher before that launcher is authenticated.
- The current launcher remains user-owned, user-replaceable, ad-hoc signed, has no TeamIdentifier, and has no internal designated requirement. Its adjacent Swift source/binary/manifest are a circular, user-writable identity set. `codesign --verify` proves self-consistency, not reviewed/pushed identity.
- A bounded live Keychain probe demonstrated that an ordinary same-user process can read the item non-interactively; only structural booleans were emitted. Consequently a modified/recompiled outer can replace the helper body with exfiltration and obtain the GitHub token before any immutable-source control runs. Keeping the token out of argv/environment does not authenticate the code that requests it.
- This is the prior WP-721 exploit class narrowed to the GitHub credential. It is release-blocking even though signing/notary inputs remain deferred.

Blocking finding 2 — repository-local config remains an executable authority root (high)
- `trustedGit` disables system/global/includes and starts in a fresh cwd, but every `git -C <checkout>` still reads `<checkout>/.git/config`. The command-line configuration does not set `core.fsmonitor=false` or otherwise close repository-local executable hooks.
- Focused adversarial reproduction created a disposable repository with local `core.fsmonitor=/usr/bin/false`, then ran the exact config-free/status-style Git command used by Swift verification. Git trace proved `fsmonitor process '/usr/bin/false' returned failure`, yet `git status` returned status 0. This demonstrates execution of a repo-local configured program inside the supposedly trusted verification command.
- The initial clone creates a benign config, but `.git/config` and hook paths are untracked and user-writable. A same-user actor can mutate them after clone; clean status and Git-object comparisons do not cover `.git`. The streamed immutable program is launched with GH/signing/notary authority already in its environment and immediately uses plain/repo-aware Git, including `git status` in `release_verify_checkout`. A malicious fsmonitor/hook can therefore execute in an authority-bearing environment while verification still reports a clean status.
- WP-739's caller-current-directory test is useful but insufficient: it proves only that Git does not inherit the launch repository. It does not test or neutralize the target checkout's local config, hooks, or config mutation between verification stages.

Additional hardening findings (non-blocking relative to the two high findings)
- Keychain lookup binds service `gh:github.com` but not account. The current default item is account `pablitoalejo`; duplicate service items/search-list changes can make selection ambiguous. Bind and validate the intended account/identity or fail on ambiguity.
- Token validation checks only a prefix. It should reject CR/LF/NUL, require the exact supported token character set and length family, and make the go-keyring envelope parser strict. Synthetic multiline input passed the prefix case even though Git discarded the injected lines in the tested fill path; fail-closed validation is still warranted.
- The inline helper ignores get/store/erase action and credential input. Current synthetic tests found no approve/reject output leak, but it should answer only `get` for exact protocol=https and host=github.com, and emit nothing otherwise.
- UUID temporary directories are removed on normal return, and the per-user temporary parent limits cross-user exposure. SIGKILL/crash can leave a private-source clone behind; document or add safe stale-directory cleanup after the primary trust flaws are resolved.

Required remediation
1. Restore the WP-721 ordering for the GitHub credential. The mutable/ad-hoc repository launcher must not query Keychain. Use a non-circular trusted bootstrap (for example a separately installed Developer-ID-signed/admin-protected bootstrap, or an independently authenticated signed source/tag path that needs no pre-verification Git credential). Authenticate the exact bootstrap before it may request Keychain access.
2. Treat checkout `.git` metadata as untrusted. Ensure every pre- and post-authority Git operation cannot execute repository config, hooks, fsmonitor, filters, helpers, pagers, or external commands. Add an exact malicious checkout-local `core.fsmonitor`/hooksPath/helper test that attempts an authority marker and must remain absent across Swift verification and the authority-bearing program's repeated checks.
3. Bind Keychain service plus intended account, reject ambiguous/multiple records, strictly parse the known envelope, enforce single-line exact token syntax/length, and implement the Git credential helper protocol for `get` plus exact GitHub host/protocol only.
4. Repeat independent QA/security against the exact remediation. Do not commit/push or run the candidate bootstrap until both high findings are closed.
