# Copilot Ecosystem Conformance Harness — Design Specification

**Status:** Proposed. Design only — no implementation code is written by this document.
**Date:** 2026-08-10.
**Purpose:** make "is the ecosystem correct?" a command you run, not a judgement call. The harness must FAIL today against the known-bad state the audit found, and pass after remediation.
**Inputs:** `docs/ecosystem-audit-open-questions.md` (all 27 owner answers ratified), `copilot-ecosystem-gap-report.md`, `RUBRIC.md` (13 dimensions), the four `FINDINGS-*.md` passes.
**Method note:** every design decision below was traced against the running code on this machine, not against the docs. Where the audit's own text disagrees with what the code does, the code wins and the divergence is called out inline.

## 1. Where it lives — decision and trade-off

### 1.1 Decision

**The harness lives in `/Volumes/Dev/Sites/COPILOT/claude-copilot/tools/cc`**, shipped as:
- a library package `src/cc/core/conformance/` (the checks), and
- a command `src/cc/commands/conformance.py` (`cc conformance ...`), and
- a test suite `tests/conformance/` (the pytest face of the same checks).

### 1.2 Evidence for `cc`, against `cli-copilot-internal`

The task framing offered `cli-copilot-internal` on the reasoning that "the CLI owns ecosystem-state computation." Traced on this machine, that premise is false for *this* CLI. There are two different programs and the ecosystem one is `cc`:

- `/Users/pabs/.local/bin/cc` is a shim whose shebang is `/Volumes/Dev/Sites/COPILOT/claude-copilot/tools/cc/.venv/bin/python`, importing `cc.main:app`. Its verb list includes `resolve`, `doctor`, `freshness`, `update`, `deprovision`, `layers`, `workspace`, `reconcile`, `extensions`, `onboard`, `env` — i.e. **every** verb the ecosystem-state contract is made of.
- `/opt/homebrew/bin/copilot` imports `copilot_cli.main:app` from `cli-copilot-internal`. Its test suites are `test_cloudflare.py`, `test_coolify_tier_fallback.py`, `test_infisical_base_url_real_overlay.py`, `test_discord_install.py`, `test_overlay_composition.py`. It is an **infrastructure/services** CLI (Cloudflare, Coolify, Infisical, Discord). It contains no tier resolver, no layer fold, no project-integration contract.
- The resolution code is unambiguously in `cc`: `tools/cc/src/cc/core/ecosystem/resolver.py` (the pure rank fold), `manifest.py` (`validate_layers`, the equal-rank hard error), `dimensions.py` (the override/accumulate table), `discovery.py` (per-layer contributions), `project_integration.py` (69 KB; `_CLAUDE_REQUIRED_LOCK_PATHS`, the five-value classification ladder, contract `project-integration` v1).

This matches the stored memory *"Four programs, two names"* and corrects the docs. Putting an ecosystem-conformance harness in `cli-copilot-internal` would force it to **re-implement** resolution outside the code that computes it — precisely the failure mode `copilot-control-tower`'s invariant #1 ("parse, never compute") exists to prevent, and precisely how the audit's own RC-3 came to contradict `RUBRIC.md`'s Divergence 2 (two readers of the same fact, computing it separately, disagreeing).

### 1.3 Evidence for `cc`, against a new dedicated repo

- A standalone repo cannot assert the contract without vendoring `_CLAUDE_REQUIRED_LOCK_PATHS`, `_CODEX_REQUIRED_LOCK_PATHS`, `_CLASSIFICATION_PRECEDENCE`, `_CLAUDE_ACTION_TARGETS`, `_MANAGED_OUTPUT_TARGET_KINDS`, and `_customized_framework_path_allowed`. A vendored copy drifts, and a conformance harness that has drifted from the contract is worse than none.
- It would add a 17th component repo to a fleet whose stated #1 pain is per-repo fan-out — the harness would immediately become one more thing to fan out.
- The cautionary precedent is on disk: `copilot-control-tower/src-tauri/tests/` holds **40** `fitness_*.rs` files that scan a retired `src-tauri` tree with the CI job disabled (stored memory *"Invariants stated, not enforced"*). Detached fitness functions die. Co-located ones do not.

### 1.4 Evidence for `cc`, on infrastructure that already exists

`tools/cc/tests/` contains **108 files**, including exactly the scaffolding this harness needs:

| Existing asset | Why it matters here |
|---|---|
| `tests/conftest.py` `_isolate_machine_config` (autouse) | Already redirects `CC_MACHINE_ROOT` and `CC_GLOBAL_MEMORY_ROOT` to `tmp_path`, **and** checksums the real `~/.claude/cc/config.json`, `~/.claude/cc/secrets.env`, `~/.claude/memory/{entries,.gitignore,copilot.lock}`, and **all three real `copilot.layers.yml` paths** before and after every test, failing loudly on any change. This is the isolation contract, already written, already battle-tested by a real incident. |
| `tests/fixtures/schemas/` (17 schemas incl. `resolve.schema.json`, `workspaces.schema.json`, `doctor.schema.json`, `layers.schema.json`) | The vendoring convention and the `Draft202012Validator` + `referencing.Registry` pattern (`test_layers_contract.py`) are established. `conformance.schema.json` slots straight in. |
| `tests/test_ecosystem_resolver.py` (19 tests) | The pure fold is already covered — including shadow ordering, cross-product isolation, override-stale, equal-rank error, and arity independence. The harness must not duplicate any of it. |
| `tests/fixtures/corpus/healthy-clean-fleet.json` | A vendored fleet corpus already exists and is already used for a field-set parity assertion against `cc doctor --json`. The harness extends this idea to a *known-bad* corpus. |
| `tests/integration/` (`test_project_integration.py`, `run_integration_tests.sh`) | An established "run real `cc` via subprocess against a real git project" pattern with a `CC_BIN` env seam. Layer 5 reuses it. |

### 1.5 The trade-off, stated plainly

**What we sacrifice:** `claude-copilot` is itself one of the systems under test. RC-1 (hook installed by nothing), RC-3 (orphan release tags), RC-4 (template lock), and RC-6 (`.mcp.json` gitignored) are all defects in `claude-copilot`'s own installer commands, release-cut process, and `.gitignore`. A harness that lives inside the repo it audits can, in principle, be weakened by the same commit that breaks the thing it guards.

**Why that is acceptable, and how it is mitigated structurally:**
1. **The regression checks assert against artifacts outside `claude-copilot`.** RC-2 asserts on `codex-copilot/scripts/`; RC-3 asserts on `~/.config/copilot/copilot.layers.yml` pins *and* `codex-copilot`'s tag topology; RC-5 asserts on 11 tier-variant repos' `copilot.layer.yml`; Layer 3 asserts on ~70 repos under `/Volumes/Dev/Sites`. A `claude-copilot` commit cannot silently satisfy them.
2. **Deletion is a visible red diff.** Each RC check is registered by id in `registry.py` and the registry has a completeness test (`test_all_root_causes_have_a_registered_check`) that hard-fails if an RC id disappears. You cannot quietly drop a check; you have to delete two things and explain it in a PR.
3. **It gates the release.** The checks run in `claude-copilot`'s own workflow, so a release cannot be cut with the RCs re-broken — closing the loop the disabled `fitness_*.rs` CI job left open.

**Is it reversible?** Yes. The check bodies are pure functions over paths and JSON with no `cc`-specific state; if a dedicated repo is ever justified, `src/cc/core/conformance/` lifts out wholesale and re-imports `cc` as a dependency. The command wiring is one `add_typer` line.

**Quality optimized:** truth-preservation (the checks and the contract cannot drift apart). **Quality sacrificed:** auditor independence. **Reversible:** yes.

## 3. Architecture

### 3.1 Shape

```
                     ┌──────────────────────────────────┐
   operator ────────▶│  cc conformance check|report|…   │  commands/conformance.py
                     └──────────────┬───────────────────┘
   pytest ──────────▶ tests/conformance/  (same checks, test face)
                                    │
                     ┌──────────────▼───────────────────┐
                     │  core/conformance/registry.py    │  check ids, layers, severities
                     │  core/conformance/report.py      │  envelope, roll-up, NO averaging
                     └──────────────┬───────────────────┘
        ┌──────────┬────────┬───────┴────┬──────────┬────────────┐
        ▼          ▼        ▼            ▼          ▼            ▼
      tier.py   stack.py  dimensions/  lock.py  roundtrip.py  root_causes.py
       (L1)      (L2)       (L3)        (L4)      (L5)          (L6)
        │          │        │            │          │            │
        └──────────┴────────┴─────┬──────┴──────────┴────────────┘
                                  ▼
                   EXISTING cc ecosystem modules (never re-implemented)
        resolver · manifest · discovery · dimensions · extensions_resolver
        project_integration · project_locking · projects · lockfile · freshness
```

### 3.2 Five architectural rules

1. **A check never computes ecosystem state it can ask `cc` for.** If a verdict needs resolution/sync/classification logic, the check calls the existing module. New computation is allowed only where §2.4 says nothing exists.
2. **Every check is a pure function of (inputs) → `CheckResult`.** No check mutates anything, ever. Mutation lives in exactly one place — Layer 5's round-trip — and only inside a `tmp_path` clone.
3. **Evidence is mandatory and specific.** A `CheckResult` with `verdict=FAIL` must carry `evidence: list[Evidence]` where each entry is `{kind, path, expected, actual, detail}`. "Failed" without a path and an actual value is a harness bug, caught by `test_every_failure_carries_path_level_evidence`.
4. **Never roll up to a single number.** `RUBRIC.md` §4: "Do not roll up to a single health percentage — S0 and S3 are not commensurable." The report emits counts per severity per layer and refuses to average. Enforced by `test_report_has_no_aggregate_score`.
5. **Three verdicts, plus a fourth for honesty.** `PASS` / `FAIL` / `NA` (dimension does not apply to this class) / `UNKNOWN` (the harness could not determine — e.g. no network in full mode). `UNKNOWN` never counts as `PASS` and drives exit code 2, never 0. This is the `fitness_no_fabricated_healthy` invariant restated.

### 3.3 Check identifier scheme

`<layer>.<area>.<name>` — stable, greppable, quotable in a remediation ticket.

```
tier.precedence.nearest_wins
tier.shadow.substance
stack.pin.ancestry
repo.d04.hook_present
lock.template.uniqueness
rc.rc3.orphan_release_tags
```

Every id is registered once in `registry.py` with `{id, layer, severity, applies_to_classes, mode(fast|full), summary, remediation}`. `cc conformance explain <id>` prints that record plus the last observed evidence.

### 3.4 Severity mapping

Reuse `RUBRIC.md` §4 verbatim — S0 (systemic, no repair path) / S1 (fan-out, O(repos) manual) / S2 (correctness, bounded) / S3 (cosmetic). Severity is a *property of the check*, declared at registration, not computed per repo. `--fail-on S1` means "exit non-zero on any S0 or S1 failure."

## 4. The six layers

Notation: **[F]** runs in fast mode, **[FULL]** only in full mode. Severity in brackets.

### Layer 1 — Tier / hierarchy resolution

**Proves:** foundation(40) → org(30) → dept(20) → personal(10) resolves correctly for content, config, skills, and agent extensions; nearer tiers shadow farther ones; and a tier declaring something *empty* does not silently shadow real content upstream.

**Wraps:** `resolver.resolve_layers`, `manifest.validate_layers`, `discovery.discover_contributions`, `extensions_resolver.resolve_extension`, `cc resolve --explain --json`, `cc env`.

### Layer 3 — Install conformance per repo (the 13 rubric dimensions)

**Proves:** the 13 dimensions as executable assertions across every reachable repo, producing per-repo pass/fail with the specific failing evidence. This is the machine-readable successor to the audit.

**Wraps:** `project_integration` (in-process), `cc workspace --all --json` (enumeration), `cc workspace verify --json` (parity canary), `cc reconcile assess --json` (full mode), `fitness-check.sh` (full mode, per repo).

## 5. Fixture and isolation strategy

### 5.1 The two-world rule

Every test runs in exactly one of two worlds, declared by which fixture it requests. There is no third option and no test may straddle.

**World A — Synthetic (default; all of L1/L2 semantics, all of L4 logic, all of L5).** A complete fake ecosystem built under `tmp_path` by the `fleet` fixture. Nothing outside `tmp_path` is read for state or written at all.

**World B — Machine truth (L1/L2/L3/L4 assertions about *this machine*).** Reads the real manifest, the real tier repos, and the real ~70 project repos, in **strictly read-only** mode, and is enforced as read-only by a tripwire rather than by discipline.

### 5.2 World A — the `fleet` fixture

`tests/conformance/conftest.py` provides a `FleetFactory` that builds, in `tmp_path`:

```
tmp_path/
  home/                              # $HOME, HOME, XDG_CONFIG_HOME all point here
    .claude/cc/config.json           # synthetic machine config (via CC_MACHINE_ROOT)
    .config/copilot/copilot.layers.yml   # synthetic manifest, N products × M tiers
  tiers/
    <product>-copilot/               # rank 40  — real `git init`, real commits, real tags
    <product>-copilot-internal/      # rank 30
    <product>-copilot-<unit>/        # rank 20
    <product>-copilot-private/       # rank 10
  projects/
    reference/                       # the golden install, materialized from a manifest
    degraded-<name>/                 # one directory per known-bad shape
```

Builder API (fluent, so a test reads as the scenario it encodes):

```python
fleet = FleetFactory(tmp_path)
fleet.product("claude").tier("foundation", rank=40).contributes("agents", {"cw": "real org content"})
fleet.product("claude").tier("personal", rank=10).contributes("agents", {"cw": ""})   # the empty-shadow case
fleet.pin("claude", "foundation", ref="v1.0.0", orphan=True)                          # the RC-3 case
fleet.project("degraded-no-hook").install(reference).remove(".claude/hooks/copilot-hook.sh")
fleet.build()   # -> FleetHandle{manifest_path, home, projects, env}
```

Four properties make this the right shape:
- **Real git, not mocks.** Tiers are real repos with real commits and real tags, because ancestry (RC-3) is a *git* property and a mocked repo cannot fail the way the real one does. `fleet.pin(..., orphan=True)` reproduces the orphan snapshot with `git commit-tree` against no parent — the harness's ability to detect RC-3 is itself tested.
- **Arity-independent.** The factory takes N products × M tiers. Layer 1's fold checks run against a 5-tier and a 2-tier fleet as well as 4, matching the resolver's own arity-independence guarantee, so nothing hardcodes "4".
- **Named degradations, not ad-hoc edits.** Each degraded project reproduces a shape actually observed in the audit and carries the citing repo in a docstring, so a fixture cannot drift into testing an imaginary failure.
- **Reference install as data.** `tests/conformance/fixtures/reference-install/manifest.json` describes the golden tree (paths, modes, ownership, checksum policy). Layers 3 and 5 both consume it, so "what correct looks like" is defined once.

### 5.3 World B — the read-only tripwire

Machine-truth checks inherit the existing `_isolate_machine_config` autouse fixture (which already guards `~/.claude/cc/config.json`, `~/.claude/cc/secrets.env`, `~/.claude/memory/{entries,.gitignore,copilot.lock}` and **all three** real `copilot.layers.yml` paths) and add a `machine_readonly` fixture that generalizes it:

1. **Before:** record `(path, mtime_ns, size, sha256)` for every path the run is about to read — the manifest, each tier repo's `.git/HEAD` + `refs/`, each project's 13 dimension paths.
2. **During:** all filesystem access goes through a `ReadOnlyFS` adapter that raises on any write call. Subprocesses are launched with `CC_CONFORMANCE_READONLY=1` and, on macOS, an env-scoped `TMPDIR` inside `tmp_path` so a stray temp write lands in the sandbox.
3. **After:** re-record and assert byte-identity. Any change fails the whole run with the offending path, in the same fail-loud style the existing fixture uses.
4. **Git safety:** only plumbing that cannot mutate is permitted — `rev-parse`, `merge-base --is-ancestor`, `rev-list --count`, `for-each-ref`, `check-ignore`, `ls-files`, `status --porcelain`. `fetch`, `gc`, `checkout`, `worktree`, and anything writing `.git/` are refused by an allowlist, not a denylist. This matters concretely: `git worktree list` on `convoco` would otherwise be tempting, and pruning is a mutation.

Two sentences, for the record: **Every test runs against either a synthetic fleet built in `tmp_path` — temp `$HOME`, a generated `copilot.layers.yml`, and real-git fake tier repos — or, for machine-truth checks, against the real machine in strictly read-only mode enforced by a pre/post SHA-256 tripwire over every path touched. No real repo is ever a test's write target: Layer 5's round-trip clones its subject with `git clone --local --no-hardlinks` into `tmp_path` and runs the installer there, and the existing autouse fixture already fails the suite if the real machine config, memory root, or any of the three real `copilot.layers.yml` paths changes.**

### 5.4 Baselines — how "fails today, passes tomorrow" is operationalized

`tests/conformance/baselines/2026-08-10-known-bad.json` freezes today's verdict for every check id, per repo. Three uses:

- **Proof of detection.** `test_baseline_captures_every_known_root_cause` asserts the baseline contains a FAIL for each of RC-1…RC-6 plus Q24/Q25. If the harness ever stops detecting a known-bad condition, this goes red.
- **Regression gate.** `cc conformance check --baseline <file>` exits **3** on any check that was PASS and is now FAIL, independently of the absolute pass rate. Remediation cannot silently break something else.
- **Progress ledger.** `cc conformance report --baseline <file>` shows fixed / still-failing / newly-failing counts — the owner's evidence that remediation moved the number, per severity, never averaged.

### 6.4 Exit codes

| Code | Meaning | When |
|---|---|---|
| **0** | Conforms at the requested threshold | No check at or above `--fail-on` failed. `UNKNOWN` verdicts never produce 0. |
| **1** | Conformance failure | At least one check at or above the threshold failed. The expected code today. |
| **2** | Harness could not run | Missing dependency, unreadable manifest, `cc` not importable, read-only tripwire fired. **Never conflated with 1** — "we could not tell" is not "it is broken," per `inv.no_fabricated_healthy`. |
| **3** | Baseline regression | With `--baseline`: something that passed now fails, regardless of the absolute rate. |

### 6.5 pytest face

Every check is reachable as `pytest tools/cc/tests/conformance/ -q`, so CI needs no bespoke runner and a developer debugging one check gets pytest's assertion introspection. `-m machine` marks World-B tests, so `pytest -m "not machine"` gives a hermetic run on any machine (including a CI box with no ecosystem installed).

## 7. Speed

### 7.1 Measured cost of every surface (this machine, 2026-08-10)

| Operation | Wall | Note |
|---|---|---|
| `cc` interpreter start (`cc layers --json`, trivial) | 0.13–0.15s | The per-subprocess floor. |
| `cc resolve --explain --json` | **0.39s** | Whole 16-layer fold. Cheap. |
| `cc workspace verify --project <p> --json` | **0.30s** | ~0.15s of that is interpreter start. |
| `cc workspace --all --json` | **6.3s** | 63 repos, status mode. |
| `cc doctor --json` | **17.3s** | Network + git. Full mode only. |
| `cc reconcile assess --json` | **45.4s** | 63 projects, deepest read-only sweep. Full mode only. |
| `bash .claude/fitness-check.sh` | ~1s/repo | Full mode only; ~70s serial, ~10s parallel. |

### 7.2 Design consequences

**In-process, not subprocess.** Layer 3 imports `project_integration` and calls it directly per repo. Shelling out would cost 70 × 0.30s ≈ 21s in process overhead alone, most of it interpreter start. Subprocess is reserved for `repo.parity.inprocess_matches_cli` on 3 canary repos (~1s) — which is exactly the check that keeps the optimization honest.

**Parallel where independent; serial where shared.**

| Work | Strategy | Why |
|---|---|---|
| Layer 3 per-repo sweep | `ProcessPoolExecutor(max_workers=cpu_count())` | Each repo is an independent pure-filesystem read. ~70 repos over 8 workers ≈ 9 batches of ~0.05s in-process work. |
| Layer 4 lock checks | Same pool, then one serial cross-repo pass | Per-repo checks parallelize; `lock.template.uniqueness` is a fleet-wide hash join and must see all locks. |
| Layer 1 | **Serial** | One shared manifest; the fold is 0.39s. Parallelism buys nothing and risks fixture interleaving. |
| Layer 2 git ancestry | **Serial, batched** | ≤16 pins. One `git for-each-ref` per repo plus one `merge-base --is-ancestor` per pin — 16 cheap calls, not 70. Concurrent git on one repo is asking for index contention. |
| Layer 5 round-trip | **Serial** | Runs installers; takes locks. Never parallel. |
| Layer 6 | Serial | Seconds. |

**Cache.** Per-repo verdicts are cached in `$CC_MACHINE_ROOT/conformance-cache.json`, keyed on a fingerprint of `(git HEAD sha, dirty bit, and (mtime_ns, size) of each of the 13 dimension paths)`. Unchanged repos reuse their verdict. Typical incremental run touches 2–5 repos. `--no-cache` for CI, and the cache is keyed on the harness's own version so a check change invalidates everything.

**Two modes.**

| Mode | Contents | Target | Use |
|---|---|---|---|
| `--fast` (default) | L1 (local fold, no network), L3 (in-process, parallel, cached), L4, L6 | **< 10s cold, < 3s warm** | Run it on every commit and before every remediation step. |
| `--full` | Everything, plus L2 git/remote checks, `cc doctor`, `cc reconcile assess` cross-check, `fitness-check.sh` per repo, and L5's round-trip | **< 3 min** | Nightly, pre-release, and after each remediation phase. |

Fast mode makes **no network calls at all** — that is what keeps it under 10s and what makes it usable on a plane. The 45.4s `reconcile assess` and 17.3s `doctor` are deliberately quarantined in full mode; fast mode gets the same per-repo verdict from the in-process inspector, and `repo.parity.inprocess_matches_cli` proves the two agree.

**Budget check:** 71 repos × 27 Layer-3 checks = 1,917 assertions, each a handful of stats and a checksum on files already in the page cache. Dominated by process-pool startup (~0.4s) and the initial `cc workspace --all` enumeration (6.3s, itself cacheable per boot). Under 10s cold is comfortable.

### 9.1 Collision control

Verified by `git diff --name-only` across branches before merge — no two packages may touch the same path.

- **`src/cc/main.py` is the only shared file.** Exactly one line (`app.add_typer(conformance_app, name="conformance")`). **WP-8 owns it; no other package may touch it.** Every other package is reachable via pytest without CLI wiring, so nothing is blocked waiting on WP-8.
- **`dimensions/__init__.py` is owned by WP-4** and defines the `DimensionCheck` protocol; WP-4a/b/c each add only their own module files and register through an entry table WP-4 owns. Splitting the registry table itself would collide, so it does not split.
- **`tests/fixtures/schemas/`** — WP-1 adds exactly one new file there and touches no existing schema.
- **`tests/conformance/fixtures/`** — WP-2 owns `tiers/`, WP-6 owns `reference-install/` and `degraded/`. Disjoint subdirectories.
- **`tests/conftest.py` (the existing 108-test suite's conftest) is not modified by anyone.** The conformance suite gets its own `tests/conformance/conftest.py`, which inherits the autouse isolation by pytest's normal conftest nesting. Editing the shared conftest would be a fleet-wide blast radius for zero gain.

### 9.2 Landing order and what each unlocks

1. **WP-1** — nothing else can assert without `CheckResult` and the fixtures. Land first, even thin.
2. **WP-7 next, not last.** The six RC regression tests are the deliverable the owner asked for ("must fail today"), they need only `registry` + `types`, and they are the fastest path to a demonstrable red run.
3. **WP-2, WP-3, WP-4(+a/b/c), WP-5 in parallel** — four to seven agents, zero shared files.
4. **WP-6** in parallel but expect it to be the long pole: it runs real installers and needs the reference manifest agreed.
5. **WP-8** once two layers exist, so the CLI has something to print.
6. **WP-9** last — the baseline can only be frozen once the checks that produce it exist.

### 9.3 Definition of done, per package

Every package is done when: (a) each of its checks has a registry entry with severity and a remediation string; (b) each check has a **positive** test (synthetic fleet where it passes) **and** a **negative** test (synthetic fleet where it fails) — a check never proven to fail is not a check; (c) machine-truth checks record their measured current verdict in the baseline; (d) `pytest -m "not machine"` passes on a machine with no ecosystem installed; (e) the read-only tripwire fires zero times across the package's full run.

## 10. Failure modes of the harness itself

Designing for graceful degradation, because a conformance harness that lies is worse than none.

| Failure mode | Degradation | Guard |
|---|---|---|
| A repo is unreadable (permissions, missing mount) | That repo's checks return `UNKNOWN`, not `PASS`; run exits 2 | `inv.no_fabricated_healthy`; `UNKNOWN` can never be coerced |
| `cc` cannot be imported (venv broken) | Exit 2 with the import error; no partial verdict | Import check at startup, before any assertion |
| The real manifest is malformed | Layer 1/2 return `UNKNOWN`; Layers 3–6 still run | `validate_layers` raises `ManifestError` with plain-language text; caught and surfaced, never swallowed |
| A check crashes | That check is `UNKNOWN` with the traceback in `evidence`; siblings continue | Per-check exception boundary in `registry.run()` |
| A test mutates a real path | Whole run fails loudly, naming the path | The pre/post checksum tripwire |
| Cache is stale or corrupt | Silently discarded, full recompute | Cache keyed on harness version + per-repo fingerprint |
| No network in full mode | Network-dependent checks are `UNKNOWN`; local ones still assert | Explicit `requires_network` flag per check |
| The harness disagrees with `cc workspace verify` | Run fails on `repo.parity.inprocess_matches_cli` | 3 canary repos, every fast run |

## 11. What this harness deliberately does not do

- **It does not remediate.** It has no `--fix`. Remediation is `/update-project`, `cc reconcile apply`, and the installer fixes. A harness that repairs is a harness you cannot trust to report.
- **It does not compute a health score.** `RUBRIC.md` §4, enforced by a test.
- **It does not open a ticket per repo for an S0.** S0 is one upstream fix that converts N repos from S0 to S1; the report groups S0 failures **by cause**, not by repo.
- **It does not audit `ECOSYSTEM.md`'s `Local path` column** — non-load-bearing (`/Users/pabs/Sites` and `/Volumes/Dev/Sites` are the same inodes).
- **It does not scan for secrets.** The audit's §4 findings are a separate concern with a separate lifecycle, and the owner has ratified dispositions (Q10–Q13, Q18, Q19) that a conformance harness must not relitigate on every run.
- **It does not verify products.** Per the CSE model, layers carry the *tools*, never the *things you build with them*. D8 is `NA` for class C/D by design.

## 12. Architecture decision records

### ADR-001: The conformance harness lives in `claude-copilot/tools/cc`
**Status:** Proposed.
**Context:** ~70 repos with partial installs and 5 systemic root causes need a verifiable remediation gate. Three candidate homes: `cli-copilot-internal` (believed to own ecosystem-state computation), `claude-copilot` (has a 108-file test suite), or a new repo. `copilot-control-tower`'s invariant #1 says state computation belongs in the CLI, not the app.
**Decision:** Build it in `claude-copilot/tools/cc` as `cc conformance` + `tools/cc/tests/conformance/`.
**Consequences:** *Easier* — checks call the same functions the contract is made of, so they cannot drift; the isolation fixture, 17 contract schemas, and jsonschema pattern already exist; no new repo joins the fan-out. *Harder* — the harness lives inside a repo it audits, so auditor independence is reduced.
**Alternatives rejected:** `cli-copilot-internal` — traced on this machine, it owns Cloudflare/Coolify/Infisical/Discord and contains no resolver, no layer fold, and no project-integration contract; the ecosystem verbs all live in `cc`. Building there would mean re-implementing resolution, the exact "parse, never compute" violation. A new dedicated repo — would have to vendor the contract constants (guaranteed drift), needs the `cc` venv anyway, adds a 17th repo to a fan-out-pained fleet, and repeats the `fitness_*.rs` failure where 40 detached fitness tests now scan a retired tree behind a disabled CI job.

### ADR-002: Wrap `cc`'s existing verbs; never re-implement ecosystem state
**Status:** Proposed.
**Context:** Real verification surfaces already exist at known cost (`workspace verify` 0.30s, `resolve --explain` 0.39s, `reconcile assess` 45.4s, `doctor` 17.3s, `fitness-check.sh` FF1–FF11). The audit's own throwaway `audit.py` re-implemented a subset and produced 7 wrong agent counts.
**Decision:** The harness calls existing modules/verbs for everything they already compute and builds only the six gaps in §2.4.
**Consequences:** *Easier* — a contract change propagates automatically; the harness is small. *Harder* — the harness inherits upstream bugs, so `repo.parity.inprocess_matches_cli` exists to detect the in-process/CLI split.
**Alternatives rejected:** An independent re-implementation (a true second opinion) — rejected because two implementations of the same contract disagreeing is exactly how `RUBRIC.md` Divergence 2 came to be wrong, and reconciling them costs more than the independence buys. Pure shell (fast to write, no dependency on the `cc` venv) — rejected: 70 repos × 27 dimensions in bash is unmaintainable, and it cannot import the contract constants.

### ADR-003: Fast mode makes no network calls; deep sweeps are quarantined in full mode
**Status:** Proposed.
**Context:** `reconcile assess` (45.4s) and `doctor` (17.3s) are the two most informative sweeps and also 62s of the budget. Remediation needs a check run *between every step*, so the default must be seconds.
**Decision:** Fast mode = local filesystem + local git + the local fold, in-process and parallel over repos, cached on a per-repo fingerprint, targeting < 10s cold. Full mode adds network, `doctor`, `reconcile assess`, `fitness-check.sh`, and the round-trip, targeting < 3 min.
**Consequences:** *Easier* — the harness is cheap enough to run constantly, which is the only way it stays true. *Harder* — fast mode cannot see remote drift, so a fast PASS is explicitly a weaker claim, and the JSON records `mode` so no consumer can mistake one for the other.
**Alternatives rejected:** Single mode wrapping `reconcile assess` — simpler, but 45s per invocation means it gets run once a week and stops being a gate. Always-parallel including git — rejected: concurrent git plumbing on one repo risks index contention for a saving of a few hundred milliseconds on ≤16 pins.

### ADR-004: Known-bad baseline plus strict-xfail regression pins
**Status:** Proposed.
**Context:** The owner will not accept remediation he cannot verify. A harness that only reports the current state cannot prove it *would have* caught the regression.
**Decision:** Freeze today's verdicts in a committed baseline; register each RC check `xfail(strict=True)` against it; exit code **3** for baseline regression, distinct from **1** for absolute failure.
**Consequences:** *Easier* — "fixed / still-failing / newly-failing" becomes a number per severity; fixing an RC turns the suite red until the marker is removed, so a fix must be acknowledged. *Harder* — the baseline is a file that must be re-frozen deliberately after each remediation phase, which is a small recurring ritual.
**Alternatives rejected:** Plain assertions with no baseline — cannot distinguish "still broken" from "newly broken," which is the distinction remediation lives or dies on. Non-strict xfail — an RC could get fixed and silently regress with the suite still green, defeating the purpose.
