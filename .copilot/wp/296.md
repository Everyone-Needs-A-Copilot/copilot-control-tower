# Authoritative CLI project-integration contract architecture

## Context and evidence

- Continuation source: `docs/40-initiatives/02-enac-self-onboarding/phases/phase-6-project-integration-aftercare-handoff.md`.
- Actual implementation source: `/Volumes/Dev/Sites/COPILOT/claude-copilot/tools/cc` on `feat/adopt-and-project-setup`; `/Volumes/Dev/Sites/COPILOT/cli-copilot` is a different public service CLI and is not the workspace/onboarding source.
- Current focused baseline: `uv run pytest tests/test_workspaces_contract.py -q` -> 38 passed.
- Current `workspace_status()` treats any recognized component as project Ready, merges Claude and Codex into one row-level state, reduces all target collisions to one string, and treats lock membership/marker presence as proof without a closed per-component contract.
- Control Tower already vendors `docs/01-architecture/schemas/workspaces.schema.json`, but upstream `tools/cc` has no workspace schema fixture or schema-validation test. Contract ownership is therefore inverted.
- Live representatives confirm the required distinctions: exact current Claude framework files plus protected local `CLAUDE.md` (`admin-server`); complete legacy Codex layout missing only current metadata (`codex-copilot`); one healthy side plus a custom entry point (`h3`, `convoco-policy-build`); guidance-only (`crm-automation-copilot`); deep specialization (`preflight-copilot`); mixed customization (`research-copilot`, `transformation`); customized and complete positive control (`pipeline-copilot`).

## Decision

### 1. Evolve the wire contract additively as schema `1.1`

Keep the existing major because the installed Control Tower gates only on major `1`, ignores additive keys, and already understands the legacy `state` enum. Preserve all existing fields during migration, but tighten legacy semantics:

- `state: ready` only when every expected component verifies;
- `setup-available` / `activation-required` for bounded safe finishes;
- `blocked` as the compatibility projection for guided integration, owner decision, and could-not-verify;
- `can_apply_now` is true only for a currently valid declared safe action.

Add authoritative fields rather than making the app derive meaning:

- project `classification`: `ready | safe-finish | guided-integration | owner-decision | could-not-verify`;
- `responsible_actor`: `none | cli | project-author | project-owner | ecosystem-owner | person`;
- closed `components[]` entries for Claude and Codex;
- project capability inventory, preservation requirements, prohibited actions;
- optional safe action summary;
- optional full integration plan/prompt/handoff on single-project inspection only;
- independent verification command and stop conditions.

Add a new `classification_summary` while retaining the old `summary` projection for existing consumers.

### 2. Make per-component evidence closed and fail-closed

Each `components[]` item carries:

- `component`, `expected`;
- `expected_contract: {id, version}`;
- the same closed classification enum;
- `recognized_setup: {variant_id, version, evidence[]}` or null;
- `missing_requirements[]`;
- `responsible_actor`;
- `safe_action` or null;
- `verification`.

Evidence entries use bounded kinds (`marker`, `manifest`, `framework-file`, `project-file`, `link`, `lock-record`) and states (`verified`, `missing`, `mismatch`, `unreadable`). Any unreadable relevant artifact, unsupported lock/declaration version, unknown symlink target, or incomplete required evidence produces `could-not-verify`, never Ready or safe finish.

Lock membership alone is not proof. A current lock must be structurally valid and its required recorded artifacts must still exist and match. Marker-only legacy recognition is allowed only through a named, tested variant matcher.

### 3. Safe finish requires an exact matcher or empty targets

Safe finish is allowed only for:

- a completely absent component whose complete installer target set is empty;
- a named immutable legacy/current layout matcher whose framework-owned artifacts match a trusted release and whose remaining change is additive;
- a known repair with an explicitly bounded file set.

Examples:

- `admin-server`: recognize exact Claude framework-owned commands/agents without treating the protected local `CLAUDE.md` as framework-owned; add only proof/lock material plus a non-colliding Codex setup if all Codex targets are empty.
- `codex-copilot`: recognize the complete Codex plugin/skill/gate/marketplace layout and add only missing current metadata/proof before considering Claude.
- `transformation`: Claude may be recognized, while its custom `AGENTS.md` makes Codex guided integration.

Every safe action returns an opaque `action_id`, `kind`, affected components, precondition inspection id, `will_add`, `will_preserve`, and `will_not_change`. The app passes the opaque id back to `cc workspace finish`; it never sends file operations. Apply re-inspects first and refuses stale action ids. Writes are staged/rolled back on failure, followed by independent re-verification; “applied” alone never means Ready.

### 4. Deterministic inspection produces the guided route, not semantic judgment

The CLI inventories known project capability locations without following external symlinks or exposing file contents: entry instructions, agents, skills, commands, plugins, rules, integrations, and framework markers. It reports counts and repo-relative paths. Unknown or overlapping entry content is a positive preservation fact and routes to guided integration; it is not a generic failure.

A single-project status response may include `integration_plan`:

- opaque `plan_id` and `inspection_id`;
- detected/missing contract facts;
- capability inventory;
- required preservation and prohibited actions;
- allowed bounded outcomes;
- prompt payload version and text;
- owner-handoff payload;
- verification argv (array, never shell text as the executable contract);
- stop conditions.

The all-project report omits full prompt/handoff text to keep the poll bounded, exposing only `plan_available` and summary facts. Control Tower fetches one project before opening details.

### 5. Separate external assistance from authoritative verification

New declared verbs:

- `cc workspace finish --project <path> --action-id <id> [--apply] --json` — exact safe action, stale-id refusal, re-verification;
- `cc workspace verify --project <path> [--plan-id <id>] --json` — read-only reinspection and complete contract verdict;
- `cc workspace hold --project <path> --plan-id <id> ... --json` — records only an unresolved owner decision in a bounded machine-local registry. It can never mark Ready.

The external agent’s report is advisory except for creating an incomplete `owner-decision` hold. Only `verify` can classify Ready. A plan/action id is invalidated before launch/apply if relevant artifacts changed. After guided edits, verification inspects the new state and either returns Ready or emits a fresh remaining-work plan.

### 6. Contract and fixture ownership moves upstream first

Add to `claude-copilot/tools/cc` before classifier code:

- `tests/fixtures/schemas/workspaces.schema.json` as the machine source of truth;
- schema validation in `test_workspaces_contract.py` using installed `jsonschema 4.26.0` / Draft 2020-12;
- synthetic, content-minimized fixture corpus for all representative shapes and all five classifications;
- negative fixtures for unreadable evidence, malformed locks, escaped symlinks, stale action/plan ids, and partial writes.

Fixtures model real layouts and counts but do not copy sensitive project contents. Live representative projects are exercised read-only as acceptance evidence; their trees are never fixture sources and are never mutated during classification.

After CLI QA, mirror the frozen schema/prose into Control Tower and update Swift DTO/rendering. Do not implement 31/11/11 as code or an acceptance expectation; only individual fixture outcomes are asserted.

## Rejected alternatives

1. App-side classification or content scanning — violates parse-never-compute and creates a second source of truth.
2. Hard-coded 31/11/11 — research grouping, not an executable verdict.
3. Treat every existing target as guided — loses safe exact-match adoption and strands compatible projects.
4. Treat marker presence or any customization as Ready — reproduces the current false-Ready bug.
5. Put full prompts in every `--all` poll — expands payload and app memory without serving the list view.
6. Let an external assistant report completion as Ready — self-report is not verification.
7. Replace `configure` wholesale — unnecessary migration risk; retain it for greenfield setup while `finish` handles proven aftercare actions.

## Fitness functions and QA evidence

- Every emitted status/detail/finish/verify report validates against the upstream Draft 2020-12 schema.
- Missing required classification/evidence/actor/action fields fail schema validation and consumer decoding.
- Each expected component has exactly one component entry and one closed classification.
- Project Ready implies all expected components Ready and a successful independent verification.
- Safe finish implies a non-null action id and exact matcher/empty-target evidence.
- Guided/owner/could-not-verify never expose an applicable safe action.
- Classification is byte-for-byte read-only across representative project fixtures and live acceptance targets.
- Safe finish stale-id and mid-apply failure tests prove zero overwrite and rollback of newly written artifacts.
- Existing Control Tower `1.x` decoding remains green until the app is migrated.
- Final QA work product must contain `ARTIFACT: test-run|...` and a passing verdict token.

## Risks and failure modes

- False recognition of a legacy layout: contain with named immutable matchers and negative near-match fixtures.
- Source-release drift: matcher ids include contract/release identity; unknown variants fail closed.
- Large inventory/prompt payload: full payload only on one-project detail.
- Symlink escape/content leakage: repo-relative, lstat-based inventory; external targets are evidence only and never traversed.
- Partial safe action: preflight, staged new files, rollback, and post-action verify.
- App/CLI rollout skew: additive `1.1` fields plus retained legacy projection; schema major stays `1` until old DTOs are removed.
- Untracked framework files already present in the Claude Copilot worktree: implementation must touch only tracked `tools/cc` surfaces and preserve unrelated untracked files.
