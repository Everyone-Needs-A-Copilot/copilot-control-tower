M2 QA (T19): settings::guard::scan_for_secrets had two real adversarial blind spots, both fixed. (1) is_high_entropy_token's class_count<2 gate let ANY single-character-class string (e.g. a 40-char purely-lowercase-alpha token) through regardless of entropy -- fixed by adding a higher-bar (entropy>=4.5 vs 4.0) single-class tier, tuned against real English/snake_case entropy measurements (~3.6-4.4) to avoid false positives. (2) scan_mapping_for_secrets only ever called scan_value on the VALUE of an extra/unmodeled mapping entry, never the KEY itself -- a secret embedded as a literal map key (e.g. 'ghp_xxx: innocuous value') bypassed the scanner entirely. Fixed by also running secret_reason_in on the key string, with a critical follow-on: the field label must NOT echo the raw key text in this case (that would put the secret INTO GuardError.field, violating the module's own never-echo-a-secret discipline) -- use a fixed '<redacted field name>' label instead when the KEY (not the value) is what matched.
