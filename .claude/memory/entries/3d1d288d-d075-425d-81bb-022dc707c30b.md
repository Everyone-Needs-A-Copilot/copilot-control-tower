Conformance harness lives in cc, not the copilot CLI (PRD-22, 2026-08-10). Ecosystem conformance harness lives in claude-copilot/tools/cc as 'cc conformance', NOT cli-copilot-internal. Traced live: ~/.local/bin/cc shims claude-copilot/tools/cc and owns EVERY ecosystem verb (resolve/doctor/freshness/update/deprovision/layers/workspace/reconcile/extensions); /opt/homebrew/bin/copilot (cli-copilot-internal) is infra/services only (Cloudflare/Coolify/Infisical/Discord) with zero tier resolution -- confirms the 'four programs, two names' memory. Rejected a dedicated repo: it would vendor _CLAUDE_REQUIRED_LOCK_PATHS + the classification ladder (guaranteed drift) and repeat the 40 detached fitness_*.rs that now scan a retired tree behind a disabled CI job. Accepted trade-off: the harness lives in a repo it audits; mitigated because the RC checks assert on artifacts OUTSIDE claude-copilot (codex-copilot/scripts, ~/.config/copilot/copilot.layers.yml, ~70 repos), a registry-completeness test makes deletion a visible red diff, and it gates the release. Measured costs that shaped the design: cc interpreter start 0.13s, workspace verify 0.30s/repo, workspace --all 6.3s/63 repos, resolve --explain 0.39s, doctor 17.3s, reconcile assess 45.4s -- so fast mode is in-process + parallel + cached with NO network (<10s) and full mode quarantines doctor/assess/roundtrip (<3min). Correction to the gap report: RC-4's real per-project lock generator is projects.py::write_project_lock, NOT core/ecosystem/lockfile.py (that is the machine-level ecosystem lock with a different schema).
